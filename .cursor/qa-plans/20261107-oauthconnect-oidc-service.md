### G-4 — JWKS technique, rotation et concurrence [A]

- Nominal : deux instances/issuers avec kid identique mais clés différentes et sub éventuellement identique ; chacune accepte sa clé et refuse l'autre sans emprunt de confiance. Même instance servie par deux clients/replicas reconnaît son token/context v2 sans cache de corrélation préalable ; pas équivalence simulée via une map globale de tokens.
- TTL≤300s : reçu/cache frais utilisable selon contrat, après expiration sans refresh réussi→refus (pas stale infini). Avancer la couture R-temps, tokens renouvelés/encore valides pour que leur exp ne masque pas le TTL. Définir inclusivité exacte au raccord R-temps ; ne pas copier un TTL défaut de bibliothèque différent.
- Rotation : clé initialeA puis publierB, kidB inconnu à instant admissible hors cooldown ; au plus un refresh puis acceptation siB publiée, sinon refus. Répétitions dans30s/instance ne multiplient pas GET ; après nouvelle fenêtre autorisée un refresh peut reprendre. Une réponse JWKS contenant kid ambigu/mal formé ne rend pas un token acceptable. Politique de conservation/remplacement des clés après rotation à reprendre de l'annexe, pas inventer un grace period.
- Single-flight : complétions concurrentes avec **codes distincts** et kid nouveau, GET JWKS retardé/contrôlé ; un refresh en vol partagé, tous terminent selon la même mise à jour. Après échec/timeout de ce refresh, waiters finissent en erreur bornée et future fenêtre permet reprise, pas verrou bloqué ni refresh herd. Un POST token par opération, jamais single-flight/retry du code OAuth.
- Oracle : reçus JWKS filtrés par issuer/phase, chronologie contrôlée et résultats crypto réels ; pas seulement compteur global ou mock disant « cache hit ». Aucun sommeil30/300s ni benchmark/performance promise ; si couture de temps/synchronisation absente, ce sous-ensemble est blocked et exige réconciliation API, pas un nouveau harness générique.

### G-5 — registry connue, canonicalisation et deux opérations [B]

- Nominal : registry construite au boot avec deux slugs et vraies instances OAuth déjà implémentées ; montage préfixe `/oauth-connect` une fois, authorize/complete de chaque slug atteignent leur vendor et DTOs exacts. Réutiliser `router_v2`/`ConnectState`, pas recompiler sa logique à part. Catalogue immutable selon API retenue, pas de mutation depuis une requête.
- Négatif : inconnue/noncanonique→404 sans vendor ; known GET métier→405 ; aucun alias v1, `/v2/profile`, callback navigateur ou wildcard de fallback. Cas de casse/prefixes/slash/encodage à préciser via R-service ; ne pas attendre qu'une canonicalisation d'URL par le client HTTP transforme le test avant arrivée au serveur (URI brute reçue doit être vérifiée).
- Corps signé ne choisit jamais le slug : erreur d'instance/path ne devient pas lookup provider dans JSON. Health/readiness GET autorisés aux seuls chemins plateforme retenus, sans config/catalogue/secrets ; leur succès n'est pas un succès d'authentification. Aucun bearer utilisateur/FGA/DB ajouté.
- RED : router/service compilable refuse les positifs connus ou ne monte pas les sous-routes ; ne pas qualifier les404 d'une application vide comme couverture des refus.

### G-6 — HMAC OriginalUri et refus avant I/O [B puis C]

- Nominal : signature METHOD/PATH complet/TIMESTAMP/BODY pour les **deux** opérations, inclut sous-route instance et préfixe avant nest via OriginalUri. Requêtes utilisant cléA atteignent seulement clientA ; résultat minimal sans raw claims. Exercices router réel puis listener réelC, pas seulement `RecordingClient` hérité.
- Négatif : cléB/corps ou nonce/PKCE muté, signature PATH nu ou instance changée, headers absents/timestamp périmé/bearer seul→401 et vendor0. Aucune tentative de toutes les autres clés. Fenêtre inclusive30s déjà vérifiée dans les fonctions pures HMAC ; en réseau utiliser un timestamp franchement périmé, pas une course à±1s de la limite.
- Corps entrant>64KiB→413 existant sans appel client ; signature valide+JSON/champs v2 invalides→codes existants d'extraction/validation, pas401 générique substitué ; erreur de collaborateur/validation OIDC après authentification→502 générique sans contenu fournisseur. Codes exacts à reprendre des handlers existants et API réconciliée, pas nouvelle enveloppe.
- Oracle : HTTP exact, vendor/auth calls0 ou1 par opération, destination et clé attendues ; sign dans le test depuis route constante/raw body fixture, pas depuis le PATH retranché calculé par nouveau router. Aucune fuite nonce/code/verifier/access/id_token/secrets/references dans Debug/Serialize quand applicable/erreurs/logs/chaînes source. Les DTOs non sérialisables restent non sérialisables, pas harness compile-fail ajouté.

### G-7 — composition mixte complète et readiness [C, après A+B intégrés]

- Nominal : vrai loader+config (OAuth et OIDC, modes direct/vault supportés), vraie résolution SDK, vrai builder, discovery/JWKS validés et vrais clients ; registry contient **toutes** les instances avec leurs clés canoniques, puis router/listener démarre. Flux authorize/complete HMAC OAuth et OIDC depuis le listener renvoie tokens+profils attendus. Nonce/challenge envoyés pour OIDC ; OAuth ne transmet toujours pas nonce OIDC au vendor.
- Négatif : dernière instance secret/issuer/métadonnées/JWKS/CA invalide, acquisition initiale en panne, identifiant dupliqué ou bind/TLS local impossible→erreur de boot et aucune registry utilisable/ready/publiée partiellement. Des GET préparatoires déjà effectués ne sont pas annulés rétroactivement ; pas exigence de rollback réseau. La panne vendor après boot refuse la requête mais ne désinscrit pas l'instance.
- Boot/snapshot : pas résolution coffre par appel, keys/credentials corrects par instance, cache JWKS est technique et isolé, aucun cache access_token→identité/nonce. Startup readiness observée seulement après toutes les préconditions. Un token valide après redémarrage/autre app s'authentifie avec contexte v2 fourni, pas grâce à une transaction process-local.
- Oracle : vrai résultat de composition/registry, reçus par instance et service réellement joignable ; pas `is_ok()` seul, faux readiness statique ou substitution d'un client de fixture au builder produit. REDC sur socle de composition refusant même quand A/B contrôles nominaux sont verts.

### G-8 — listener et binaire Windows RustyCog [C]

- Tests listener : réemploi `start_router_owned`/OwnedHttpServer ou API wrapper ratifiée ; bind0/adresse réellement annoncée, readiness bornée, requête HMAC réussie et refus représentatif sur TCP réel, TLS CA/SAN si TLS activé. `request_shutdown`/join bornés et sockets/tâches fermées même sur assertion/panic ; pas nouveau mécanisme de serveur maison.
- **Binaire** : target `.exe` réel compilé dans le paquet service (CARGO_BIN_EXE/artefact réel à confirmer R-service), processus enfant à cwd/config/tempfile/env isolés ; son chemin fait loader→logging RustyCog→setup→registry/router→serve, pas un main de test substitué. Contrôle positif readiness **et** appel v2 signé via son adresse ; mauvais config/secret/discovery/TLS→exit nonzero sanitized sans service métier prêt.
- Adresse/port0 et stop Windows à réconcilier avec l'API avant test : ne pas présenter un « find free port puis close » racy comme réservation garantie, ni ajouter une route shutdown au produit. Parent possède uniquement ce child ; arrêt gracieux si supporté, terminaison bornée du seul child+wait en dernier recours de cleanup, jamais taskkill par nom/global. stdout/stderr bornés/capturés sans secrets ; timeout de lancement est échec de preuve, pas PASS fail-closed.
