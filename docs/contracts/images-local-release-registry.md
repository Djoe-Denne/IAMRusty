# Contrat — Images locales/release et registre applicatif

- **Proposed / Partial**, 2026-11-01 ; canon : [ADR-0607](../adr/0607-images-source-snapshot-registre-zot-hors-kind.md). Base initiale `f609105`, SDK `93b890f` ; pas de GO runtime par ce document. Registre/publication OCI désormais implémentés et éprouvés localement ; raccord Kind et refresh codés, qualification live en attente d'un bail explicite.
- Directions utilisateur acquises : local rapide = code courant, cache Linux conservé, images autonomes ; release = commit exact de `master` ; Zot local hors Kind. Les détails suivants restent Proposed, pas un Accept global.
- Un backend Python Windows/CI Linux, recettes/cibles du catalogue commun. Pas de code applicatif Rust/SDK, de nouvel orchestrateur d'agents ni de framework de plugins.

**Arbitrage humain accepté le 2026-11-01 : « Snapshot final »**, identifiant auditable **`snapshot-final-v1`**. A→B→A est accepté si l'image vient du snapshot immuable A et si les entrées finales sont byte-identiques A, SDK compris ; toute différence finale est refusée. Aucun watcher natif/daemon exigé, aucune détection des transitoires prétendue. Pas d'Accept global de l'ADR ni de qualification cloud déduits.

**Delta acquis par le parent :** réutiliser `ops/deploy/build/images.py`, **`aiforall.image-build/v1`**, capture/profils/cibles sélectionnées, export exact, provenance content des consumers et `--build-manifest`/kind-load explicite. Après correctifs relus : 52 Python offline PASS et oracle Cargo natif Windows 1/1 PASS communiqués (§7/§9). `--policy release`, `--revision` et `--cold` restent gated avant capture/Docker ; `--profile release` est une optimisation **locale**, pas une release livrée. Build Linux réel `ext-authz`, réemploi chaud et publication OCI acquis ensuite (§10). Pas de duplication de cette couche ni de digest OCI simulé par un ID Docker.

## 1. Entrées et preuve de source

**Modes exclusifs :** `working-tree` pour le local livré ; `commit` est la cible release future, non implémentée par A. Aucun repli d'un mode vers l'autre, d'une image manquante vers un ancien tag, ou de la release vers le dirty.

- `working-tree` capture les octets actuels, pas seulement `git diff` : modifications suivies, nouveaux fichiers pertinents, recettes/scripts et SDK effectivement résolu. Son HEAD est une information de base, **pas** l'identité complète. Un changement pertinent du SDK avec le même HEAD doit modifier son identifiant d'entrées. Ne pas lire automatiquement le dépôt frère à la place du SDK consommé.
- `commit` exporte automatiquement l'objet choisi de `master` et le contenu du gitlink SDK de **ce commit**, locks et recettes compris. Vérifier appartenance à la principale et référence distante retenue ; résoudre le SHA avant export. Pas de `checkout/reset/stash` du workspace, pas de copie du sous-module dirty courant. Gitlink indisponible ⇒ échec explicite. L'UI Obsidian étrangère ne bloque ni ne contamine cet export.
- Le catalogue définit par cible une fermeture conservatrice des entrées : packages/path dependencies réellement utilisés (SDK inclus), `build.rs`/assets, fichiers runtime COPY et recette ; manifests/locks/config build et scripts partagés. Réutiliser les boundaries content du parent et vérifier leur couverture, pas ajouter un framework de graphe. Ne pas étendre silencieusement à tout le disque.
- L'inventaire de fichiers ne dépend pas de leur statut Git : nouveaux modules/build inputs inclus. Allowlist de sources/assets et exclusions privées explicites, chemins relatifs normalisés et ordre déterministe ; refuser collisions de casse, reparse/symlink sortant et type spécial. `.env*`, credentials, clés privées, kubeconfigs, états agent/runtime et caches ne sont **ni lus, ni copiés, ni hachés**. Les fixtures publiques nécessaires sont classées explicitement, pas admises parce qu'un nom semble inoffensif. Pas de promesse qu'un scanner détecte tout secret enfoui dans du code.
- Préserver le `.dockerignore` utilisateur. Réutiliser les Dockerfile-specific fournis et identifier le filtre **effectif** selon leur précédence ; le contexte envoyé au builder est une copie fermée/hors Git, pas `.` non filtré. Hash des seules entrées non secrètes réellement admissibles et de la recette/options/outils ; jamais de credentials de registre dans ce contexte.

**Capture/fraîcheur — `snapshot-final-v1` :** inventaire/hashes, copie privée fermée vérifiée puis compilation depuis cette copie immuable. Recalculer les entrées effectives après build et, pour B, après publication, puis avant consommation locale ; SDK réel inclus. Toute différence finale ou impossibilité de comparer ⇒ **STALE**, non-zéro, aucun manifeste consommable promu. Un mtime préservé ne dispense pas de relire les octets. Si A→B→A intervient sur l'arbre vivant, le résultat issu du snapshot A reste admissible lorsque l'état final est byte-identique à A ; il n'est pas nécessaire de détecter cet aller-retour. Le code peut refuser une instabilité observée pendant capture, mais ne revendique pas un audit continu des mutations. Aucun watcher/daemon requis.

La copie compilée ne devient jamais un mélange de fichiers vivants. Un candidat déjà publié dont les entrées finales diffèrent reste un ancien snapshot, pas un résultat courant. Le reçu de build porte `freshness_policy: snapshot-final-v1` ; la publication reprend cette politique explicitement et ne la transforme pas en preuve de mutation continue ou de conformité release. Le vérificateur local recalcule les IDs par cible : une autre cible inchangée peut garder son image, même si l'ID global du lot a changé.

## 2. Cargo, caches et export exact

- Garder le builder BuildKit Linux existant ; base compilateur stable, dépendances/outils épinglés et réutilisés, puis compilation/exports, puis images runtime. Les builds conteneur sont ici de la **livraison Linux pour Kind**, pas le remplacement des builds/tests de dev natifs Windows.
- Profil **`dev-image`** proposé : hérite `dev`, `opt-level=0`, `debug=0`, `incremental=true`, sans LTO ; pour fonctionnel/itérations rapides. **`release`** optimisé, incremental désactivé ; seul profil admissible pour mesures perf/release. Conserver les sélections legacy `workspace`/`openbao` ; `DELIVERY_PROFILE` (sélection) et `CARGO_PROFILE` (optimisation) ne sont pas interchangeables.
- Un Cargo de compilation sélectionnée, `--locked`, packages/binaires/features du catalogue : **sélection complète demandée**, même si une seule image est périmée ; Cargo décide les recompilations, le packaging reste limité aux images périmées. Le hash de contexte et les labels `build-context`/`build-targets` lient sélection complète, profil et union des features ; ne pas reconstruire avec un sous-ensemble puis réutiliser sous le contexte complet. **24 jobs via la config**, aucun `-j`/`CARGO_BUILD_JOBS` divergent ; cible Linux explicite, jamais E:\cargo-target ni un mount target Windows. Cache registry/git préservé ; accès target exclusif (`sharing=locked`).
- **Barrière anti-binaire stale :** journal content→mtime remplacé atomiquement et fsync **avant Cargo**, indépendamment du succès de compilation. Pour un contenu changé/rollback, date effective relue strictement postérieure au floor des fingerprints conservés, y compris après échec partiel ; dates des octets inchangés conservables. Cache dans le futur/précision insuffisante ⇒ refus sans purge, jamais vieux binaire déclaré frais. Manifest `image-inputs.json` obligatoire pour `DELIVERY_PROFILE=images`. Le mécanisme est relu et éprouvé nativement Windows (§7) ; sa qualification Linux/BuildKit reste à faire, sans second checkout manuel ni target Windows partagé.
- Cette synchronisation et l'ID d'entrées participent à l'étape compile ; ne pas compter sur un simple `touch` pour invalider COPY/RUN BuildKit. Ni label nouveau ni `compiler-artifact` JSON ne prouvent à eux seuls que Cargo a vu une modification. La preuve A→B→A avec mtime host conservé doit porter sur les **octets/comportement du binaire**, y compris une entrée de build script. Pas d'option Cargo nightly checksum imposée ; elle ne couvre d'ailleurs pas tous les inputs build script.
- Export uniquement des `compiler-artifact` correspondant aux couples package/binary/features attendus, existence + hash vérifiés avant repackage ; jamais `find` dans target/deps, ni ancien fichier trouvé dans le cache. Le parent possède l'inventaire exact (migrations distinctes, Sentinel, ext-authz/controller et Cosign) : ne pas inventer de collision actuelle. Les runtime Dockerfiles copient ces exports exacts ; aucun Cargo embarqué séparé ou binaire monté au lancement.
- **Release froide, cible future gated dans A :** `cache_mode=cold-compilation` créera un ID target neuf et forcera seulement l'étape compile (nonce explicite), tout en gardant les téléchargements registry/git. Dev/warm-release préservés ; pas de `prune`, wipe ou `cargo clean` global. Ce mécanisme ne devient utilisable qu'avec la future policy commit-release ; l'option `--cold` est refusée dans A. Pas de promesse de machine/réseau entièrement froid ou de build bit-à-bit reproductible.

## 3. Zot hors Kind et transport

**Registre distinct, phase B :** Zot **2.1.22**, image officielle épinglée par digest Linux/amd64 avant exécution. Correction empirique de la proposition 2.1.8 : cette dernière refuse les ACL avec mTLS seul ([issue 3085](https://github.com/project-zot/zot/issues/3085)), sans contournement htpasswd/proxy. Volume/stockage applicatif propre persistant et réseau Docker dédié ; aucune adoption, copie ou migration du Zot/PV/credentials P4, qui reste en **2.1.8**. Le bootstrap ne requiert ni cluster, ni OpenBao, ni Secret Kubernetes. Smoke réalisé sans opération Kind ; le raccord nodes est phase C.

- Autorité OCI proposée : **`aiforall-apps-registry:5000`** ; alias Docker unique vérifié, pas nom d'ownership. Helper de publication sur son réseau dédié → cette autorité. Hôte Python → `https://127.0.0.1:<port-explicite>` (bind loopback seulement) pour vérification. Aucun `/etc/hosts`, DNS global ou modification Desktop/WSL nécessaire.
- Nodes : rattacher le **seul conteneur registre possédé** au réseau Docker effectif des nœuds attestés, alias identique ; découverte/connexion derrière l'autorité de cible. Ne pas connecter les nœuds à un nouveau réseau ni supposer que le réseau `kind` est privé à cette mission. S'il est partagé, d'autres conteneurs peuvent joindre Zot : **mTLS + ACL**, non le nom du réseau, porte alors l'isolation d'accès. Collision/ambiguïté ⇒ STOP.
- Bundle PKI **registry distinct**, extension explicite non destructive de l'outil commun : leaf serveur SAN DNS `aiforall-apps-registry` et IP `127.0.0.1`, plus deux leaves client `registry-publisher` et `registry-reader` (CN uniques, EKU clientAuth). CA mesh existante réutilisable, jamais CA workload Lazaret ; aucune ancienne clé/CA/leaf remplacée ou hash de clé dans les preuves. CA privée reste hôte, hors build/context. Bootstrap/génération hors Kind reste possible dès le départ ; pas de dépendance au bundle OpenBao pour le registre.
- **mTLS Zot 2.1.22** : `http.tls.{cert,key,cacert}`, sans Basic/bearer parallèle ; validation ACL mTLS-only supportée, CN par défaut. Publisher : `read/create/update` sur `apps/**`, sans delete/admin. Reader : `read` seulement sur `apps/**`. Anonymous/default et tout autre repo/CN refusés. Les clients présentent **la leaf seule**, CA dans le trust store séparé. Le check de pin utilise RepoDigests et la plateforme ; `.Id` Docker reste opaque (manifest/index avec le store containerd observé, config avec certains stores classiques).
- Bootstrap minimal codable : entrée explicite `state-dir` privée hors Git, bundle PKI et port hôte (défaut proposé **15443**, collision ⇒ refus/override explicite), pins Zot/helper. Créer les volumes propres, y provisionner uniquement les données/runtime TLS nécessaires puis lancer Zot non-root ; initialisation des permissions uniquement sur volumes fraîchement créés ou ownership vérifié, jamais chown d'un disque inconnu. Si un helper d'initialisation est nécessaire, il est borné à ces volumes, sans socket Docker. CA privée jamais transférée. Aucun « Ready » avant lecture mTLS authentifiée de `/v2/` avec la bonne CA.
- **Helper OCI Skopeo épinglé**, un outil de transport borné, pas nouveau builder : exporter par ID exact l'image autonome du daemon dans une archive privée ; copier via le helper vers Zot avec format OCI, vérification TLS et certificat publisher monté lecture seule. Le helper n'a **ni socket Docker, ni clé CA**, ni secret en argument/image/log. Cert-dir Skopeo scoped (`ca.crt`, `client.cert`, `client.key`), droits privés parents POSIX/Windows. Le reader suffit pour les vérifications hôte. Pas d'installation Skopeo globale Windows, de `docker login` global ou d'insecure-registry.
- Justification : le daemon/builder par défaut ne reçoit pas automatiquement notre CA. Le helper conserve ses caches existants sans changement global de trust ni migration froide vers un autre daemon BuildKit ; coût = export/archive et petit client OCI réutilisé. Si la plateforme ne permet pas le bind privé requis, STOP ; pas de nouveau disque/partage Desktop imposé silencieusement.
- Vérifier manifeste OCI publié, corps/digest et config (labels/profil/plateforme). En V1, une plateforme `linux/amd64`, manifeste OCI simple ; ne pas déduire un digest du tag, Docker ID ou nom d'archive. Tags de candidats uniques par build, sans écrasement ; consommation uniquement par digest. La policy de copie du helper est locale aux archives possédées et ne prétend pas vérifier une signature de release/P4.

Tous les outils/base images (Rust, frontend, Skopeo, Zot, outils runtime nécessaires dont Cosign controller) ont un pin/version enregistrés dans une petite lock de livraison et dans `toolchain_id`. Tags actuels seuls ne suffisent pas à la release : pins absents ⇒ blocage avant build/publish, pas digest inventé dans ce plan. Le provisioning des identités est local/private PKI, indépendant du coffre ; renouvellement/rotation explicites, pas remplacement silencieux à expiration.

## 4. Interfaces de consommation

États : **CAPTURED → BUILT → PUBLISHED → VERIFIED → CONSUMED**. Échecs `STALE`, `CONFLICT`, `UNSUPPORTED`, `FAILED` ne deviennent pas un ancien succès. Un reçu BUILT contient ID Docker + exports vérifiés ; ce n'est pas un manifeste OCI de déploiement. Pas de reçu release/v1 final avant publication vérifiée et contrôle de fraîcheur final.

Le reçu de build **`aiforall.image-build/v1`** du parent reste inchangé dans son rôle : il porte des IDs Docker, pas des digests OCI. La publication produit un reçu distinct **`aiforall.image-release/v1`**, JSON strict, dont les champs minimaux suivants sont à mapper depuis ce build manifest sans le réinterpréter :

```text
schema: aiforall.image-release/v1
freshness_policy: snapshot-final-v1
source: { mode: working-tree|commit, snapshot_id, root_revision,
          sdk_revision, cargo_lock_sha256, mainline_ref? }
profile: dev-image|release
cache_mode: warm|cold-compilation
platform: linux/amd64
toolchain_id: sha256:...
images: { <clé image_catalog>: {
  inputs_id: sha256:..., sdk_inputs_id: sha256:...,
  oci_ref: aiforall-apps-registry:5000/apps/<repo>@sha256:...,
  manifest_digest: sha256:..., config_digest: sha256:...,
  artifacts: [{ package, binary, sha256 }]
} }
```

`inputs_id` lie contenu de la fermeture de cette cible + recette/options/profil/outils. `snapshot_id` identifie la capture du lot, pas une obligation de rebâtir toutes les cibles quand une seule change. Le manifeste ne contient pas les clés, mots de passe, empreintes de secrets ou chemins privés de provisionnement. L'ID Docker peut rester dans le reçu de build pour diagnostic, **jamais comme `manifest_digest`**. Labels OCI/AIForAll concordants avec ce reçu : mode, input ID, profil, révision de base et SDK réel ; labels ≠ signature. Le nom du schéma release/v1 désigne la distribution OCI : il ne ratifie pas à lui seul le profil/source d'une release cloud.

- **Local nominal :** vérifier chaque target requis contre ses entrées actuelles, profil et plateforme, ainsi que l'existence/identité OCI. Correspondance ⇒ réutilisation permise ; différence ⇒ build explicite ou refus, jamais `latest`/ancien reçu. Les nouveaux fichiers et SDK dirty comptent.
- **Livraison release :** `source.mode=commit`, profil release, SHA principale exact, `mainline_ref` obligatoire, gitlink SDK et locks/pins conformes à l'export ; source propre **dans l'export**, pas exigence de nettoyer le workspace étranger. Une mesure perf exige le profil release ; un snapshot working-tree peut servir à une mesure locale clairement identifiée, jamais être promu comme livraison release/cloud.
- Les consumers `local-full-images.py`, renderer et deploy distinguent **build/v1** (compatibilité locale kind-load explicitement sélectionnée, déjà codée) et **release/v1** (publication OCI). Dans ce dernier flux : `repository@digest`, `IfNotPresent`, pas `Never`/kind-load caché. Le rendu digest fourni par le parent est réutilisé. Aucun remplacement silencieux d'un reçu OCI manquant par un reçu Docker local ; phase A ne revendique pas la distribution de B/C.
- Un déploiement depuis manifeste ne compile/publie rien. Un `local up` peut composer préflight registre → capture/build/publish si nécessaire → vérification → readiness/consommation séparées. Une URL locale de registre n'est pas par magie routable en cloud : publication distante explicite et vérifiée avant un manifeste de cette destination, sans rebuild implicite du consumer cloud. Aucun adaptateur cloud livré ici.

## 5. Autorité Kind, ownership et arrêt

- Étendre **`LocalClusterTargetAnchor`**, pas créer une API `exec` libre : opérations fermées de connexion du registre, installation/vérification trust pour cette seule autorité et pull/probe. Vérifier leasev2/IDs/CP endpoint-mapping **avant tout API GET**, puis UID avant mutation ; tous les nœuds visés appartiennent aux IDs attestés. Mauvais port, stale UID, foreign/legacy ⇒ zéro opération node/publish-pull supposée sur cette cible.
- Installer via cette autorité les seuls fichiers de `certs.d/<autorité>/` (CA publique, leaf/key reader privées, `hosts.toml` pull/resolve, TLS vérifié). Payload privé par stdin/fichier contrôlé, jamais clé inline en argv ; modes/owner vérifiés. Ne pas écraser un fichier étranger, `_default` ou confiance d'autres registres. Détecter version/config_path containerd réellement embarqués ; inconnu ⇒ refus. Les mises à jour `certs.d` ne requièrent pas un restart containerd selon sa documentation, mais **activer config_path** doit être confirmé sur l'image Kind épinglée, pas inventé.
- État privé versionné par le helper : Docker context, IDs registre/réseaux/helper/volumes, pins, ownership et chemins PKI autorisés ; empreintes **publiques** de certificats possibles, pas empreintes de clés. Réutilisation seulement avec cet état + inspection concordante et bail de session, jamais nom/label/image seuls. Répertoire/volume préexistant inconnu ⇒ STOP, pas adoption automatique ni montage du disque ext4 déclaré mais non localisé.
- Création : registre JSONL `.tmp/docker-resources-<date>.log` immédiatement, IDs réels ; opaque ⇒ UNKNOWN/ask puis résolution vérifiée, pas identité inventée à partir du nom. Stockage Zot et caches existants à conserver (`safe_to_delete=no`), événements append-only. Réseau/ownership également dans l'état opérateur.
- Fin de tâche : stop gracieux réversible des runtimes possédés sans bail actif (Zot/helper ; aucun nouveau daemon BuildKit requis), inventaire avant/après ; données, certificats, images utiles et caches conservés. Pas de prune, wipe, `down -v`, rm forcé, WSL/disk/trust global. Un consumer réellement actif exige un bail/keepalive explicite, pas une fuite masquée.

## 6. Lots et scope d'implémentation

1. **A — Images locales, travail parent réutilisé** : `ops/deploy/image_catalog.py`, `build/{images.py,compile-artifacts.py}`, `Dockerfile.build`, profil `dev-image`, snapshots et ignores spécifiques. Finir/qualifier la fraîcheur Cargo et les exports, normaliser les recettes ext-authz/controller **sans perdre Cosign** ; inventaire package/bin/COPY au parent. Build/v1 et kind-load explicite peuvent constituer une première livraison bornée ; pas une livraison registry/cloud. `.dockerignore` utilisateur et source Rust/SDK intacts.
2. **B — Zot sans Kind, puis publication OCI réelle** : petit helper Python registre sous `ops/deploy/` (proposé `local_registry.py`, pas un nouveau backend de build), config Zot applicative distincte, extension PKI et pins Zot/Skopeo. Interfaces séparées `registry-up/status/stop` puis `publish --build-manifest … --output …` : build/v1 vérifié → export exact du daemon → helper Skopeo → vérification distante → release/v1. Pas de dépendance Kind/OpenBao, ni de prétendu digest avant push/lecture. Cette phase peut être livrée avant C, limite explicitée.
3. **C — Consommation OCI protégée** : `local_full_target.py` (opérations fermées registry-network/trust/pull), puis `local-full-images.py`, renderer/deploy et provenance pour release/v1. Aucun `docker exec` libre, aucune confiance globale ; si ce raccord n'est pas prêt, conserver A explicitement et marquer le pull registry **NOT RUN**, sans le simuler par kind-load. Un pull réel borné suffit, **pas d'E2E global**.
4. **D — Refresh ciblé, pas prérequis de B** : action `refresh` distincte du full deploy, seulement image/pull-policy des PodTemplates sélectionnés, UID/resourceVersion vérifiés, readiness ciblée et entrées recontrôlées. Ne pas quiescer/recréer OpenBao, réémettre son root, rejouer seed/Jobs/migrations, toucher SA/RBAC/NP/PKI/données pour du code. Changement migration/config bootstrap/schéma ⇒ arrêt et plan explicite. V1 bornée aux images sans migration automatique : ext-authz/sentinel/github/gitlab/controller ; deux reçus avec garde `refresh_inputs_id` identique (non-Rust + build scripts/migrations), même profil/transport et configuration runtime OCI. Les services à migration automatique sont refusés. Aucun branchement implicite sur `deploy_locked` ; exécution live encore NOT RUN.

Le dernier lot n'autorise ni rollout aveugle ni modification de l'autorité de cible. Fenêtre source changée pendant consommation ⇒ résultat STALE explicite ; pas de rollback/destruction automatique. Le lancement initial et la validation métier gardent leurs autorisations et interfaces propres. Les corrections Linux hôte doivent conserver **toutes** les étapes CNI/Calico/attentes du bootstrap, pas seulement son CLI Python.

## 8. Sources et points d'intégration

Constats de base : `.cargo/config.toml:1–3`, caches/target `Dockerfile.build`, ancien `local_full_image_provenance.py::verify` commit/diff et `deploy-local-full.py::verify_images → kind_load`, `p4/{zot.yaml,Dockerfile.zot}`.
