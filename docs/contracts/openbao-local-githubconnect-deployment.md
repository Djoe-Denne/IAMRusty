# Plan de raccord — OpenBao local / GitHubConnect

- **Statut : Proposed ; Réalité : Unimplemented pour ce raccord**, amendé le 2026-10-31 après accord humain limité au durcissement décrit ci-dessous. Aucun GO d'implémentation, de CI ou de runtime.
- Jalon : Ops local-full / portabilité, hors Apparatus P0–P6. Préparation publiée en `2f3505d` ; sources inchangées depuis `c3da69f3de244b3534f0215e746cc87441e93054`, service livré en `21caa8b`, SDK consommé `93b890f`.
- Canon lié : [0505](../adr/0505-startup-secrets-sdk-openbao.md), [contrat SDK](startup-secrets-openbao.md), [0606](../adr/0606-local-full-kind-isole.md), [séparation runtime/validation](ops-kind-runtime-validation-separation.md). Aucune ADR Accepted modifiée ou acceptation générale de ces ADR déduite.

**Choix humains acceptés, limitativement :** root généré privé réservé au bootstrap ; credential Lazaret limité à son besoin ; credential GitHubConnect déjà borné ; TLS et réseau restreint. Les mécanismes, durées et matérialisations proposés ci-dessous restent **Proposed**, notamment CAS, bundle de certificats, transfert seed et configuration IAM en RAM. L'accord ne ratifie ni zéro disque, ni KMS/HA/prod, ni une exception pour vrais credentials sous le root public actuel.

## 1. Cible et limites de livraison

Même chaîne logique local Windows, CI Linux et, ultérieurement, cloud Kubernetes : **source privée → seed OpenBao → identité workload → credential privé → lecture applicative au bootstrap**. Adaptateurs d'entrée différents, pas injection directe des valeurs OAuth/HMAC dans GitHubConnect. Pas d'ESO concurrent pour ces deux champs.

Le raccord proposé est une variante explicite `github-openbao` du déploiement local-full existant, indépendante des tests. GitHub reste optionnel et `oauth-proof` GitLab reste distinct ; le durcissement OpenBao/Lazaret commun décrit ici ne doit pas supprimer leurs parcours simulés. Aucun simulateur sous `ops/tests/` ne devient une dépendance du lancement nominal. L'image GitHubConnect actuelle et son mapping immuable sont des entrées fournies par le lot images du parent, pas un motif de reconstruction globale.

**Condition préalable aux vrais credentials :** le coffre actuel est DEV, volatile, avec un root connu également configuré dans Lazaret. Le durcissement accepté entre désormais dans ce même lot préparatoire, avant l'import de vrais credentials ; il ne justifie pas leur accès anticipé. La qualification commence avec des sentinelles synthétiques. Un parcours GitHub réel ne devient éligible qu'après réalisation/vérification du durcissement, choix d'une application de test à droits bornés et autorisation d'exécution distincte. Ce n'est ni une interdiction synthétique-only définitive, ni une parité cloud/prod.

## 2. Décisions proposées

### D0 — Root privé, fenêtre de bootstrap et epoch du coffre

- **Mécanisme proposé pour le local/CI volatile :** à chaque lancement du processus serveur DEV, son entrée bootstrap génère un unique bearer root aléatoire (CSPRNG, au moins 256 bits), sans valeur fixe, entrée utilisateur ou réutilisation d'un ancien root. Injection dans l'environnement privé du seul processus serveur (`VAULT_DEV_ROOT_TOKEN_ID` documenté en 2.6.x), jamais en argument, TOML/YAML, image, Secret Kubernetes, preuve ou artifact. L'autorité bootstrap co-localisée reçoit ce root en mémoire ; aucune application ni Job de seed GitHub ne le reçoit. Le root n'est pas un credential de workload.
- `-dev-no-store-token` empêche le token helper, **pas l'affichage** : la sortie DEV contenant root et clé d'unseal ne doit jamais être relayée dans les logs. Le lanceur doit supprimer cette sortie sensible avant tout logger/runtime, sans parser un banner pour retrouver le root ; diagnostics bornés et expurgés seulement. Vérifier aussi stderr et les chemins d'erreur avec des sentinelles. Les détails de ce lanceur restent à valider sur l'image épinglée ; pas de nouvelle infrastructure générale.
- Le bootstrap privilégié configure mounts, policies, auth Kubernetes, rôles distincts et fixtures locales nécessaires (dont Transit), puis **révoque le root et vérifie son refus** avant de déclarer cette étape terminée. Budget proposé : 240 s ; l'initial root DEV n'a pas une TTL de 240 s par magie. Échec/timeout/révocation non prouvée ⇒ aucune readiness positive ni import réel, arrêt du seul processus serveur possédé par ce lanceur. Pas de root conservé pour faciliter la prochaine commande.
- Une nouvelle instance mémoire est une nouvelle **epoch** : nouveau root, nouvelle configuration et nouveaux credentials. Aucun ancien root/bearer n'est réinjecté. Un restart du seul serveur doit rejouer ce bootstrap avant la remise en service ; les consommateurs ne réutilisent pas leurs credentials devenus invalides. Un coffre déjà initialisé de propriété inconnue n'est ni adopté ni réinitialisé ; perte de l'autorité au milieu du bootstrap ⇒ arrêt explicite, pas génération d'un second root sur l'état vivant.
- Après révocation, le seed GitHub utilise sa propre SA/role Kubernetes, TTL/max proposés ≤ 5 min, droits bornés aux deux documents et métadonnées nécessaires au contrôle CAS, sans `sys/*`, gestion de policy/role ou Transit. Le root ne reste donc pas ouvert pendant la fourniture de credentials externes. Les tokens émis par auth Kubernetes sont orphelins du root ; tout token émis directement au bootstrap doit l'être explicitement, sinon la révocation du parent les révoquerait aussi.

### D1 — Même TLS et réseau restreint pour tous les clients du nominal durci

- Ajouter au **même serveur OpenBao** un listener TLS natif `8443`. Endpoint commun SDK/agents/Lazaret/seed/P4 : `https://openbao.aiforall-local-full.svc.cluster.local:8443`. Dans le nominal durci, HTTP `8200` ne reste accessible qu'en loopback du Pod coffre pour son bootstrap co-localisé ; retirer son exposition Service/NetworkPolicy. Aucun bearer root ne traverse le réseau inter-Pods, aucun client applicatif ne garde un fallback HTTP. Ce loopback interne ne contourne pas les règles HTTPS du SDK.
- Réutiliser l'image serveur **2.6.2** épinglée dans `platform/dependencies.yaml`. Le serveur DEV accepte une configuration additionnelle ; les listeners s'ajoutent. Déclarer les adresses API/cluster sans collision avec le listener DEV et vérifier ce raccord sur cette image avant de le déclarer opérationnel. Aucun proxy TLS ou second coffre nécessaire à ce lot.
- Certificat OpenBao émis par la CA **mesh** existante, jamais la CA workload Lazaret : SAN DNS `openbao`, `openbao.aiforall-local-full.svc`, `openbao.aiforall-local-full.svc.cluster.local`, usage serveur. Leaf GitHubConnect distinct, SAN équivalents pour `github-connect`, pour IAM→Connect HTTPS. Pas de wildcard, SAN loopback ajouté pour contourner le contrat ou distribution de clé CA aux Pods supplémentaires.
- SDK : CA publique explicite, `allow_loopback_http=false`, nom/chaîne vérifiés, pas de redirection HA. Agents/CLI seed/P4 et Lazaret : même CA publique et vérification stricte, aucun `tls_skip_verify`. Pour Lazaret, qualifier le bundle public dans le trust store du backend TLS effectivement compilé : le builder actuel n'a pas d'option CA dédiée ; une variable d'environnement seule n'est pas une preuve. Si ce raccord Ops ne suffit pas, exposer avant GO le petit changement local de configuration/client CA nécessaire, sans migration SDK. Le healthcheck serveur n'atteste pas à lui seul la confiance TLS d'un client.

**Compatibilité à préserver :** mêmes chemins KV/Transit et sémantiques métier, rôles controller/admit-sign et clés existantes sur un coffre vivant ; seules adresse/trust et identité Lazaret changent comme explicité ici. Les étapes privilégiées du seed historique rejoignent le bootstrap privé : aucun ancien Job ne conserve le root connu. Un nouveau coffre volatile perd aussi son état Transit : ne pas présenter la recréation d'une fixture comme continuité de clé/signature. Pas de migration SDK ou Transit IAM ; 0506 reste une veille conditionnelle.

**Lazaret — snapshot borné, pas agent de refresh fictif :** retirer le root de `local-full/config/lazaret.toml` et de toute configuration livrée. Le setup clone actuellement `vault.token` dans `VaultHttpSecretResolver`, qui garde cette String pendant le processus. Proposition sans changement de cycle applicatif : init de Pod sous SA/role Lazaret distincts, login Kubernetes HTTPS, bearer transmis par configuration runtime privée en RAM ; policy KV = `read` sur **`secret/data/ops/token` seulement**, plus `lookup-self/read` pour contrôler ce credential. Pas de wildcard, autres documents, métadonnées/list, écriture, Transit, root ou policy default. Le seed local et les scénarios T6/T7/T12 emploient `ops/token` ; toute autre référence effectivement requise doit être inventoriée et autorisée précisément, pas couverte par `secret/*`.

Durée proposée local/CI : `token_ttl = token_max_ttl = token_explicit_max_ttl = 8 h`, non périodique, sans permission renew-self ni renouvellement annoncé. Déploiement/campagne d'une durée bornée inférieure à cette fenêtre avec marge (cible 15 min) ; sinon refus ou **nouveau login + rollout du Pod Lazaret** avant échéance. Le helper de préparation n'est pas une preuve de supervision continue. Restart du seul conteneur ≠ nouveau login : il relit la configuration privée restante, pas un bearer neuf garanti. Expiration/coffre redémarré ⇒ résolution KV refusée, jamais root/fallback ; nouveau Pod requis après rebootstrap du coffre, alors que l'agent GitHub peut se réauthentifier durablement. Une session locale sans borne ou un renouvellement transparent demanderait une évolution explicite de Lazaret, pas ce raccord Ops. La limite d'une heure de 0505 reste propre au credential GitHub, non transposée arbitrairement à ce consommateur runtime.

**Frontière de scope applicatif à approuver avant code :** `VaultConfig` dérive aujourd'hui `Debug` et `Serialize` avec le token. Pour introduire un vrai bearer privé sans cette exposition, proposer un delta de confidentialité local Lazaret (Debug expurgé, token omis de la sérialisation, désérialisation conservée), tests ciblés compris. Le contrat Ops ne donne pas à lui seul ce GO Rust. Toute évolution CA supplémentaire doit être nommée pareillement ; aucune lecture de token-file/relance d'auth, généralisation de port ou adoption SDK dissimulée.

### D2 — Extension explicite des certificats, jamais régénération implicite

Le générateur actuel refuse un ensemble incomplet et ne sait pas ajouter de leaves. Ne pas rendre les nouveaux fichiers obligatoires pour réutiliser un ancien répertoire valide.

- Prévoir une option explicite d'extension `openbao-github`, commune Python/OpenSSL et façades Windows/Linux. Valider d'abord intégralement l'ensemble existant, y compris l'éventuel superset GitLab ; absence/incohérence/expiration ⇒ refus, aucun remplacement.
- Publier les deux nouvelles paires dans un **nouveau bundle privé** `extensions/openbao-github/` du répertoire de certificats ; réutiliser `mesh/ca.{crt,key}` seulement pour signer. Staging privé puis publication exclusive du bundle complet ; bundle existant valide ⇒ réutilisation, partiel/invalide ⇒ refus.
- Aucun ancien fichier modifié, y compris les fichiers de série CA : nouveaux numéros de série sans écriture du compteur historique. Ni nouvelle racine ni renouvellement/rotation dans cette opération. Après extension et réinvocation, les octets des anciennes CA/leaves restent identiques.
- Le déployeur ne projette que le certificat/clé serveur nécessaires à chaque Pod et la CA **publique** aux clients. Ne pas étendre le sac de certificats mesh partagé avec les nouvelles clés privées.

### D3 — Deux documents KV v2, seed create-only et conflit explicite

Références nominales : `secret/github-connect/oauth`, champ `client_secret`, et `secret/github-connect/iam`, champ `hmac_secret`. Un document par finalité, aucun autre secret dans ces documents ; l'ACL KV porte sur le document, pas le champ.

- Local : lecture explicite d'un fichier privé ignoré, allowlist des seuls champs requis ; ne pas sourcer/exécuter tout `.env`. CI : entrées GitHub Actions Secrets explicitement transmises au seed, jamais au build. Client ID/URLs/redirects ne sont pas des secrets et restent dans la configuration déclarative.
- Le seed GitHub est une étape de bootstrap runtime, pas un test. Après D0 il utilise le credential de provisionnement non-root distinct, jamais le rôle GitHubConnect/Lazaret. Il ne réinitialise ni les mounts existants, ni Transit, ni les rôles controller/admit-sign. Un mount `secret` non-KV-v2 est un conflit, pas une conversion automatique.
- Pour chaque document : lecture/validation privée de l'état existant, création avec **CAS=0** seulement si réellement absent. Valeur existante identique ⇒ aucune nouvelle version ; différente ⇒ erreur expurgée demandant une rotation explicite. Supprimé/détruit/403/mount erroné/transport KO ne signifie pas « absent ». Comparaison en mémoire, sans valeurs ni empreintes de secrets dans les preuves.
- Valider les deux entrées avant la première écriture. Deux clés KV ne constituent pas une transaction : concurrence/CAS perdant/échec partiel ⇒ arrêt avant démarrage des applications, état conservé et reprise idempotente ; pas de rollback destructif.
- HMAC proposé : 64 caractères hexadécimaux, issus d'une source aléatoire sûre, sans whitespace ; mêmes octets côté IAM et Connect, sans hash/base64/canonicalisation nouvelle. Le seed ne remplace pas un HMAC existant pour « réparer » une discordance.
- Si le transfert au Job utilise un Secret Kubernetes temporaire : création exclusive task-owned, montage seed seulement, aucun rendu contenant ses données sur disque hôte, retrait par UID après seed selon mandat/ownership. **Cela matérialise une copie dans le stockage Kubernetes**, même si temporaire ; ni base64 ni suppression ne prouvent l'effacement d'etcd/backups. Une exigence zéro matérialisation etcd nécessiterait un transport de seed distinct avant coding.

### D4 — Agent Kubernetes durable pour le token-file GitHubConnect

- SA dédiée `github-connect`, rôle lié exactement à cette SA et au namespace local-full, audience dédiée `openbao-github-connect`. JWT projeté à courte durée, renouvelé par Kubernetes, monté dans l'agent seulement, sans `subPath` ; pas de JWT statique copié dans OpenBao. Aucun droit Kubernetes de lecture de Secret ni TokenReview accordé au connecteur.
- Réutiliser le reviewer **local d'OpenBao** et son RBAC `tokenreviews/create` existants ; CA Kubernetes vérifiée, `disable_local_ca_jwt=false`. Ne pas remplacer ce mécanisme partagé ni employer le JWT client comme reviewer. Le rôle GitHub a son audience explicite, sans modifier celles des rôles P4.
- OpenBao Agent même version/digest que le serveur, méthode auto-auth `kubernetes`, **`exit_after_auth=false`**. Préférer une sidecar native restartable (`initContainers`, `restartPolicy: Always`) : le Kind épinglé est Kubernetes 1.32.2, fonctionnalité activée par défaut depuis 1.29 ; vérifier la capacité effective, pas d'upgrade cluster implicite.
- Sink **plain token** `/run/github-openbao/token`, volume `emptyDir.medium: Memory` borné (1 MiB suffit), écriture agent seule, lecture seule dans Connect, UID/GID explicites compatibles avec l'image effective ; mode `0600` même UID ou `0640` groupe dédié. Montage du répertoire, jamais `subPath` du token. Pas de wrapping, chiffrement de sink, proxy/cache Agent ou rendu de secrets OAuth dans Connect.
- Token `service`, TTL initiale proposée **15 min**, `token_max_ttl` et **`token_explicit_max_ttl` ≤ 1 h**, aucun token périodique, `token_num_uses=0`, `token_no_default_policy=true`. Policy exhaustive : `read` sur `auth/token/lookup-self` et les deux chemins `secret/data/github-connect/{oauth,iam}` ; ni list, écriture, Transit, `sys/*`, enfant ni root.
- **Pas de droit renew-self ajouté implicitement.** Avec cette policy de 0505, un renouvellement refusé conduit l'agent à se réauthentifier, comme documenté. Qualifier cette voie et son backoff ; ne pas la remplacer par un token fixe ni élargir la policy pour cacher un échec. Une stratégie renouvelable avec droits supplémentaires exigerait un amendement explicite du contrat.
- La startupProbe de l'agent vérifie, sans sortie sensible, qu'un sink utilisable existe et que lookup-self respecte le contrat, avec une marge de TTL supérieure au budget SDK (cible ≥ 30 s). Cela ordonne le premier lancement du Pod ; **cela ne rejoue pas les init containers au seul restart de Connect**. La garantie de restart tardif repose sur l'agent toujours actif, ses re-logins et la rotation du fichier.
- En cas de course à l'expiration ou de coffre indisponible au restart : le SDK refuse le boot sous ses bornes, puis le superviseur Kubernetes peut retenter. Pas de fallback ni garantie zéro restart transitoire. Ne pas étendre la deadline SDK **20 s** pour attendre le bootstrap. Après boot réussi, une expiration du token ne révoque pas le snapshot applicatif ; aucune readiness métier couplée en continu au coffre.

### D5 — HMAC IAM identique, sans migration applicative IAM

Proposition RAM-only pour **la nouvelle valeur HMAC** : init de distribution OpenBao dans le Pod IAM, identité SA/role IAM distincte, accès au seul document HMAC, qui rend une fois le fichier de configuration runtime privé dans un `emptyDir Memory`. IAM conserve son loader existant et ne reçoit ni root ni credential du connecteur. Le template versionné contient une référence, pas la valeur ; conserver les autres paramètres IAM et les parcours GitLab.

Utiliser Agent avec sortie après acquisition/rendu, erreurs de secret/champ obligatoires et validation du fichier avant de laisser démarrer IAM ; `exit_after_auth` seul n'est pas un oracle de rendu. Permissions privées, aucun backup/template output hors RAM, aucun hook exécutant un reload. Le snapshot HMAC est une valeur KV statique, **pas un bearer expirant** : un init one-shot est acceptable pour cette copie IAM, contrairement au token-file Connect. La valeur reste en RAM après restart du seul conteneur IAM ; une future rotation exige le rollout coordonné des Pods IAM/Connect.

Cette proposition ne met aucun HMAC dans un TOML **versionné**, ConfigMap, image, log ou artifact. Elle implique néanmoins un TOML **runtime privé en RAM**, puisque IAM consomme aujourd'hui une valeur configurée. Si l'interdit « aucune configuration » inclut ce fichier runtime, **STOP et arbitrage humain** : ce serait un changement de consommation IAM, pas un raccord Ops à dissimuler. Pas d'ESO supplémentaire ni extraction SDK imposée.

## 3. Ordre, réseau et fichiers du prochain lot

Séquence d'implémentation proposée, seulement après GO :

1. Confirmer les détails encore Proposed (fenêtre Lazaret, delta Rust borné, matérialisations seed/IAM/Lazaret), puis consommer le mapping immuable d'image GitHub du parent contenant `21caa8b` + SDK `93b890f`. Si un delta Lazaret est approuvé, seule son image supplémentaire doit être livrée/attestée ; pas de vieux tag présenté comme preuve ni reconstruction globale.
2. Ajouter l'extension certificats, le bootstrap root privé et la variante `github-openbao/` ; rendus offline sans entrée secrète, parcours par défaut/GitLab conservés hors durcissement commun D0/D1. Valider le transport de tous les consommateurs concernés, pas uniquement GitHub.
3. Après autorisation runtime distincte et bail vérifié : fondations/CA/RBAC → serveur/bootstrap privé → mounts/auth/policies/rôles/fixtures → root révoqué et vérifié → OpenBao HTTPS prêt → seed GitHub non-root/deux documents → fin du seed → init Lazaret/IAM et agent Connect → boot des applications. D'abord des sentinelles synthétiques et preuve du durcissement ; vrais credentials seulement après gate et autorisation distincte. Attentes opérateur bornées hors deadline SDK, erreurs non-zéro et expurgées. Les ressources privées ne sont ni adoptées ni écrasées à la réinvocation.
4. Ajouter NP : Lazaret/init, GitHubConnect, IAM-init, seed GitHub et clients Transit autorisés → OpenBao **8443** avec ingress réciproque ; DNS nécessaire ; IAM → Connect **8443** et ingress correspondant. Retirer les autorisations inter-Pods **8200**, sans egress général ajouté. TokenReview reste OpenBao→API sur les destinations déjà bornées. Pas d'accès API/DB accordé au nouveau connecteur par convenance. NetworkPolicy isole les Pods, pas les conteneurs d'un Pod. Egress GitHub externe réel à traiter explicitement avant ce parcours, pas un `0.0.0.0/0` implicite pour le smoke coffre.
5. Qualifier puis documenter ; déploiement utilisable sans runner E2E, validation appelée séparément. L'absence de fournisseur OAuth live n'empêche pas de prouver ce raccord de bootstrap ; elle empêche de revendiquer une connexion utilisateur GitHub réelle.

Périmètre autorisable : `ops/scripts/prepare-local-full-certs.{py,ps1,sh}`, nouveau bundle de sorties privées hors Git ; `ops/deploy/apps/overlays/local-full/github-openbao/` (proposé), helpers de bootstrap/seed/distribution sous `local-full/helpers/`, patch ciblé `platform/{dependencies,bootstrap,policies,kustomization}.yaml`, `config/lazaret.toml` et raccords TLS `apparatus/` ; `ops/deploy/{render-local-full.py,deploy-local-full.py}` pour sélection, ordre, références et hashes **non secrets**. Raccords documentation opérateur et tests source existants proportionnés. Exception applicative seulement après GO explicite : confidentialité `services/Lazaret/configuration/src/lib.rs` et tests ciblés ; éventuel support CA local `configuration/infra/setup` si le préflight prouve sa nécessité. Le lot images/mapping reste au parent ; ne pas réécrire ses fichiers sans coordination.

**Gap Linux hôte explicite :** `deploy-local-full.py:701–706` appelle actuellement `powershell.exe bootstrap-local-full.ps1` (preuve parent réutilisée). Le contrat Kubernetes/seed/Agent est portable ; l'exécution du pipeline complet sous Linux n'est pas prouvée. Selon la source vérifiée par le parent, `ops/deploy/common.ps1::Initialize-LocalKind:95–123` appelle d'abord `local_full_target.py bootstrap`, puis contrôle CNI/CIDR, installe Calico **3.29.7** si absent, fixe le pool **10.244.0.0/16** et `FELIX_IGNORELOOSERPF`, et attend Calico/CoreDNS/nœuds Ready. Le CLI Python existant (`:1522`, `:1583–1591`) ne représente donc que le premier maillon : remplacer simplement le wrapper par ce CLI supprimerait des étapes indispensables. Le raccord portable doit conserver/porter cette séquence complète derrière la même autorité de cible, avec parité des paramètres cluster/config/bail/after-final-it et des chemins privés POSIX ; son changement minimal reste à déterminer et à vérifier, pas déjà prouvé. Préserver leasev2, endpoint/mapping avant tout API GET, UID avant mutations, refus foreign/legacy, verrous et inventaires. Ni suppression simple du wrapper, ni application YAML directe depuis un nouveau shell Linux contournant cette autorité. **Windows dev n'interdit pas GitHub Actions Linux** ; le GO de cette préparation n'autorise ni l'un ni l'autre runtime.

Hors scope : code Rust autre que les exceptions Lazaret à autoriser ci-dessus, SDK, migrations DB, GitHub App installation/API, client cloud, ESO, transit/IAM signing, migration Lazaret vers SDK ou refresh applicatif, KMS/HSM/unseal/HA/durabilité du coffre, rotation métier, nouveau framework de tests, reconstruction générale ou campagne k6 globale.

**Frontière prod :** conserver produit et étapes de pipeline communs, pas les modes de confiance identiques par décret. La simulation locale DEV/volatile reste permise ; aucune valeur root connue ou root applicatif dans le nominal durci. Prévoir des gardes non contournables par un simple flag de transport refusant mode DEV/stockage mémoire et policy root des credentials applicatifs pour une cible prod ; `lookup-self` GitHub reste inchangé, les autres contrôles doivent être placés aux frontières de provisionnement/consommation pertinentes et prouvés. Auth, stockage, initialisation/reprise et disponibilité prod restent des paramètres/décisions futurs explicites, pas un adaptateur cloud livré maintenant. Aucune garantie zéro copie disque/swap/etcd déduite de cet accord.

## 4. Vérification proportionnée à exécuter ultérieurement

- **Offline Windows + Linux :** syntaxe/rendu de la variante, références/volumes/SA/NP et absence de valeurs ; contrôles source pertinents de `ops/tests/test_oauth_browser_alignment_source.py`, `test_envoy_upstream_server_identity.py`, `test_local_full_target.py`, limités aux raccords modifiés. Pas de batterie nouvelle ni tout-Cargo. Certificats : un smoke réel par OS, extension d'un ancien ensemble valide et seconde invocation, comparaison privée des anciens octets et vérification chaînes/SAN ; ajout partiel refusé sans écrasement.
- **Runtime Windows pilotant les Pods Linux, puis CI Linux autorisée :** même scénario court, même image/config : TLS accepté avec bonne CA/DNS, mauvaise CA/SAN refusés ; login bon SA/audience et refus d'une identité étrangère ; bootstrap Connect = lookup-self nonroot/TTL puis **les deux** lectures KV, champ/secret manquant ⇒ aucun Connect prêt, aucun fallback. Démontrer IAM↔Connect avec HMAC concordant et refus d'une autre clé, sans OAuth vendor réel. Traces de contrôle expurgées, pas de dump KV/token ni d'audit en mode brut.
- **Seed :** deux invocations identiques, versions inchangées ; entrée divergente et clé supprimée ⇒ refus, pas écriture réparatrice. Les preuves publiques ne contiennent que verdicts/compteurs/versions non sensibles, pas hash de valeurs privées.
- **Durcissement préalable, avec sentinelles seulement :** ni root fixé dans les sources/rendus ni bearer dans args/logs/token helper/artifacts ; root généré distinct à chaque epoch, refus après révocation avant seed réel ; panne/timeout bootstrap sans readiness ni import. Lazaret lit `secret/data/ops/token`, mais reçoit 403 sur les deux documents GitHub, Transit, écriture et administration ; GitHub n'obtient pas le besoin Lazaret. Bonne CA/DNS exigés aussi pour Lazaret/P4. Expurgation Debug/sérialisation du credential Lazaret vérifiée si ce delta est autorisé.
- **Restart décisif :** garder Pod/agent et volume, dépasser la durée de vie du premier bearer, observer plusieurs authentifications puis redémarrer **seulement Connect**. Constater nouveau boot/trois requêtes SDK, agent/Pod non recréés, TTL valide, HMAC effectif.
