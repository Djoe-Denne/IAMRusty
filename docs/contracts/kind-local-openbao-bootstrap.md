# Contrat — bootstrap natif d'un coffre OpenBao neuf, existant préservé

Version 1.2 amendée — 2026-11-10, photographie courante au §7, sans nouveau choix structurel. [ADR-0611](../adr/0611-openbao-neuf-raft-pvc-sans-conversion-du-coffre-existant.md) **Proposed / Partial** ; complément du [lanceur v1.4, §5.2/5.5](kind-local-native-launcher.md). Chart/primitives/bootstrap **raccordés au lanceur en code** ; serveur/API OpenBao/init/unseal/PVC/reset/Kind réels **NOT RUN**. **Choix humain acquis « 1/1 local (Recommended) » : Shamir 1 part / seuil 1 dans un fichier privé protégé, coffre neuf du lab mono-opérateur uniquement.** Conservation de l'existant et inputs explicites inchangés, sans Accept global de l'ADR.

## 1. Branche existante et coffre neuf

- **Existant HTTPS compatible :** ne pas changer Deployment/Pod, image, Secrets/TLS, ConfigMaps/scripts, Service ou PVC qui le servent ; aucun rollout, conversion DEV→persistant, reseed ou remplacement de token au rebuild. Utiliser les fichiers produit complets valides fournis par l'opérateur. Un coffre volatil conservé n'est pas devenu durable : perte du Pod/processus = données perdues. Incompatibilité TLS/configuration ou coffre ancien inaccessible = diagnostic explicite, pas remplacement silencieux.
- **Ressource de lancement absente :** créer les éléments manquants du serveur non-DEV 2.6.2, PVC RWO `openbao-data` monté `/openbao/data`, backend natif Raft et `node_id` stable `openbao-local`. Une réplique, stratégie sans chevauchement de writers (Deployment `Recreate` suffit). Pas de StatefulSet/HA/join manager requis. API HTTPS `https://openbao.aiforall-local-full.svc.cluster.local:8443`, `cluster_addr` cohérent avec le listener cluster déclaré ; CA/SAN existants, clés RO. Ne pas toucher aux sources PKI ni en produire une seconde.
- Un PVC préexistant reste le même coffre : lancer son serveur n'autorise ni réinitialisation ni suppression du volume. `bao status -format=json` fournit `initialized`/`sealed` ; exit 0 = unsealed, 2 = sealed, 1 = erreur, **pas absent**. Évaluer le JSON natif, pas une sentinelle maison. Transport/permissions/JSON invalides = échec. Attendre serveur joignable avant status, pas Pod Ready/unsealed ; liveness ne redémarre pas un serveur parce qu'il attend init/unseal, readiness normale continue de refléter l'état non prêt.
- **Initialisé + unsealed :** ne pas appeler init ou rejouer le bootstrap au lancement. **Initialisé + sealed :** uniquement unseal explicitement demandé et matériau désigné, jamais init. **Non initialisé :** uniquement l'initialisation explicite avec sortie neuve ci-dessous. Pas de boucle de « réparation » ou d'initialisation suite à un timeout.
- Exclure réellement les objets existants des mutations, **y compris suppressions par Helm** : désactiver leur rendu dans un ancien release puis faire son upgrade/uninstall peut les supprimer. Ne pas upgrader globalement le release historique en supposant qu'un `enabled=false` les préserve ; le parcours calcul et la création des données manquantes doivent laisser ces objets hors de leurs mutations. Aucun nouveau gestionnaire d'ownership demandé.

## 2. Interfaces publiques et privées du petit lanceur

Variables de chemins uniquement, aucun secret en argument ; le répertoire privé est celui de `KIND_LOCAL_PRIVATE_DIR`, hors Git/contexte Build/logs. Les fichiers complets de l'opérateur sont considérés valides : pas de détection d'admin malveillant, protocole d'empreintes ou preuve d'origine.

**Réalité du raccord :** `just kind-local` / `ops/deploy/kind-local.ps1` consomment maintenant les inputs décrits au [guide opérateur](../../ops/deploy/kind-minimal.md), notamment `KIND_LOCAL_PRIVATE_DIR`, `KIND_LOCAL_BAO` (CLI2.6.2), CA, sorties privées et `KIND_LOCAL_INITIALIZE_EMPTY=1` pour le neuf. Le module garde ses paramètres explicites : `Connection` (`Executable`, `Address`, `CaFile`, `ServerName`), `OutputFile`/`InputFile`, puis `-InitFile` **ou** `-AdminTokenFile` pour un bootstrap explicite. Raccord présent, **aucune invocation live qualifiée** ; une reprise administrative reste distincte du rebuild normal.

- `KIND_LOCAL_OPENBAO_CA_FILE` : CA PEM hôte existante. CLI officiel **2.6.2** au poste comme prérequis explicite ; `BAO_ADDR` vers HTTPS et `BAO_CACERT` vers cette CA. Si port-forward natif nécessaire, le faire vers le **Pod running même non Ready**, sur boucle locale ; `BAO_TLS_SERVER_NAME=openbao.aiforall-local-full.svc.cluster.local` conserve la vérification SAN malgré l'adresse locale. Endpoint et port de forward sont paramètres publics ; aucune exposition externe ou proxy ajouté. Environnement enfant explicite, pas de token ambient hérité.
- `KIND_LOCAL_OPENBAO_INIT_OUT` : **nouveau chemin complet choisi**, obligatoire avant toute init. JSON brut du `operator init -format=json` 2.6.2, notamment `unseal_keys_b64`/`unseal_keys_hex`, seuil/parts et **`root_token`** (pas supposer le champ API `initial_root_token`). Pas de fichier « latest », glob, découverte d'anciennes clés ou valeur recyclée par défaut.
- `KIND_LOCAL_OPENBAO_UNSEAL_INPUT` : fichier init explicitement fourni pour **ce coffre**, contenant l'unique part du coffre neuf 1/1. Première init : sa sortie est l'input de cette invocation ; aux invocations suivantes, aucun ancien chemin choisi automatiquement. Un coffre existant unsealed n'en a pas besoin ; son ancien matériau et son seuil ne sont pas modifiés par ce choix. Aucun fichier de part ni root injecté dans un Secret applicatif ou monté dans le serveur en mode Shamir.
- `KIND_LOCAL_OPENBAO_ADMIN_TOKEN_FILE` : token brut privé optionnel pour une **opération bootstrap explicitement reprise** sur un coffre déjà initialisé ; inutile au rebuild normal et distinct de l'input unseal. Première init : root du JSON privé lu en mémoire pour cette seule opération. Module livré : `-AdminTokenFile` lu explicitement puis token chargé seulement dans l'environnement enfant `BAO_TOKEN`, jamais `bao login <token>`, `kubectl --from-literal` ou contenu interpolé dans une commande. Environnement BAO/VAULT hérité expurgé, `BAO_CONFIG_PATH` et `BAO_TOKEN_PATH` forcés à `NUL` : aucun token/config/helper ambient. La variante native token-path évoquée au cadrage n'est pas le raccord actuellement implémenté.
- `KIND_LOCAL_OPENBAO_PRODUCT_OUT_DIR` : répertoire de sorties privées **neuf et explicitement choisi** si le bootstrap émet des tokens métier. Réponses JSON natives de création de token par consommateur, sans écrasement ; pas un état du déployeur. Les configs complètes IAM/Lazaret/connecteurs restent les inputs produit du contrat principal. `VaultConfig.token` de Lazaret est une chaîne : l'opérateur y reporte son token dans le fichier complet avant lancement, pas un faux chemin token-file ni un composeur automatique nouveau.

## 3. Init/unseal et garde — choix humain 1/1 local

1. Vérifier les chemins/ACL privés avec primitives OS, puis ouvrir la sortie init **en création exclusive** (Windows `FileMode.CreateNew`, répertoire à ACL privée avant le premier octet ; POSIX équivalent 0600/umask 077). Fichier déjà présent = refus **avant** d'appeler init, même s'il est vide. Ne pas utiliser `>` susceptible d'écraser un ancien bundle, ni sortir les secrets dans la console pour les recopier. Le correctif ACL PKI Windows est désormais vérifié indépendamment par la racine ; aucune modification PKI ou réparation globale dans ce raccord.
2. Pour le coffre neuf du lab mono-opérateur : `bao operator init -format=json -key-shares=1 -key-threshold=1`, stdout directement capturé dans ce fichier privé protégé, stderr expurgé, aucune capture dans un log/transcript/Helm/ConfigMap. La confirmation humaine est acquise, pas de nouvelle barrière de garde à demander. Ce fichier est du **matériel de déverrouillage/récupération d'accès**, pas une sauvegarde des valeurs, clés Transit ou données du backend. Sa part unique suffit à unseal ; il contient aussi le root initial avant révocation. Compromis mono-opérateur explicitement choisi, pas de séparation entre détenteurs ou de qualification production.
3. Relire le JSON privé sans le journaliser ; sélectionner **une seule représentation de l'unique part** (base64 ou hex, pas les deux comme deux parts), transmettre en mémoire le corps JSON `{ "key": <part> }` sur stdin de **un appel** `bao write sys/unseal -`, sortie supprimée ou limitée au statut public. C'est le CLI natif vers `/v1/sys/unseal`, pas un client HTTP ou protocole de reprise maison. **Ne pas piper vers `operator unseal`** : son `password.Read(os.Stdin)` attend un terminal au pin 2.6.2 ; la saisie cachée interactive sans argument demeure possible. Ne jamais rekey/abaisser le seuil d'un coffre existant pour lui appliquer ce choix neuf.
4. **Aucun auto-unseal statique/KMS sélectionné** : pas de stanza `seal "static"`, pas de part/clé suffisante montée implicitement dans le serveur, pas de migration de seal ou généralisation à d'autres environnements. Le serveur reste Shamir ; le poste n'utilise que le chemin privé explicitement fourni. Les fichiers/CA/credentials hôtes antérieurs restent intacts, pas de latest, epoch ou découverte d'anciennes clés.

Un appel init dont la réponse s'est perdue peut avoir initialisé le backend sans bundle exploitable. Conserver fichier partiel et erreur, ne pas rappeler init, effacer le PVC ou chercher d'autres clés automatiquement ; état et intervention opérateur explicites. Après un bootstrap partiellement échoué, le root peut ne pas être révoqué : signaler cette condition sans afficher sa valeur, conserver les fichiers privés et demander une action explicite. Aucun journal de reprise ni rollback.

## 4. Bootstrap produit, natif et à la demande

- Serveur neuf déverrouillé : déclarations publiques existantes de `files/openbao/bootstrap.json`, plus mount **KV v2 `secret` explicitement créé** (DEV le fournissait implicitement), Transit, auth Kubernetes, clés/policies/rôles nécessaires aux seuls consommateurs actifs. Refuser les erreurs au lieu de les interpréter comme absence ; idempotence = vérifier présence/config compatible et créer le manquant, pas écraser clés/valeurs existantes. Une incompatibilité demande une modification explicite. Seeds privés par fichiers/stdin et CAS0 natif : conflit/403/réseau ne signifie pas « absent ». Pas de transaction multi-documents promise.
- CLI uniquement, `bao write <path> -` pour les corps JSON privés, `@<fichier>` quand la commande native le permet, sorties de tokens dirigées vers fichiers privés exclusifs. `BAO_DISABLE_REDIRECTS=true` dans les commandes CLI, TLS/CA/SAN vérifiés, aucun skip-verify ou listener HTTP caché. Ne pas annoncer l'auto-auth Agent 2.6.2 corrigée : `OPS-OPENBAO-262-REDIRECTS` demeure distincte.
- Pour un consommateur utilisant un token statique de config, créer un token natif **sans root/default policy**, limité aux chemins/politiques existants nécessaires ; `-orphan` s'il est émis par le root à révoquer. Durée bornée conforme au consommateur déclaré, pas de TTL infini ou de prolongation implicite pour faire tenir le lancement ; expiration = nouveau credential fourni explicitement. Les consommateurs qui possèdent déjà une authentification native continuent leur parcours produit, pas un remplacement général par des tokens statiques.
- Sauver les sorties de tokens ; après bootstrap et écriture privée réussis, **révoquer le root avant la remise à l'opérateur**, sans attendre qu'il prépare ses fichiers produit : `bao token revoke -self`, résultat vérifié et environnement secret libéré. Le `root_token` présent dans le bundle historique est alors **révoqué**, pas un admin credential réutilisable. Pas de révocation automatique d'un token admin fourni par l'opérateur pour un coffre existant. L'unseal ultérieur utilise les parts, pas le root. Un admin ultérieur relève des procédures natives/opérateur, hors renouvellement automatique du lanceur.
- L'opérateur complète ensuite ses fichiers produit, montés en Secrets standards RO. **Le premier passage Bao neuf du lanceur raccordé s'arrête avant les applications** : reporter le token dans la chaîne `VaultConfig.token` du TOML Lazaret complet et relancer explicitement après préparation des fichiers/annexes. Cette étape humaine non supprimée remplace l'ancienne composition Ops ; aucun nouveau renderer ou Agent bogué.

## 5. Reset et limites de qualification

`reset-data` ne supprime ni CA/clés TLS ni anciens bundles/tokens/configs hôtes. Pour le coffre neuf, exiger **avant init** un `INIT_OUT` neuf et, si émission de tokens, un `PRODUCT_OUT_DIR` neuf ; vérifier cette précondition de chemins avant destruction du lab dans le parcours reset. Les anciens fichiers restent intacts mais le lanceur ne les copie ni ne les sélectionne pour ce nouveau bootstrap. Les nouveaux tokens du coffre neuf doivent être reportés dans les fichiers complets par l'opérateur avant lancement produit : conserver un fichier d'un ancien coffre n'autorise pas à annoncer l'accès fonctionnel. Aucune recherche de clés anciennes, réutilisation forcée du root, overwrite ou identifiant d'epoch pour résoudre cela.

Conservation du backend = PVC/nœuds conservés et mêmes parts d'unseal ; elle ne couvre ni suppression de nœud, ni sauvegarde/restauration, ni perte du matériau privé. Le passage d'un DEV ancien à cette cible exige une disposition/migration séparément autorisée : aucun export ou backup automatique ajouté.

Validation : reprendre le plan QA existant, sans nouvelle campagne imposée ici. Les points à ne pas prétendre acquis contre un serveur réel restent : absence de mutation de l'existant par le rendu/upgrade, init vers sortie exclusive, unseal sans argv/log, révocation du root sans révoquer les tokens produit, non-réinitialisation d'un PVC existant et credentials neufs après reset. **Les tests parent du §6 sont réutilisés sans réexécution par l'architecte ; aucune API/runtime Bao réelle, persistance après restart ou qualification Kind acquise par ce raccord documentaire.** Les faits Redis TLS Windows et Build offline antérieurs restent inchangés. Sources exactes et limites : [ADR-0611](../adr/0611-openbao-neuf-raft-pvc-sans-conversion-du-coffre-existant.md).
