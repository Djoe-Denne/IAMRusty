## 1. Interfaces fixées pour les lots Build puis Lancement

```text
just kind-local                         # keep-data par défaut ; build + import + lancement
just kind-local reset-data              # même parcours, destruction explicite du seul lab
just kind-local-build <build-tag>        # toutes les images applicatives, pas de cluster
just kind-local-import <build-tag>       # import natif des sorties dans le lab nommé
```

- Entrée native courte dans `justfile`/fichier just dédié, avec seulement un adaptateur PowerShell standard si nécessaire pour la portabilité Windows. Pas de second CLI Python, parser d'argv d'autorité, moteur de graphe, états d'opération ou traduction de l'ancien framework.
- Cible fixe : cluster `aiforall-local-full`, contexte `kind-aiforall-local-full` ; Kind YAML versionné existant et Calico épinglé. `kind get clusters` suffit au branchement créer/réutiliser ; pas d'audit de daemon, endpoint, IDs ou UID de cluster. Toute commande `kubectl` reçoit le contexte explicitement, pas un contexte courant modifié globalement.
- Un `build-tag` public commun est fourni aux sous-recettes ; l'entrée complète le produit une fois avec les outils natifs si non fourni. C'est un tag d'image, **pas** un nonce/bail/reçu. Pas de secret dans les arguments. Le seul input privé de lancement est un répertoire de fichiers complets, par exemple via `KIND_LOCAL_PRIVATE_DIR`, hors Git/contexte de build. Les overrides publics restent des fichiers de valeurs Helm.
- Le profil nominal `kind-minimal` réutilise le chart existant ; une réplique par workload de calcul. Services plateforme, Lazaret, workers et dépendances consommées sont déclarés. Un connecteur réel peut être activé explicitement par les valeurs et ses fichiers privés ; aucun simulateur OAuth, gold path, ancien flag de preuve ou protocole de compatibilité n'est requis. Les profils de tests ne sont pas annoncés migrés s'ils restent hors de cette entrée.

## 2. Build — la racine peut commencer ce lot indépendamment du lancement

**Entrée :** checkout courant complet, SDK local compris, fichiers non committés pertinents inclus ; inventaire `ops/deploy/build/targets.json` et Dockerfiles. **Sortie :** images Linux chargées dans Docker, références déterministes `<repository-déclaré>:<build-tag>` pour chaque cible du groupe natif `kind-local-images`.

- Créer ce groupe Bake depuis l'inventaire unique, avec les onze cibles applicatives actuelles de `workspace` (sans sortie supplémentaire monolithe). Aucun catalogue Python ou liste parallèle dans le lanceur. Les images tierces restent épinglées ; elles ne sont pas réputées recompilées depuis les sources de leurs vendors. Le Zot P4, si consommé, est une dépendance distincte du registre d'images applicatives retiré.
- Exemple de primitive : `docker buildx bake --no-cache --load -f ops/deploy/build/targets.json -f ops/deploy/build/docker-bake.hcl kind-local-images`, avec la variable native `BUILD_TAG` fixée pour cette invocation. Les cibles finales restent canoniques ; pas de clones par groupe ni de writers multiples d'un même tag. Le producteur partagé peut rester un contexte BuildKit lié/cacheonly : **aucune obligation d'exporter ou attester son image intermédiaire** comme dans l'ancien wrapper.
- Remplacer l'appel à `compile-artifacts.py` par Cargo natif dans une recette Dockerfile multi-stage. Sélection explicite des packages/binaires/features depuis les déclarations ; union nécessaire incluant `apparatus-operator/controller`. `cargo build --locked --profile dev-image --target-dir <target-linux-neuf>` ; conserver les 24 jobs configurés, pas d'override contradictoire. Pas de parsing du flux `compiler-artifact`, de réparation des mtimes ou de découverte du cache Cargo.
- **Target neuf obligatoire** : répertoire vide dans le stage de compilation réexécuté, hors checkout copié, sans mount de cache target. `--no-cache` seul sur le Dockerfile actuel ne suffit pas. Les caches registry/git de téléchargement peuvent rester ; pas de prune, suppression du builder ou cache d'un autre travail. Un seul Cargo à la fois.
- Export natif des binaires déclarés aux chemins attendus par les Dockerfiles consommateurs, notamment `/app/target/release/<binaire>` : `COPY`/installation standard depuis le target/profil connu, sans emporter tout le cache/deps. Les cinq images métier gardent `/app/migration` et leur binaire service. Les recettes OAuth/Connect ne doivent plus imposer un faux reçu `image-inputs.json` ou des SHA attestées pour ce parcours local ; pas de fabrication de provenance pour satisfaire une ancienne garde.
- Adapter `.dockerignore` : sources locales/SDK présents, secrets et `.env*`, `.tmp`, `.worktrees`, répertoires privés, targets Windows, archives et logs exclus ; ne pas exclure un fichier de recette/asset réellement consommé. Pas de `git archive HEAD`, snapshot privé, comparaison finale de dérive, manifest de promotion ou protocole A→B→A. Le lancement suppose un checkout non modifié pendant le build, sans machine de surveillance.
- `kind-local-import` consomme les tags du **plan natif Bake** pour le même groupe/tag, via un lecteur JSON standard (PowerShell `ConvertFrom-Json` ou outil natif équivalent), puis `kind load docker-image ... --name aiforall-local-full`. Pas de mapping attesté Python ou registre Zot/Skopeo. Les Pods utilisent ces références et `imagePullPolicy: Never` pour les images applicatives importées ; les tiers ont leur policy explicite. Un import en échec interdit l'étape déploiement.

## 3. Calcul, données et reset-data

Les catégories sont des déclarations du profil, pas une heuristique par nom dans un programme :

- **Calcul remplaçable** : services métier/connecteurs activés, workers, ext-authz/Envoy, operator si activé. Mettre à zéro/retirer leurs seuls Deployments/Pods et attendre la fin des writers avant les nouvelles migrations ; ne pas supprimer leurs PVC de données.
- **Données conservées** : nœuds Kind, PVC PostgreSQL/Redis/Zot P4/admission-store et dépendances porteuses d'état ; OpenFGA conserve store/modèle/tuples dans PostgreSQL. Les références de Secret, ConfigMaps d'initialisation et données publiques consommées restent stables. Les appels natifs d'existence/initialisation sont permis ; pas de preuve d'ownership ou de reprise maison.
- **Volatil explicitement limité** : OpenBao DEV existant et LocalStack sans backend durable démontré. Les garder en fonctionnement lors d'un rebuild calcul, sans appliquer un changement de tag/hash global qui les ferait rouler. Aucun PVC fictif, manager d'epoch ou promesse de survie à la perte de Pod/nœud. OpenBao **neuf seulement** reçoit le stockage du §5.2, pas une conversion du coffre DEV. Une configuration de données nécessitant un rollout, notamment TLS lors de la transition initiale, est un changement visible à traiter au lot Lancement ; ne pas le cacher dans le rebuild normal.

Par défaut, ne supprimer **ni cluster/nœuds, namespace, PV/PVC, DB, tuples, KV, queues ou cache**. Créer les dépendances manquantes avec les déclarations ; conserver les dépendances existantes et leurs configurations compatibles, pas un apply global destructif ou un nouveau run-id dans tous les noms. La nouvelle entrée ne doit pas adopter/reconfigurer silencieusement une ressource étrangère. Les règles de prudence de l'agent avant intervention restent procédurales, pas un module du lanceur.

**`reset-data` choisit le reset complet du lab dédié** : arrêter les calculs puis `kind delete cluster --name aiforall-local-full`, recréer avec le YAML et réinstaller/importer. Cela efface le périmètre Kubernetes/node-local du lab, y compris DB/cache/stockage/coffre et Secrets en cluster. Aucun `delete --all` hors de cette cible, suppression de PV globale, Docker prune/volume prune ou reset de Docker Desktop/WSL. Les fichiers hôtes privés, CA/clés, images/caches du builder, registre applicatif externe éventuel et tous autres clusters restent hors périmètre. Ne jamais exécuter ce scénario de test sur des données historiques sans leur disposition explicite. Le cluster est réservé au lab : une présence étrangère connue interdit de transformer ce nom en autorisation de destruction de cette ressource.

**Pas de conservation promise après suppression des nœuds.** Les YAML actuels n'ont pas d'extraMount ; les PVC `standard` restent node-local. Le reset n'est ni une sauvegarde ni un effacement forensique. Après échec, état partiel et erreur native visibles ; relance explicite, pas de rollback transactionnel ou verrou global ajouté.

## 4. Séquence courte et initialisations réelles

Ordre nominal : fichiers privés/PKI disponibles → rebuild complet → création/réemploi Kind et CNI → import → dépendances disponibles → initialisations manquantes → remplacement des calculs → readiness. Les étapes sont des recettes just/appels natifs ; erreurs et timeouts non masqués.

- **SQL :** les entrypoints IAM/Hive/Telegraph/Manifesto/Lazaret exécutent déjà `/app/migration up` avant le service. Garder ces exécutables et ce comportement ; arrêter les anciens writers, une réplique par scope DB, attendre la disponibilité. Pas de nouveau mode Rust, Job migration inventé ou scale-out 1→2 obligatoire. Les scripts natifs PostgreSQL créent seulement les DB/rôles manquants ; rien n'est tronqué au rebuild normal. Le Job SQL distinct crée seulement les **DB absentes**, sans rôle/password nouveau ni migration applicative ; son appel/recréation/attente Complete est maintenant raccordé en code, **pas exécuté contre un datastore réel**.
- **OpenFGA :** garder sa migration datastore native existante et le modèle du dépôt. Remplacer `fga-bootstrap.py` par le CLI officiel dans des Jobs déclarés ; la commande native **`store create --model`** réalise la même séquence création store puis écriture modèle que les deux commandes indiquées au cadrage. Précision exécutable au §5.4 : CLI **0.8.2**, DSL canon monté RO et parser officiel, inspection readonly puis création seulement sur première installation explicite vide ; le petit caller **hôte** publie les vrais IDs dans `local-full-fga` via `kubectl`. Au rebuild, références conservées = aucun bootstrap/replay. Références perdues sur données existantes = erreur, jamais découverte par nom/dernier modèle ou réinitialisation. Pas de provider/state/verrou/model manager ajouté. Jobs/caller/API encore non qualifiés ; la qualification offline du parser n'est pas une preuve de création store.
- **Queues/autres dépendances :** uniquement les créations standard nécessaires aux services activés, idempotentes et sans purge ; Jobs déclarés et attente de Complete réel. Pas de fixture OAuth ou preuve de panne dans ce graphe.
- **OpenBao :** conserver les documents publics mounts/auth/policies/rôles ; distinguer coffre existant intact et bootstrap CLI du **coffre neuf** selon le §5.2. Les seeds nécessaires passent par le CLI et les primitives natives CAS0, fichiers/stdin privés ; pas de reseed de données existantes à chaque rebuild, client Python ou protocole de comparaison/ACK multi-documents à porter en shell. Un secret déjà présent n'est pas « absent » après une erreur réseau/403. Les CAS ne forment pas une transaction ; conflit/échec est signalé sans rollback destructif.
- Les sorties CLI et les ConfigMaps d'IDs sont de la configuration normale, pas un nouveau ledger de preuve. Pas de collecte automatique de logs/admin Envoy, journal d'opération, backup ou refresh pour considérer le lancement réussi.

## 5. Secrets, TLS et exceptions nommées

- **Fichiers privés complets** : IAM, Lazaret et connecteurs activés prennent leur configuration/credentials complets depuis le répertoire privé. Création/référence de Secrets Kubernetes via `kubectl create secret ... --from-file ... --dry-run=client -o yaml` transmis directement à l'apply, jamais imprimé ou stocké dans les valeurs Helm. Pas de secret en `--from-literal`, argv, contexte BuildKit, ConfigMap publique ou log. Montages RO, permissions/ACL Windows natives (`icacls`/Get-Acl) ou POSIX adéquates ; Secret volume privé ne signifie pas etcd chiffré ou RAM-only global.
- **PKI stable** : OpenSSL CLI + `ops/scripts/local-full-certificates.cnf`, sans générateur/parser de profils Python. Émission initiale explicitement nécessaire seulement si matériau absent ; réemploi sinon, vérifications OpenSSL des clés/chaînes/SAN/usages/validité, pas d'écrasement d'un bundle partiel ou de rotation implicite. `reset-data` recrée les Secrets depuis ces mêmes fichiers, pas les CA/clés. Les appels fixes d'outils natifs ne deviennent pas un deuxième catalogue de services.
- **Transport** : HTTPS pour l'edge, JWKS, S2S et HTTP des dépendances conservées ; PostgreSQL avec vérification CA/hostname et Redis TLS, ports plaintext non utilisés. Les probes/init/clients doivent viser le transport réel ; pas de `-k`, `sslmode=disable`, `tls_skip_verify` ou HTTP caché pour faire passer la readiness. Une dépendance simulée non consommée peut être désactivée, pas présentée comme TLS qualifiée. Si un client ou fournisseur au pin n'accepte pas le TLS/CA requis via sa configuration native, nommer ce blocage de hop au lot Lancement ; ne pas modifier Rust/SDK ou ajouter un proxy implicitement. **Seule exception Rust explicitement autorisée : Lazaret/Redis au §5.1**, sans changement de backend. Le lot Build figé reste hors de ce delta.
- **Accès local standard** : `https://127.0.0.1:18443`, via `kubectl --context kind-aiforall-local-full -n aiforall-local-full port-forward --address 127.0.0.1 service/envoy-mesh 18443:10000` après readiness, au premier plan. Ctrl+C termine cet accès, pas les données/cluster ; aucun framework de tunnel/processus. Le profil doit servir HTTPS sur ce port et aligner issuer/origine/cookies/callbacks. OAuth réel exige des callbacks correspondants dans l'application fournisseur existante, à préparer hors déployeur ; pas de compte ou secret vendor créé automatiquement.
- **OPS-OPENBAO-262-REDIRECTS** : dette [documentée](../guides/ops-declarative-boundaries.md), indépendante du nettoyage. La voie fichiers complets évite l'auto-auth/templating Agent pour l'hydratation Ops ; elle ne supprime pas l'accès **du produit** à OpenBao (ex. Transit, KV Lazaret) ni ses permissions/credentials. Le token Lazaret dans sa configuration est une capacité legacy, pas un token root. Fournir des credentials autorisés valides comme inputs ; renouvellement/perte du coffre non couverts par un manager automatique. S'il reste un consommateur imposant cette hydratation/auth Ops, le nommer comme capacité non retirée/non qualifiée ; pas de conservation tacite du framework ou de claim Agent sûr au pin 2.6.2. Aucun bump/patch/proxy ni downgrade TLS dans ce lot.

### 5.1 Exception autorisée : transport Redis TLS dans Lazaret, sans changement métier

Choix utilisateur explicite **« TLS natif »** : conserver Redis, ses données et la sémantique du port KV ; étendre seulement sa configuration, l'adaptateur Redis et le raccord setup. Pas de PostgreSQL de remplacement, migration des données, proxy, nouveau framework, extension SDK ou changement des opérations KV/CAS/purge.

**Interface configuration minimale, rétrocompatible :**

- `RedisConfig` conserve `hostname`/`port` et reçoit `tls_enabled: bool` avec défaut serde/Default **false**, et `tls_ca_cert_path: Option<PathBuf>` avec défaut **None** (chaîne de chemin TOML).
- `url()` retourne désormais un **`Result<String, …>`** après validation par `url::Host` : `redis://` lorsque TLS est désactivé, `rediss://` lorsqu'il est activé ; le consommateur setup propage l'erreur. Pas de nouveau champ d'URL libre, de flag insecure ou de changement de DB Redis ; ne pas permettre à un hostname/fragment d'activer `#insecure` ou un autre schéma.
- Pour cette extension locale, TLS activé exige le chemin d'une CA PEM explicite, monté en lecture seule ; absence, fichier vide/illisible/invalide ou configuration incohérente = erreur, jamais confiance désactivée ni retour au plaintext. CA renseignée avec TLS désactivé = configuration refusée plutôt que CA silencieusement ignorée. Les anciens fichiers sans ces deux champs gardent leur comportement plaintext ; cela ne s'applique pas au nouveau profil, qui les définit explicitement.

**Adaptateur et dépendances, au pin résolu redis 0.27.6 :**

- Garder `RedisKvStore::connect(&str)` compatible avec les usages plaintext existants ; ajouter une entrée TLS bornée, par exemple `connect_tls(url: &str, ca_cert_path: &Path)`, puis la sélectionner dans `build_platform_kv` selon la configuration. Pas de dépendance de la configuration vers l'infra, ni de changement du trait `AsyncKvStore`.
- Le driver fournit réellement `redis::Client::build_with_tls(conn_info, redis::TlsCertificates { client_tls: None, root_cert: Some(ca_pem_bytes) })`. Utiliser son parsing/validation TLS avec schéma `rediss`, vérification du certificat et du nom serveur, `insecure: false`. Pas de verifier personnalisé, `#insecure` ou feature `tls-rustls-insecure`. Aucun mTLS Redis nouveau n'est imposé : l'authentification TLS du serveur par la CA est le périmètre de cette extension.
- Activer **`tls-rustls`** sur la dépendance redis consommée par `lazaret-infra`, sans bump du driver ; `Cargo.lock` ne change que si nécessaire à cette activation. Les connexions actuelles sont synchrones (`get_connection`) et déportées par `spawn_blocking` : ne pas ajouter `tokio-rustls-comp` ni réécrire l'adaptateur async sans besoin introduit. Contrôler l'unification finale des features au gate ciblé, non exécuté par cette rédaction.
- Attention au provider : redis 0.27.6 active `rustls/ring` par `tls-rustls`, tandis que le workspace déclare `rustls/aws_lc_rs`. Son `create_rustls_config` appelle `ClientConfig::builder()` ; ne pas laisser la coexistence des deux provoquer un panic de sélection du provider. Réutiliser le provider standard déjà installé, ou installer nativement celui du workspace côté Lazaret avant construction/usage TLS si nécessaire. Cette initialisation locale ne justifie ni patch du driver ni modification du framework/SDK. Tester aussi le chemin TLS sans supposer qu'un serveur HTTP a auparavant initialisé Rustls.
- Propager les erreurs de configuration/lecture CA et de connexion/handshake/commande en erreur du chemin Redis, sans fallback backend ni downgrade. Conserver des diagnostics expurgés, sans contenu de configuration ou certificat. `Client::open` et la construction d'un client ne sont pas une connexion réussie : ne pas annoncer Redis prêt sur ce seul résultat.

**Profil et conservation :** le nouveau profil Kind maintient `kv.backend = "redis"`, active `redis.tls_enabled`, fournit `redis.tls_ca_cert_path` et le montage de CA correspondant. Redis sert en TLS natif avec certificat/SAN du DNS réellement utilisé ; pas de port plaintext consommé dans ce profil. Conserver DB, PVC/AOF/RDB et clés ; un redémarrage de transition TLS n'autorise ni flush, recréation du volume ni migration vers un autre backend. Les profils/tests hérités explicitement sans TLS restent supportés.

**QA ciblée :** configuration ancienne sans champs TLS → mêmes valeurs et URL ; activation → `rediss` ; champs CA manquants/incohérents et tentative insecure refusés. Tests de l'adaptateur sur Redis TLS réel : une opération KV réussie avec bonne CA/SAN, échec avec mauvaise CA/SAN et contre un endpoint plaintext, absence de fallback, absence de panic Rustls avec les features réelles ; forcer le handshake par une opération, pas seulement construire le client. Conserver les oracles Redis plaintext KV/CAS/isolation/purge existants (`apparatus_p3_t6_kv.rs`, `apparatus_p3_t8_kv_purge.rs`) et une sentinelle de données au passage TLS. Units de configuration et fmt/check/Clippy ciblés aux crates modifiées ; pas de campagne Cargo globale imposée. ### 5.2 OpenBao : existant intact, première installation persistante

[ADR-0611](../adr/0611-openbao-neuf-raft-pvc-sans-conversion-du-coffre-existant.md) **Proposed / Partial** et [contrat OpenBao dédié v1.2](kind-local-openbao-bootstrap.md) fixent ce delta ; pas de réécriture des faits Redis du §5.1.

- Existant HTTPS compatible : aucun apply/upgrade/rollout/reseed, particulièrement pour le DEV mémoire. Le supprimer des rendus d'un release Helm que l'on upgrade peut aussi le supprimer : l'exclusion doit préserver les objets existants, pas seulement un flag. Aucune migration DEV→durable implicite.
- Neuf : même image 2.6.2, serveur non-DEV, **Raft mono-nœud/PVC `openbao-data`**, CLI standard init/unseal/mounts/auth/policies/seeds ; KV v2 `secret` déclaré explicitement hors DEV. PVC déjà initialisé ≠ coffre neuf ; attendre serveur joignable, pas readiness unsealed avant init/unseal.
- Chemins privés explicites d'init exclusive, d'input unseal, de CA et de sorties tokens définis dans le contrat dédié ; jamais argv/log ou recherche du « dernier bundle ». Un fichier init n'est pas une sauvegarde des données. **Choix utilisateur acquis « 1/1 local (Recommended) » : Shamir 1 part / seuil 1, fichier hôte privé protégé, coffre neuf du lab mono-opérateur uniquement.** Init `-key-shares=1 -key-threshold=1`, unseal d'une part par JSON stdin ; réserve de garde levée, aucun rekey de l'existant ni auto-unseal statique/KMS.
