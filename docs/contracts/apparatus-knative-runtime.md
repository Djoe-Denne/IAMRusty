- Version : 1 — 2026-10-19 ; annexes décisionnelles B1–B6 complétées le 2026-10-20, ratifiées par Accept humain.
- Statut : Accepted le 2026-10-20 (Accept humain du paquet ; pins B5 reportés à un spike séparé) ; Réalité : Unimplemented
- Canon primaire : [ADR-0012](../adr/0012-apparatus-http-knative-par-binding.md), Accepté le 2026-10-20 ; Réalité Unimplemented jusqu’aux preuves de campagne.
- Base observée : `2760e02bc43f5149070aac6ace29f7c2d11f9aad`.
- Portée : contrat de cible et de preuves ; **pas un GO code/runtime**, pas le contrat complet de tous les cycles métier.

## 1. Frontières et invariants

La release OCI immuable est réutilisable ; l’installation est isolée par `(project_id, binding_id)`, jamais par digest seul. Binding = `ProjectComponent.id`. Les digests descripteur, enveloppe et image CRI gardent leurs rôles distincts (0002/0008) ; le kubelet utilise exclusivement l’image pinée issue d’une enveloppe admise. Activer/configurer un binding ne produit ni `VALID` ni `VERIFIED`.

Manifesto reste l’autorité métier (activation, génération, consentement/grant revision, révocation). Il n’obtient aucun client/token Kubernetes ; les gates zéro `k8s`/`kubernetes` sous ses `*/src` ne sont ni déplacées ni affaiblies. Adaptation Kubernetes dans `workers/apparatus-operator` ; Lazaret reste la seule frontière d’invoke/I/O. Aucun nouveau BC HTTP de contrôle, proxy/queue HTTP maison ou scheduler propriétaire.

Les identités privilégiées P4 restent séparées du plugin ; les SA internes Knative sont un TCB supplémentaire à inventorier, pas une justification de fusionner les quatre responsabilités existantes. Ni plugin ni publisher n’obtiennent de token API ou droit de créer des workloads. `automountServiceAccountToken: false` côté plugin ; RBAC minimal côté adaptateur.

## 2. Identités, générations et projection

Distinguer obligatoirement :

- **Release** : identité immuable de contenu descripteur 0002 ; peut être commune à plusieurs installations. Aucun nom de workload/route ne repose sur ce seul digest.
- **Binding** : installation projet × binding ; objet Serving stable distinct des autres bindings, y compris pour une même release. Nom Kubernetes déterministe dérivé de la clé complète, validé contre les collisions ; labels ne constituent pas une preuve d’autorité/propriété.
- **Génération métier** : version désirée, distincte de `metadata.generation` Kubernetes et de la Revision Knative. La projection conserve explicitement leurs correspondances ; une observation ancienne n’autorise pas une nouvelle génération.
- **Grant revision** : version de consentement/permissions, distincte de la génération ; une projection de route n’accorde jamais de droits par elle-même.
- **Instance** : identité d’une exécution/replica réelle, enregistrée par le chemin de confiance Lazaret. Ce n’est ni le digest, ni le binding, ni une identité fictive permanente recyclée après scale-to-zero. Relation instance ↔ Pod UID ↔ Revision ↔ binding/génération/release prouvée ; aucune identité d’instance partagée entre bindings/replicas.

Le modèle `WorkloadIdentity { instance, binding, release, generation, grant_revision }` est conservé ; ne pas réduire ses champs pour faire entrer un service virtuel Knative. Rotation/enrollment et invalidation reçoivent une proposition explicite en annexe B1 ; sa ratification et les preuves B2 restent requises avant code/publication.

Une projection interne de confiance vers Lazaret associe au minimum projet, binding, génération, release admise, grant revision, état logique, identité/UID de la ressource Serving et de sa Revision cible, endpoint privé et version de projection. Les DTO/port/API et migrations proposés sont inventoriés §13, non ratifiés. L'annexe B3 tranche source, writer, CAS/fencing et panne ; B5 propose la borne de fraîcheur et garde le verrou des pins ouvert. Aucun secret value ni token Kubernetes dans cette projection ; aucune URL fournie par le caller/publisher. Absence/ambiguïté/obsolescence = refus, jamais endpoint reconstruit par digest ni fallback silencieux vers le dispatch local.

## 3. Activation logique et ressource avant le premier appel

**Option retenue : pré-déclaration à zéro.** Après lecture authoritative de l’activation et vérification de la release `VALID`, l’adaptateur projette un `serving.knative.dev/v1 Service` privé par binding, son template plateforme et sa configuration. Aucune requête d’échauffement/smoke/probe applicative n’est émise pendant l’activation. Readiness probes du Pod au réveil ≠ autorisation métier.

Cette pré-déclaration ne demande ni Pod plugin ni nœud plugin. Les contrôleurs, ingress, Activator et services de sécurité/metadata partagés, eux, restent disponibles. Si la route n’est pas encore établie, l’invoke autorisé ne part pas vers une URL imaginaire : indisponibilité bornée, sans file métier maison. Un Knative Service/Revision déclaré `Ready` avec échelle initiale zéro ne prouve pas qu’un Pod tourne.

**Variante non retenue : provisionnement au premier usage.** Knative ne crée pas un Service inconnu en découvrant une URL. Cette variante demanderait un ensure métier idempotent, durable/fencé par binding+génération et une attente de route bornée, hors Manifesto ; elle ne permettrait ni réimplémentation d’Activator ni deuxième buffer HTTP. Elle exige un amendement du contrat et une motivation métier avant de remplacer la pré-déclaration.

## 4. Premier invoke, concurrence et attente

Ordre exigé : vérifier caller/autorité courante → activation/génération/release admise et grant revision → projection valide → envoyer à l’ingress privé Serving → Activator/KPA si zéro/capacité absente → queue-proxy → plugin Ready. L’Activator bufferise la demande et KPA demande des replicas ; à chaud, le chemin Knative peut éviter l’Activator. L’attente du résultat HTTP reste bornée ; pas de réponse produit `QUEUED`/`SCALING`, job asynchrone ou nouvel état public introduit implicitement.

**Constat à la base (B1) :** l’actuel `POST /invoke?project_id=…` vérifie une session de **workload**, impose `CallOrigin::Background`, puis autorise un grant vivant. Ce n’est pas une API générique end-user permettant déjà de réveiller une instance inexistante. Définir le caller et sa preuve valide avant réveil, sans dépendance circulaire au certificat/session du plugin dormant. Ne pas accepter un bearer IAM dans le plugin ni inventer une nouvelle route publique au cours du câblage. Si un nouveau contrat d’appel est nécessaire, le ratifier explicitement ; sinon démontrer le parcours avec les interfaces conservées. L’autorisation avant réveil reste assurée par Lazaret ; aucun sidecar d’autorisation n’est choisi ici.

Concurrence : un seul objet Serving logique courant par binding ; apply déterministe et idempotent pour `(project, binding, génération)`, writer unique et protection CAS/fencing inter-processus. Deux premiers appels ne créent ni deux installations, ni deux routes concurrentes ; ils utilisent le buffer natif Knative. Plusieurs replicas du **même** binding restent possibles dans les bornes autorisées, chacun avec son identité propre. Une génération dépassée, un apply retardé ou un événement rejoué ne recrée pas une installation désactivée/supprimée. Pas de lock mémoire présenté comme garantie distribuée.

L’idempotence de **provisionnement** ne vaut pas déduplication d’invokes. `operation_id` est conservé, mais aucune garantie exactly-once/déduplication métier n’est ajoutée sans contrat existant et preuve de persistance.

## 5. Configuration Serving portable et bornée

Socle : `serving.knative.dev/v1 Service` ; annotations du template de Revision : `autoscaling.knative.dev/class: kpa.autoscaling.knative.dev`, `autoscaling.knative.dev/min-scale: "0"`, `autoscaling.knative.dev/initial-scale: "0"`. Config Serving : `enable-scale-to-zero: "true"` et `allow-zero-initial-scale: "true"`. Vérifier ces clés et leur portée sur la version **épinglée** avant livraison. L’échelle initiale upstream vaut 1 par défaut : omettre ce réglage violerait « activation sans Pod ».

Le profil plateforme doit fixer et tester :

- `autoscaling.knative.dev/max-scale` **strictement positif** (0 signifie illimité upstream), plafond global `max-scale-limit` approprié ; pas seulement une borne par Revision présentée comme budget total du binding lorsque plusieurs Revisions coexistent ;
- `containerConcurrency` strictement positif et cible KPA/concurrence cohérente, taille de requête et nombre d’attentes admissibles bornés ;
- requests/limits CPU/mémoire et quotas de namespace/binding ; limites prises dans une politique plateforme approuvée, pas celles demandées arbitrairement par le publisher ;
- `timeoutSeconds` de Revision et délais ingress, Activator/queue-proxy, client HTTP Lazaret et appelant ; deadline de bout en bout cohérente et non prolongée indéfiniment par des retries ;
- fenêtres d’inactivité/rétention/scale-to-zero Knative documentées ; aucun cron de suppression/recréation Pod pour reproduire KPA ;
- traffic ciblant uniquement la Revision de génération/release autorisée, sans tag/route vers une ancienne Revision contournant révocation ou migration.

Aucun chiffre de capacité ni SLO n’est ratifié par ce fichier. B5 propose explicitement des valeurs à ratifier ; pins/digests exacts manquent encore et bloquent la publication. Profil sans lock ni bornes approuvés = non déployable. Ne pas installer HPA/KEDA contrôlant le même workload ni laisser l’ancien operator écrire/supprimer les Pods Knative. Les enfants (Revision, Deployment, ReplicaSet, Pod, Service réseau) sont gérés par leurs contrôleurs standards.

Helm : packaging de la pile tierce et éventuellement rendu contrôlé, **pas** control loop. Préférence projection métier en manifests/Kustomize ; pas de chart arbitraire publisher, CRD/RBAC/hostPath/privileged/hostNetwork/hooks libres. Flux peut réconcilier la pile et ses paramètres ; aucun double writer Flux/adaptateur sur les mêmes champs des Services par binding. Suspendre Flux/HelmRelease ne supprime ni n’arrête les workloads. B2 propose net-istio/Istio, dépendance supplémentaire à ratifier et à qualifier ; pins/compatibilité restent un verrou B5 ; le site Knative consulté en `release-1.23` n’est pas le pin de livraison.

## 6. Autorisation, révocation et réseau

- Toute demande non autorisée est refusée **avant** provisionnement/réveil/forwarding ; session cryptographiquement valide ou état Serving Ready ne suffisent jamais. Relecture authoritative des droits selon 0004/0007, y compris génération/grant revision. Readiness observée = information opérationnelle, pas permission.
- Ingress/route cluster-local : aucun accès public alternatif au plugin. « Cluster-local » seul ne bloque pas les autres workloads du cluster. Interdire les accès directs aux endpoints de Revision, Services/Pods, ports user-container et URLs taguées ; laisser seulement les chemins plateforme nécessaires, avec authentification démontrée. DNS obscur ou URL non publiée n’est pas une barrière.
- Policies et preuves doivent couvrir Lazaret → ingress/Activator → queue-proxy → plugin, trafic de contrôle/probes strictement nécessaires, et plugin → Lazaret pour capacités ; default deny et interdiction Transit/système maintenues. Ne pas simplement autoriser tout `knative-serving`/tout namespace plugins : distinguer ingress, activator, controllers et code auteur. Egress/DNS et mécanisme d’authentification évalués avec le dataplane choisi.
- **Bloquant B2 :** Knative n’atteste pas l’identité Lazaret et ne transporte pas magiquement son mTLS. Établir chaque terminaison TLS, pair certifié, validation de binding/génération/instance et résistance aux headers forgés. La politique doit marcher au réveil **et** sur le chemin chaud direct sans Activator. Si le transit impose de modifier le modèle de confiance ou les contrats, amender la décision avant code ; ne pas ajouter discrètement un proxy métier.
- Révocation/désactivation : refus immédiat des **nouvelles autorisations**, invalidation/fencing de la projection et des anciens epochs/identités ; ne pas attendre le ticker, le scale-to-zero ou Flux suspend pour fermer l’accès. Admission révoquée et autorisation de binding sont deux décisions distinctes.
- **Bloquant B4 :** une requête admise par Lazaret puis bufferisée par Activator peut être révoquée pendant l’attente. Spécifier la linéarisation/validation avant effet, le sort des requêtes déjà transmises, le drain et la portée d’une annulation. Une relecture à Lazaret avant envoi ne prouve pas une révocation pendant le buffer. Ne promettre ni arrêt instantané d’un effet en cours ni admission après révocation. Déterminer et prouver le mécanisme sans queue/proxy maison ; pas de révocation globale déclarée livrée.

## 7. État, repos, retrait et propriété

Séparer état **logique** du binding, état **observé** Serving et exécutions effectives. Binding actif + Service à zéro = dormant et invocable, pas nécessairement erreur/pending ; Pod Ready ne réactive pas un binding interdit. La sémantique des états/événements publics Manifesto actuels reste conservée jusqu’à décision explicite. Un nouveau vocabulaire interne n’est pas un nouvel event déjà accepté.

Scale-to-zero retire les Pods, **pas** le binding, l’artefact admis, les références de secrets ni le KV plateforme. Tout état uniquement en mémoire ou filesystem éphémère doit pouvoir disparaître. Pas d’hibernation mémoire ni de PVC implicite. Compatibilité d’un plugin HTTP avec ce modèle, durée des requêtes/streams, tâches de fond et éventuelle migration de données sont à qualifier (B6).

Retrait minimal sûr : fermer les nouvelles autorisations et fencer la génération, retirer l’exposition/projection, puis traiter les requêtes en cours et l’objet Serving selon la politique de drain à ratifier. L’ordre doit résister aux replays et à la recréation d’un objet de même nom. Conservation/purge des données, délais et destruction irréversible ne sont **pas** décidés ; aucun uninstall global des releases/Secrets/PVC partagés à partir d’un seul binding. Retirer un binding ne révoque pas une release pour les autres projets.

Propriété : enregistrer UID effectivement créé/observé, owner chain, namespace, génération et rôle du writer. Vérifier les UID et utiliser des préconditions de suppression ; conflit/propriété inconnue = stop, pas adoption ni `force`. `ownerReferences` seulement valides pour les scopes Kubernetes, jamais vers un UUID SQL Manifesto ou une ressource d’un autre namespace. Le contrôleur ne supprime pas lui-même les enfants Knative ; ses propres objets doivent avoir une généalogie vérifiable. Nom, digest, label ou field manager seuls ne prouvent pas la propriété.

Secrets : références scopées binding et politique plateforme (OpenBao/Secret approuvé), **jamais valeurs** dans artefact, labels, projection, events ou logs. Un secret projet n’est pas mutualisé par digest. Rotation, invalidation et nettoyage ne doivent ni réveiller un plugin à son insu ni effacer un secret utilisé ailleurs ; modalités exactes à fixer avec B6.

## 8. Cold-start et défaillances

Image pull, scheduling sans capacité, révision invalide, absence d’ingress, erreur de readiness, projection périmée et échec de service d’autorité doivent produire une issue bornée et observable, fail-closed. Saturation et deadline épuisée ne déclenchent ni file durable maison ni attente infinie. Pas de nouveau code HTTP/DTO introduit sans examen de `InvokeHttpError` et du contrat actuel ; fixer le mapping exact en B5. Échec opérationnel ≠ refus d’autorisation dans les preuves.

Lazaret n’ajoute pas de retry automatique d’opération non idempotente après envoi ambigu. Inspecter aussi les retries ingress/Activator/queue-proxy de la version choisie : la chaîne complète doit être compatible avec les garanties métier. Timeout/déconnexion client ne prouve pas que l’opération n’a pas eu lieu. Un retry client peut produire un doublon ; conserver `operation_id` ne suffit pas à promettre le contraire. La politique pour ces ambiguïtés reste explicite et testée ; pas de garantie exactly-once.

## 9. Surfaces, migration et hors scope

Surfaces attendues, **sans autorisation de changer leur contrat public implicitement** :

- `workers/apparatus-operator/src/{controller,desired_state}.rs` : fin de la clé digest pour le runtime, projection binding/génération, contrôle de propriété, observation Serving ; admission/Jobs inchangés. `ReadyBinding` actuel ne porte pas les versions nécessaires : décider projection/transport avant de modifier ce trait/DTO.
- `services/Lazaret/application/src/invoke.rs` : locator bindé et attente HTTP bornée ; `PluginEndpointLocator` n’appelle pas Kubernetes. `identity.rs`, grants et enrollment : préserver leur autorité et claims, démontrer le cycle d’instance.
- Projections métier depuis Manifesto : conserver routes `/components`, routes Lazaret, `crates/manifesto-events`, `crates/apparatus-contracts/src/{protocol,ports}.rs` tant qu’aucun amendement ratifié ne les change ; ne pas fabriquer un event de démarrage/arrêt requis par Knative.
- `ops/deploy/p4/` et pile système : installation/pins Serving/ingress, policies, SA, profils, placement. Aucun changement du monolithe/Compose, du framework ou de CI demandé par ce contrat.

Plan de migration à arrêter avant activation : inventaire CR/Pods/Services historiques par digest et bindings concernés ; nouvel objet par binding avec mapping explicite ; double contrôle/traffic interdit ; couper l’ancien endpoint digest avant ouverture du nouveau chemin ; retrait uniquement des objets prouvés possédés, jamais suppression partagée depuis la réconciliation d’un seul binding. Préserver les données. Rollback fail-closed qui ne restaure pas silencieusement le partage inter-projets. Migrations de contrôle additives explicitement proposées en B3/§13 ; migrations destructives de données hors scope B6, jamais implicites.

L’actuel `apply_valid_record` peut supprimer un CR par digest et `reconcile_object` supprimer un Pod : ces chemins ne doivent jamais agir sur les objets partagés historiques au nom d’un seul binding, ni sur les enfants Serving. Le locator digest de Lazaret et le gold path 0605 sont des preuves historiques/locales, pas le routage cible.

Hors scope : Factory auteur/host P5/P6, runtime non HTTP, coût zéro global, cloud bootstrap/ratification 0600, autoscaler nœuds/predictif, nouveau service de contrôle, partage explicite inter-bindings. Pools système/plugins distincts ; nœuds plugins mutualisés, pas un nœud par binding. Le pool système et la plateforme partagée restent actifs ; choix/provider et minimum de nœuds sont séparés. Partage de noyau ≠ sandbox forte : pas d’exposition de code non fiable sans profil de confiance/isolation qualifié.

## 10. Blocages avant GO implémentation

- **B1 — caller du réveil et cycle d’identité.** Parcours sans session de plugin déjà vivant ; relation instance/Pod/Revision et enrollment au réveil, sans modifier silencieusement les claims ni accepter un bearer IAM dans le plugin.
- **B2 — transport et isolation.** Ingress/pins retenus, preuve mTLS/identité et anti-contournement à froid/chaud ; compatibilité NetworkPolicy/queue-proxy/probes ; sandbox gVisor/Kata ou autre, ou restriction de confiance documentée. Aucun de ces profils n’est présenté livré.
- **B3 — projection/générations.** Source/writer/CAS/fencing et durée de validité, autorité pour désactivation/retrait, évolution éventuelle de `ReadyBinding`/trait/transport et migration des objets par digest. Aucun event/HTTP/trait changé sans inventaire et décision correspondante.
- **B4 — révocation, buffer et drain.** Sémantique d’une requête déjà acceptée, preuve avant effet, invalidation des vieilles instances/Revisions et politique de retrait. Choix métier requis, pas une capacité implicite de Knative.
- **B5 — profil opératoire borné.** Versions Serving/ingress épinglées et compatibilité, valeurs capacité/concurrence/ressources/deadlines/idle, cohérence des retries et mapping HTTP existant ; rien d’illimité/non documenté accepté.
- **B6 — état et cycle métier.** Contrat HTTP réellement éligible au retour à zéro, stockage externe/persistance et migrations éventuelles, rotation/rétention/retrait des références de secrets ; aucun cycle complet de désinstallation inventé.

Les annexes §12 proposent ces décisions ; la lead doit faire ratifier l'ensemble, y compris restrictions/ownership et profil/lock B5, avant de transformer ce document en ordre de codage. Les pins exacts ne sont pas fournis par A : ce verrou reste explicitement NON LEVÉ. Un spike technique peut documenter une compatibilité mais ne ferme ni blocage métier, ni gate pré-prod par lui-même. Le lot présent n’autorise aucun spike/runtime.

## 12. Annexes décisionnelles B1–B6 — propositions du lot A

Les choix suivants complètent la v1 ; **tous restent à ratifier**, sans modification du Statut/Réalité de 0012. Ils prévalent sur les questions ouvertes des §§2–10 seulement après Accept humain. Les valeurs proposées ne sont ni des mesures ni des SLO acquis. Une restriction explicitement indiquée est un choix de périmètre à accepter, pas un trou à combler librement pendant le code. Les compatibilités non démontrées restent des gates techniques.

### B1 — Caller vivant distinct de la cible dormante ; enrollment par instance

**Choix proposé.** Le premier caller de cette tranche est un **workload déjà vivant et enrôlé auprès de Lazaret**, distinct de la cible dormante. Il présente son certificat mTLS et sa session workload courante ; `CallOrigin::Background` reste requis. L'activation administrative n'accorde pas ce droit au caller. Pas de session fictive de la cible, pas de certificat permanent par Service, pas d'end-user/browser ni de host P5/P6 inventé. Cette restriction workload→plugin est à ratifier ; si le produit exige un premier appel utilisateur sans workload caller, **retour A**, pas ajout d'un bearer au plugin.

Nouvelle route Lazaret proposée, relative au préfixe de service : `POST /runtime/invoke?project_id=…`. `RuntimeInvokeRequestV1` contient `target_binding_id`, `expected_generation`, `operation_id`, opération et payload bornés ; le projet vient de la query, jamais d'une URL de destination fournie par le caller. La session identifie uniquement la **source**. Lazaret consulte l'autorité pour source, cible, génération, consentements et politique de la capacité proposée `runtime.invoke` ; ACL ∩ consentement ∩ politique reste la règle. Le grant de cible n'est pas déduit du droit de l'admin, d'un droit du seul caller ou du digest commun. `/invoke` existant garde son DTO et sa sémantique ; les bindings migrés ne peuvent plus y joindre un endpoint digest. Pas de nouveau type OpenFGA implicite.

Après autorisation courante, Lazaret signe un `RuntimeInvocationTicketV1` (JWS, clé dédiée au purpose invoke) : version, issuer/audience, identifiant d'autorisation non réutilisable, source, projet/cible, génération, release, grant revision, epoch de révocation, `operation_id`, hash canonique de l'opération/payload, date d'émission/expiration et deadline (jamais au-delà de la validité de la preuve caller). Aucune identité d'instance cible n'y est inventée avant réveil. Le ticket accompagne **la requête elle-même**, pas une nouvelle file ; il n'est ni bearer IAM ni permission autonome d'effectuer une I/O. Sa consommation est définie en B4.

**Enrollment proposé :** l'operator observe dès sa création (sans attendre Ready, pour éviter une boucle enrollment/readiness) un Pod réellement possédé par la chaîne Revision→Deployment→ReplicaSet→Pod, puis enregistre via B3 son UID, namespace, ServiceAccount, Revision UID, binding, génération et release. Le Pod génère sa clé privée en mémoire et adresse CSR + preuve à `POST /runtime/enroll` Lazaret. La preuve est un jeton projeté, lié au Pod UID, audience enrollment dédiée ; `automountServiceAccountToken=false`, aucun jeton audience API cluster ni token par défaut monté. Lazaret vérifie signature/issuer/audience/expiration via clés OIDC de confiance configurées, **sans client Kubernetes**, et recoupe les claims Pod/SA/namespace avec l'enregistrement courant authoritative. Une preuve fournie sans correspondance, un UID supprimé ou une Revision ancienne sont refusés. Validation offline du jeton seule ne prouve pas la présence courante du Pod.

L'operator réserve un nouvel `instance_id` dans l'enregistrement authoritative du Pod ; seul l'enrollment Lazaret active ses credentials. Le certificat est lié à CSR + instance, avec unicité par instance/Pod UID, pas unicité globale du binding empêchant les replicas. La clé reste dans le Pod ; la preuve projetée n'est pas loggée. `/session` peut émettre une session pour cette instance après les mêmes vérifications. `WorkloadIdentity` et `SessionClaims` existants conservent leurs champs ; epoch/UID/Revision sont liés côté registre, pas ajoutés silencieusement à leurs claims. Réveil après zéro = nouveau Pod UID/nouvelle instance, anciennes entrées clôturées ; rotation cert/session ne réactive jamais une ancienne entrée. La modalité CA de 0010 n'est pas décidée par ce choix ; aucune fourniture de clé privée à Lazaret n'est introduite.

**Responsables/surfaces :** D : caller, ticket, enrollment/registre/session ; C : attestation observée Pod/Revision et autorité B3 ; B : preuve projetée et clés publiques de confiance. Fichiers attribués §14. **Oracles :** source vivante→cible à zéro sans session cible ; requête sans droit refusée avant forward ; faux UID/SA/Revision, preuve rejouée après retrait et substitution de CSR refusés ; deux replicas = deux instances ; deux bindings de même release sans identité partagée ; nouveau réveil avec ancienne session refusée. La délivrance enrollment est idempotente sur preuve+empreinte CSR, jamais transfert d'une identité sur un autre Pod.

### B2 — Ingress net-istio privé ; mTLS hop-by-hop et délégation signée

**Choix proposé, à ratifier :** un seul ingress Serving **net-istio**, gateway interne uniquement, avec transport Istio/Envoy standard en mTLS strict ; pas de Kourier en parallèle ni de proxy métier supplémentaire. Le sidecar standard de transport n'est **pas** un sidecar d'autorisation métier ; l'autorisation pré-réveil reste Lazaret. Cette dépendance mesh supplémentaire est un delta structurant explicite de 0012, pas une prétendue réutilisation déjà livrée du mesh actuel. Si son intégration n'est pas retenue ou compatible, retour A ; aucune rétrogradation silencieuse vers HTTP clair/headers de confiance. Version/digests et compatibilité sont soumis au verrou B5.

Pairs à configurer et prouver : Lazaret→gateway interne ; gateway→Activator puis Activator→queue-proxy à froid ; gateway→queue-proxy à chaud. Chaque terminaison Envoy vérifie certificat, trust domain et identité du **pair immédiat**, avec policies distinguant les ServiceAccounts de gateway, Activator et Lazaret. Les connexions proxy→conteneur au sein d'un Pod constituent un segment local de la même frontière sandbox, pas un mTLS bout en bout au plugin. À chaud l'identité du pair peut changer, jamais le besoin de validation du ticket signé. Les clés de transport ne sont pas des certificats d'instance B1 ; aucun certificat/header ne prouve à lui seul le consentement métier.

L'ingress externe refuse ces routes ; l'ingress privé n'accepte que le principal Lazaret autorisé. Nettoyer/refuser les headers entrants réservés d'identité, de routage interne et d'enrollment ; les headers de certificat ne sont admis que depuis une terminaison authentifiée qui les réécrit. Le header `Apparatus-Invocation` transporte un ticket JWS vérifiable dont hash, cible et deadline sont contrôlés avant tout effet via B4. Un `Host`, `Forwarded`, `X-Forwarded-Client-Cert`, `K-*` ou header Apparatus forgé ne doit ni choisir une autre Revision/binding ni conférer de droit. Le ticket ne remplace pas la restriction réseau : un accès direct autorisé par erreur pourrait déjà réveiller du compute.

Default-deny ingress/egress plugins ; autoriser seulement le chemin standard authentifié jusqu'au port queue-proxy, plugin→Lazaret pour enrollment/session/capacités, résolution DNS et contrôle de transport strictement requis. Pas de plugin→plugin/Transit/API cluster/Internet ni de permissions générales par namespace `knative-serving`. Restreindre ports admin/metrics, endpoints Pod/Service directs et URLs taguées ; aucun tag de trafic applicatif publié. Les probes kubelet/queue-proxy et metrics KPA utilisent leurs ports/paths de contrôle, jamais un handler métier et jamais un ticket d'invoke ; leurs exceptions ne doivent pas ouvrir le port applicatif. Une NetworkPolicy seule ne distingue pas les conteneurs du même Pod ni ne prouve l'identité mTLS.

**Sandbox cible proposée : gVisor (`runsc`) via RuntimeClass plateforme**, tout le Pod plugin (user-container, queue-proxy et transport) dans ce profil, sans privilèges/hostNetwork/hostPath, capacités minimales, filesystem en lecture seule hors volumes éphémères bornés. Pool plugins séparé du pool système, nœuds mutualisés. Compatibilité de queue-proxy, injection/probes, démarrage/départ des sidecars et montée depuis zéro **non démontrée ici**. Tant que ces preuves ou le pin RuntimeClass/runtime manquent : aucune exposition de code hostile ; un éventuel spike sur image de référence contrôlée requiert un accord séparé, n'est pas une qualification sécurité. Ne pas présenter le partage de noyau runc comme solution de repli conforme.

**Responsable :** B pour pins, mesh, policies, probes et sandbox ; D pour vérification des tickets/frontière Lazaret ; C pour template Serving ne permettant pas d'override publisher. **Oracles :** matrice cold/hot avec principal permis fonctionnel et canary disponible, autre binding/principal refusé au hop identifié ; falsification de tous les headers réservés ; accès direct Pod/Service/Revision/tag et egress interdits ; probes/metrics fonctionnent sans exécuter d'opération ; nouveau réveil et extinction complète du Pod y compris sidecars. Un DNS cassé, un Pod absent ou une simple capture de configuration ne valent pas preuve de confinement.

### B3 — Autorité transactionnelle Manifesto ; observation non autorisante

**Choix proposé, à ratifier :** source métier = writer PostgreSQL Manifesto ; pas de lecture replica/cache pour une décision allow. C expose un **port métier interne** et son adapter HTTP protégé, sans dépendance cluster dans Manifesto. Operator et Lazaret n'ont pas d'accès SQL direct à sa base. Les événements existants peuvent accélérer une réconciliation, jamais rendre une projection authoritative ni porter une autorisation. Aucun nouveau topic/event `Started/Stopped/Ready` n'est requis.

Schéma additif proposé : `apparatus_runtime_bindings` (clé projet/binding, génération métier existante, grant revision, release admise, état, epoch de révocation, version monotone, profil), `apparatus_runtime_observations` (Service UID, génération observée, Revision UID, endpoint interne contrôlé, fence writer, version et date d'observation), `apparatus_runtime_instances` (mapping B1 et état d'instance), `apparatus_runtime_effects` (réservations B4). Contraintes de clé/monotonie et tombstones durables ; aucune autorisation dans un simple label ou nom DNS. Pas de génération métier concurrente : utiliser la génération Apparatus existante, et mettre à jour epoch/version dans la transaction de changement métier/consentement.

Transport proposé, chemins relatifs au préfixe Manifesto : `GET /internal/apparatus/runtime/bindings` (pagination/cursor), `GET /internal/apparatus/runtime/bindings/{binding_id}?project_id=…` (snapshot writer), `POST …/bindings/{binding_id}/writer-lease`, `PUT …/bindings/{binding_id}/observation`, `PUT …/bindings/{binding_id}/instances/{instance_id}` ; `project_id` est obligatoire et recoupé à chaque chemin. Commande additionnelle explicite : `POST …/bindings/{binding_id}/instances/{instance_id}/revoke`, permise à Lazaret pour fermer/fencer une identité, jamais pour activer un binding. Elle persiste un tombstone d'identité sous le même verrou writer avant l'accusé de révocation local ; pour un caller legacy, ce tombstone d'identité ne crée pas d'instance cible ni de mapping Pod fictif. Rôles machine séparés : operator = read/lease/observe ; Lazaret = read/effets/revoke-identité ; aucun de ces rôles ne modifie activation, consentement ou `VALID`. Authentification mTLS de service + principal machine autorisé, pas d'endpoint public/bearer utilisateur de contrôle. Les méthodes de commande passent par le composition root et l'exécution de commandes du service ; pas de nest operator.

`ReadyBinding` devient un snapshot désiré versionné (`RuntimeBindingSnapshotV1`), non un filtre « seulement ready » : actifs, interdits et tombstones sont nécessaires. `DesiredStateSource::list_ready` est remplacé côté runtime par une lecture paginée de snapshots et un report CAS ; admission par release reste distincte. `PluginEndpointLocator` consomme une projection par projet/binding/génération/version, jamais Kubernetes ; aucun `resolve(digest)` de secours. D ne lit ni les tables ni les détails cluster de C directement.

Writer unique de l'intention = Manifesto ; writer des observations/ressources par binding = operator tenant un bail **distribué**, avec numéro de fence monotone alloué par le writer DB. CAS observation sur `(project, binding, generation, epoch, projection_version, writer_fence)` ; perte de bail/conflit = abandon, jamais dernier-writer-wins. Mutations de l'objet Serving existant via précondition UID/resourceVersion ; création uniquement si état courant actif et absence autorisée par le registre de propriété. Un échec/timeout de création n'autorise pas à adopter un objet de même nom : relire UID/owner chain, puis réconcilier ou STOP. Pas de double writer Flux/operator, pas de suppression des enfants Knative.

Distinguer cinq compteurs : génération **métier** (configuration/release), `metadata.generation` (objet API), **Revision UID** (template Knative), **grant revision** (consentement), **epoch/version de projection** (fencing/invalidation). Aucun n'est inféré d'un autre. 100 % du trafic du Service vise la seule Revision autorisée observée ; pendant une mise à jour sans correspondance exacte, pas de forwarding. Un nombre `observedGeneration` correct sans UID/version métier correspondants ne suffit pas.

Fraîcheur d'autorisation : **aucun cache allow** ; chaque admission d'invoke, enrollment/session et début d'effet consulte le writer courant. La projection opérationnelle/les enregistrements d'instance ont une validité maximale bornée par le profil B5 (valeur proposée là, non acquise). Autorité indisponible, clés inconnues, snapshot expiré, grant incertain ou version discordante = refus/indisponibilité bornée ; aucun stale-while-revalidate pour permettre. Le signal de retrait de Pod borne l'usage ultérieur de son instance, mais l'observation n'est pas une attestation continue d'exécution physique.

Désactivation/retrait : transaction writer ferme l'état, incrémente epoch/version et persiste un tombstone, avant tout nettoyage. Replays/anciennes observations ne peuvent réactiver une autorisation. **Limite distribuée explicite :** un apply déjà en vol peut laisser/créer un objet Serving résiduel à zéro ; le bail DB n'est pas une transaction atomique avec l'API cluster. Cela n'est jamais une réactivation métier ni une route autorisée ; C le détecte et le retire seulement avec UID prouvé. Aucune promesse « zéro objet après commit » ou fencing API fourni par une annotation seule. Si l'interdiction absolue de cette création transitoire est requise, retour A pour admission/fencing additionnel, pas une garantie inventée.

Migration : inventaire global digest→tous bindings/UID/consommateurs, tombstones/init de versions à partir du writer, mode `closed` par défaut pour chaque historique, objets distincts par binding. Le CR d'admission par release peut demeurer partagé ; ses chemins de suppression ne gèrent plus le runtime d'un binding. Aucun événement ancien n'ouvre un binding migré. Transition détaillée §15.

**Responsable :** C pour Manifesto, stockage, port/DTO partagés, bail/CAS et operator ; D consomme le port gelé. **Oracles :** writer redémarré, failover de bail, CAS perdu, apply retardé après fermeture, delete/recreate même nom UID différent, anciens cursors/events, panne writer/observation expirée, deux bindings même release ; aucune autorisation ressuscitée ni suppression croisée. Tests SQL réels pour atomicité/fencing, API réelle pour propriété ; mocks sortants seulement pour adapter HTTP, jamais preuve de confinement.

### B4 — Révocation linéarisée au début de chaque effet, pas au buffer

**Choix proposé, à ratifier :** le commit writer de désactivation/révocation/epoch est le point de linéarisation. Une admission d'invoke antérieure autorise seulement son **acheminement**, pas tous ses futurs effets. Après sortie du buffer, le plugin présente ticket + session mTLS de l'instance cible à `POST /runtime/accept` Lazaret. Vérifications : signature/hash/deadline, source encore autorisée, cible/instance/Revision/génération/release/epoch/grant revision encore courants. Une consommation durable CAS de l'identifiant d'autorisation ouvre un `execution_id` lié à cette instance ; deuxième consommation refusée. Le handler HTTP de référence attend cet accept avant travail, mais un plugin hostile peut l'ignorer : la garantie de sécurité porte sur ses I/O exclusivement via Lazaret.

Chaque effet d'une instance en mode runtime passe par la nouvelle route Lazaret `POST /runtime/effects/invoke`, DTO `RuntimeEffectRequestV1 { execution_id, effect_id, invoke }`. Lazaret applique les validations de capacité existantes et demande au writer Manifesto `POST /internal/apparatus/runtime/bindings/{binding_id}/effects/begin?project_id=…` ; réponse = réservation liée à l'exécution, empreinte de l'effet, epoch, grant revision et deadline. `POST …/effects/{effect_id}/complete` journalise résultat terminé/indéterminé, sans secret. La transaction begin prend le même verrou de binding que les mutations activation/consentement/epoch, recoupe le grant source→cible et l'identité cible, puis commit avant l'I/O. Les verrous source/cible et identités concernées ont un ordre stable ; la révocation d'identité et les changements de consentement passent par le même writer avant leur accusé, pas un simple cache éventuellement cohérent. Aucun autre endpoint capacité, y compris `/invoke` legacy, ne peut contourner ce passage pour une session runtime. Le registre impose ce mode côté serveur, pas un flag choisi par le plugin.

Ordre observable :

- Révocation commit **avant** begin-effect ⇒ effet refusé, même si invoke était dans Activator ou si le plugin tourne déjà. Une session/ticket valide cryptographiquement ne contourne pas epoch/grant courant.
- Begin-effect commit **avant** révocation ⇒ cet effet précis est engagé et peut terminer dans sa deadline ; aucun effet suivant n'est réservé. Le commit begin est la frontière d'engagement métier, pas la fin physique de l'I/O. Ce compromis est à accepter explicitement.
- Timeout/déconnexion/crash après réservation/envoi ⇒ résultat possiblement **indéterminé** ; pas de retry automatique de l'effet, pas de réservation réémise après expiration, pas d'exactly-once revendiqué. Une clé d'effet déjà vue ne permet pas de ré-exécuter une issue ambiguë. Le journal de réservations n'est pas une queue de travail.

Une demande révoquée **pendant Activator** peut encore réveiller un Pod ou atteindre son code : Knative ne fournit pas ici de retrait individuel de buffer. Elle ne peut plus ouvrir d'exécution/effet après le commit de révocation. On ne promet donc ni absence de CPU après révocation d'une demande déjà admise, ni annulation instantanée d'une I/O engagée. Si ces garanties plus fortes sont requises, cette cible est NO-GO et revient à A. « Non autorisé ne réveille pas » concerne la décision initiale d'admission Lazaret, pas une cancellation rétroactive imaginaire.

Drain proposé : fermer/fencer dans le writer, interdire nouveaux tickets/accept/begin, observer les réservations engagées jusqu'à leur deadline, fermer l'exposition et laisser les contrôleurs Serving terminer/retirer le workload selon leur lifecycle. Pas de queue/proxy de drain maison, pas de kill Pod par operator ; les appels HTTP sans effet engagé peuvent échouer. À l'échéance, journaliser les issues inconnues, invalider registre/credentials/ancienne Revision ; ne pas déclarer qu'un timeout a annulé l'effet. Nettoyer uniquement les ressources possédées, par précondition UID, jamais une release/Secret partagé. Les durées sont celles du profil B5 à ratifier.

**Responsables :** C pour sérialisation writer, journal et contrats begin/complete ; D pour accept/exécution/autorisation et tous les chemins I/O ; B pour absence d'egress alternatif et lifecycle Serving. **Oracles :** barrières contrôlées avant/après admission, attente Activator, accept et begin commit ; révocation de part et d'autre du commit ; absence d'effet nouveau prouvée sur KV/collaborateur, pas seulement HTTP refusé ; effet déjà engagé identifié séparément ; replay ticket/effet, ancienne instance et ancienne Revision refusés ; panne writer refuse, crash post-envoi n'entraîne pas de retry. Le durcissement de l'émission CA reste 0010 ouverte.

**Choix proposé :** un profil versionné unique, plateforme, sans override publisher et sans valeurs illimitées. Ce profil n'est pas un SLO production ni la clôture `APP-03/06`. Les mécanismes zéro des §§3/5 (KPA, min/initial zéro et permission globale correspondante) sont des exigences de cible déjà écrites ; les autres nombres ci-dessous sont **proposés, à ratifier individuellement**.

Résolution statique autorisée seulement au lot compétent ; validation de compatibilité réelle séparée en E. Double livraison ne donne pas deux accept d'un ticket/effet. Aucune de ces preuves n'est produite par ce document.

### B6 — HTTP fini et état externe ; retrait conserve les données

**Choix proposé, à ratifier :** éligibles uniquement les opérations HTTP finies, bornées par B5, qui tolèrent perte complète de mémoire/filesystem et peuvent reprendre après création d'une nouvelle instance. Pas de websocket/stream durable, daemon, tâche de fond indépendante de l'invoke, cron, affinité mémoire ou transaction ouverte entre deux requêtes. Une image qui l'exige reste non éligible au profil zéro : la rendre `min-scale>0` en cachette n'est pas une implémentation de 0012. La readiness ne lance ni migration ni opération métier et n'est pas un warm-up.

État métier persistant = KV/stockage plateforme externe déjà autorisé et scopé `(project, binding)` via Lazaret ; aucun stockage mutualisé par digest, volume hostPath, hibernation mémoire ou PVC ajouté implicitement. Le filesystem temporaire est borné/jetable ; pas de secret durable ni journal d'effet uniquement local. L'accusé de succès d'une opération exige la persistance prévue par sa capacité, pas une écriture en mémoire. Les effets sont engagés selon B4 ; aucune garantie transactionnelle inter-services ou exactly-once nouvelle. Le profil initial peut se limiter au plugin HTTP de référence KV : compatibilité de chaque autre release à qualifier, sans prétendre Factory/host livrés.

Migration de schéma métier : version de données externe distincte de génération/Revision ; aucune migration exécutée par chaque replica au startup. Fermer/fencer le binding, attendre les engagements admis, établir une sauvegarde/récupération prouvée et une migration exclusive par binding/génération avant ouverture ; privilégier une évolution additive compatible avec la release précédente. Une migration destructive/incompatible nécessite une décision humaine et un contrat de données séparés ; elle est hors GO de cette tranche. Les migrations SQL de **contrôle** B3/registre D sont additives : backfill fermé, aucun downgrade supprimant données/tombstones. Ne pas confondre migration de schéma contrôle et données utilisateur.

Secrets : seule la référence scoped/versionnée apparaît dans configuration, snapshot et événements. Résolution par la capacité Lazaret et la politique existante ; aucun credential externe durable monté/env qui ouvrirait une I/O hors gateway. Un secret plaintext déjà légitimement remis n'est pas « effacé » par un epoch : ne pas promettre cette propriété. Changement de référence/version ⇒ epoch/grant revision invalidés selon politique, génération si configuration template modifiée, ancienne instance refusée aux nouveaux effets ; pas d'appel de warm-up pour forcer la rotation. Rotation à zéro ne démarre aucun Pod. Ancienne référence conservée uniquement pour engagements admis et selon la politique du secret owner, puis invalidée sans suppression automatique du secret partagé. ### Rollback et restrictions résiduelles

Au premier échec d'autorité, mismatch génération/UID, perte de bail, compatibilité mTLS/sandbox, borne non prouvée ou bypass : **fermer/fencer le binding dans le writer, refuser les nouveaux tickets/accept/effets, conserver les preuves et données, drainer les seuls engagements déjà admis**. Un objet/Pod résiduel n'est pas réautorisé ; les contrôleurs standards gèrent sa terminaison. Ne pas remplacer cette fermeture par Flux suspend.

Rollback de code/config : revenir seulement à une version qui comprend le marqueur de fermeture/tombstones et refuse le runtime migré. Si le binaire précédent réactive le locator digest ou ignore les epochs, **ne pas le redéployer pour ce binding** : conserver le mode fermé/maintenance. Aucune réouverture automatique du partage digest, de HTTP clair, d'un dispatch local ou d'un profil sans sandbox. Rollback d'une release uniquement si schéma externe compatible et nouvelle génération/epoch explicitement approuvée ; jamais rollback SQL destructif ou réemploi d'identités anciennes. Perte de disponibilité assumée plutôt que fallback permissif.

Restrictions à accepter : caller workload vivant (pas premier appel browser autonome) ; requête anciennement autorisée pouvant encore réveiller du compute après révocation mais aucun nouvel effet admis ; effet réservé avant révocation pouvant finir/être indéterminé ; objets résiduels transitoires possibles lors d'apply en vol, sans résurrection d'autorisation ; pas d'exactly-once, purge, workload non HTTP ou coût système zéro ; pins et preuve gVisor/mesh non fournis par A, donc **aucune exposition hostile ni GO de publication sans ces verrous**.
