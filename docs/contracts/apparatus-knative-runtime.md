- Version : 1 — 2026-10-19 ; annexes décisionnelles B1–B6 complétées le 2026-10-20, ratifiées par Accept humain.
- Statut : Accepted le 2026-10-20 (Accept humain du paquet ; pins B5 reportés à un spike séparé) ; Réalité : Unimplemented
- Canon primaire : [ADR-0012](../adr/0012-apparatus-http-knative-par-binding.md), Accepté le 2026-10-20 ; Réalité Unimplemented jusqu’aux preuves de campagne.
- Base observée : `2760e02bc43f5149070aac6ace29f7c2d11f9aad`.
- Portée : contrat de cible et de preuves ; **pas un GO code/runtime**, pas le contrat complet de tous les cycles métier.

## 1. Frontières et invariants

La release OCI immuable est réutilisable ; l’installation est isolée par `(project_id, binding_id)`, jamais par digest seul. Binding = `ProjectComponent.id`. Les digests descripteur, enveloppe et image CRI gardent leurs rôles distincts (0002/0008) ; le kubelet utilise exclusivement l’image pinée issue d’une enveloppe admise. Activer/configurer un binding ne produit ni `VALID` ni `VERIFIED`.

Manifesto reste l’autorité métier (activation, génération, consentement/grant revision, révocation). Il n’obtient aucun client/token Kubernetes ; les gates zéro `k8s`/`kubernetes` sous ses `*/src` ne sont ni déplacées ni affaiblies. Adaptation Kubernetes dans `workers/apparatus-operator` ; Lazaret reste la seule frontière d’invoke/I/O. Aucun nouveau BC HTTP de contrôle, proxy/queue HTTP maison ou scheduler propriétaire.

Les identités privilégiées P4 restent séparées du plugin ; les SA internes Knative sont un TCB supplémentaire à inventorier, pas une justification de fusionner les quatre responsabilités existantes. Ni plugin ni publisher n’obtiennent de token API ou droit de créer des workloads. `automountServiceAccountToken: false` côté plugin ; RBAC minimal côté adaptateur.

## 2. Identités, générations et projection

Distinguer obligatoirement :

- **Release** : identité immuable de contenu descripteur 0002 ; peut être commune à plusieurs installations. Aucun nom de workload/route ne repose sur ce seul digest.
- **Binding** : installation projet × binding ; objet Serving stable distinct des autres bindings, y compris pour une même release. Nom Kubernetes déterministe dérivé de la clé complète, validé contre les collisions ; labels ne constituent pas une preuve d’autorité/propriété.
- **Génération métier** : version désirée, distincte de `metadata.generation` Kubernetes et de la Revision Knative. La projection conserve explicitement leurs correspondances ; une observation ancienne n’autorise pas une nouvelle génération.
- **Grant revision** : version de consentement/permissions, distincte de la génération ; une projection de route n’accorde jamais de droits par elle-même.
- **Instance** : identité d’une exécution/replica réelle, enregistrée par le chemin de confiance Lazaret. Ce n’est ni le digest, ni le binding, ni une identité fictive permanente recyclée après scale-to-zero. Relation instance ↔ Pod UID ↔ Revision ↔ binding/génération/release prouvée ; aucune identité d’instance partagée entre bindings/replicas.

Le modèle `WorkloadIdentity { instance, binding, release, generation, grant_revision }` est conservé ; ne pas réduire ses champs pour faire entrer un service virtuel Knative. Rotation/enrollment et invalidation reçoivent une proposition explicite en annexe B1 ; sa ratification et les preuves B2 restent requises avant code/publication.

Une projection interne de confiance vers Lazaret associe au minimum projet, binding, génération, release admise, grant revision, état logique, identité/UID de la ressource Serving et de sa Revision cible, endpoint privé et version de projection. Les DTO/port/API et migrations proposés sont inventoriés §13, non ratifiés. L'annexe B3 tranche source, writer, CAS/fencing et panne ; B5 propose la borne de fraîcheur et garde le verrou des pins ouvert. Aucun secret value ni token Kubernetes dans cette projection ; aucune URL fournie par le caller/publisher. Absence/ambiguïté/obsolescence = refus, jamais endpoint reconstruit par digest ni fallback silencieux vers le dispatch local.

## 3. Activation logique et ressource avant le premier appel

**Option retenue : pré-déclaration à zéro.** Après lecture authoritative de l’activation et vérification de la release `VALID`, l’adaptateur projette un `serving.knative.dev/v1 Service` privé par binding, son template plateforme et sa configuration. Aucune requête d’échauffement/smoke/probe applicative n’est émise pendant l’activation. Readiness probes du Pod au réveil ≠ autorisation métier.

Cette pré-déclaration ne demande ni Pod plugin ni nœud plugin. Les contrôleurs, ingress, Activator et services de sécurité/metadata partagés, eux, restent disponibles. Si la route n’est pas encore établie, l’invoke autorisé ne part pas vers une URL imaginaire : indisponibilité bornée, sans file métier maison. Un Knative Service/Revision déclaré `Ready` avec échelle initiale zéro ne prouve pas qu’un Pod tourne.

**Variante non retenue : provisionnement au premier usage.** Knative ne crée pas un Service inconnu en découvrant une URL. Cette variante demanderait un ensure métier idempotent, durable/fencé par binding+génération et une attente de route bornée, hors Manifesto ; elle ne permettrait ni réimplémentation d’Activator ni deuxième buffer HTTP. Elle exige un amendement du contrat et une motivation métier avant de remplacer la pré-déclaration.

## 4. Premier invoke, concurrence et attente

Ordre exigé : vérifier caller/autorité courante → activation/génération/release admise et grant revision → projection valide → envoyer à l’ingress privé Serving → Activator/KPA si zéro/capacité absente → queue-proxy → plugin Ready. L’Activator bufferise la demande et KPA demande des replicas ; à chaud, le chemin Knative peut éviter l’Activator. L’attente du résultat HTTP reste bornée ; pas de réponse produit `QUEUED`/`SCALING`, job asynchrone ou nouvel état public introduit implicitement.

**Constat à la base (B1) :** l’actuel `POST /invoke?project_id=…` vérifie une session de **workload**, impose `CallOrigin::Background`, puis autorise un grant vivant. Ce n’est pas une API générique end-user permettant déjà de réveiller une instance inexistante. Définir le caller et sa preuve valide avant réveil, sans dépendance circulaire au certificat/session du plugin dormant. Ne pas accepter un bearer IAM dans le plugin ni inventer une nouvelle route publique au cours du câblage. Si un nouveau contrat d’appel est nécessaire, le ratifier explicitement ; sinon démontrer le parcours avec les interfaces conservées. L’autorisation avant réveil reste assurée par Lazaret ; aucun sidecar d’autorisation n’est choisi ici.

Concurrence : un seul objet Serving logique courant par binding ; apply déterministe et idempotent pour `(project, binding, génération)`, writer unique et protection CAS/fencing inter-processus. Deux premiers appels ne créent ni deux installations, ni deux routes concurrentes ; ils utilisent le buffer natif Knative. Plusieurs replicas du **même** binding restent possibles dans les bornes autorisées, chacun avec son identité propre. Une génération dépassée, un apply retardé ou un événement rejoué ne recrée pas une installation désactivée/supprimée. Pas de lock mémoire présenté comme garantie distribuée.

L’idempotence de **provisionnement** ne vaut pas déduplication d’invokes. `operation_id` est conservé, mais aucune garantie exactly-once/déduplication métier n’est ajoutée sans contrat existant et preuve de persistance.

## 5. Configuration Serving portable et bornée

Socle : `serving.knative.dev/v1 Service` ; annotations du template de Revision : `autoscaling.knative.dev/class: kpa.autoscaling.knative.dev`, `autoscaling.knative.dev/min-scale: "0"`, `autoscaling.knative.dev/initial-scale: "0"`. Config Serving : `enable-scale-to-zero: "true"` et `allow-zero-initial-scale: "true"`. Vérifier ces clés et leur portée sur la version **épinglée** avant livraison. L’échelle initiale upstream vaut 1 par défaut : omettre ce réglage violerait « activation sans Pod ».

Le profil plateforme doit fixer et tester :

- `autoscaling.knative.dev/max-scale` **strictement positif** (0 signifie illimité upstream), plafond global `max-scale-limit` approprié ; pas seulement une borne par Revision présentée comme budget total du binding lorsque plusieurs Revisions coexistent ;
- `containerConcurrency` strictement positif et cible KPA/concurrence cohérente, taille de requête et nombre d’attentes admissibles bornés ;
- requests/limits CPU/mémoire et quotas de namespace/binding ; limites prises dans une politique plateforme approuvée, pas celles demandées arbitrairement par le publisher ;
- `timeoutSeconds` de Revision et délais ingress, Activator/queue-proxy, client HTTP Lazaret et appelant ; deadline de bout en bout cohérente et non prolongée indéfiniment par des retries ;
- fenêtres d’inactivité/rétention/scale-to-zero Knative documentées ; aucun cron de suppression/recréation Pod pour reproduire KPA ;
- traffic ciblant uniquement la Revision de génération/release autorisée, sans tag/route vers une ancienne Revision contournant révocation ou migration.

Aucun chiffre de capacité ni SLO n’est ratifié par ce fichier. B5 propose explicitement des valeurs à ratifier ; pins/digests exacts manquent encore et bloquent la publication. Profil sans lock ni bornes approuvés = non déployable. Ne pas installer HPA/KEDA contrôlant le même workload ni laisser l’ancien operator écrire/supprimer les Pods Knative. Les enfants (Revision, Deployment, ReplicaSet, Pod, Service réseau) sont gérés par leurs contrôleurs standards.

Helm : packaging de la pile tierce et éventuellement rendu contrôlé, **pas** control loop. Préférence projection métier en manifests/Kustomize ; pas de chart arbitraire publisher, CRD/RBAC/hostPath/privileged/hostNetwork/hooks libres. Flux peut réconcilier la pile et ses paramètres ; aucun double writer Flux/adaptateur sur les mêmes champs des Services par binding. Suspendre Flux/HelmRelease ne supprime ni n’arrête les workloads. B2 propose net-istio/Istio, dépendance supplémentaire à ratifier et à qualifier ; pins/compatibilité restent un verrou B5 ; le site Knative consulté en `release-1.23` n’est pas le pin de livraison.

## 6. Autorisation, révocation et réseau

- Toute demande non autorisée est refusée **avant** provisionnement/réveil/forwarding ; session cryptographiquement valide ou état Serving Ready ne suffisent jamais. Relecture authoritative des droits selon 0004/0007, y compris génération/grant revision. Readiness observée = information opérationnelle, pas permission.
- Ingress/route cluster-local : aucun accès public alternatif au plugin. « Cluster-local » seul ne bloque pas les autres workloads du cluster. Interdire les accès directs aux endpoints de Revision, Services/Pods, ports user-container et URLs taguées ; laisser seulement les chemins plateforme nécessaires, avec authentification démontrée. DNS obscur ou URL non publiée n’est pas une barrière.
- Policies et preuves doivent couvrir Lazaret → ingress/Activator → queue-proxy → plugin, trafic de contrôle/probes strictement nécessaires, et plugin → Lazaret pour capacités ; default deny et interdiction Transit/système maintenues. Ne pas simplement autoriser tout `knative-serving`/tout namespace plugins : distinguer ingress, activator, controllers et code auteur. Egress/DNS et mécanisme d’authentification évalués avec le dataplane choisi.
- **Bloquant B2 :** Knative n’atteste pas l’identité Lazaret et ne transporte pas magiquement son mTLS. Établir chaque terminaison TLS, pair certifié, validation de binding/génération/instance et résistance aux headers forgés. La politique doit marcher au réveil **et** sur le chemin chaud direct sans Activator. Si le transit impose de modifier le modèle de confiance ou les contrats, amender la décision avant code ; ne pas ajouter discrètement un proxy métier.
- Révocation/désactivation : refus immédiat des **nouvelles autorisations**, invalidation/fencing de la projection et des anciens epochs/identités ; ne pas attendre le ticker, le scale-to-zero ou Flux suspend pour fermer l’accès. Admission révoquée et autorisation de binding sont deux décisions distinctes.
- **Bloquant B4 :** une requête admise par Lazaret puis bufferisée par Activator peut être révoquée pendant l’attente. Spécifier la linéarisation/validation avant effet, le sort des requêtes déjà transmises, le drain et la portée d’une annulation. Une relecture à Lazaret avant envoi ne prouve pas une révocation pendant le buffer. Ne promettre ni arrêt instantané d’un effet en cours ni admission après révocation. Déterminer et prouver le mécanisme sans queue/proxy maison ; pas de révocation globale déclarée livrée.

## 7. État, repos, retrait et propriété

Séparer état **logique** du binding, état **observé** Serving et exécutions effectives. Binding actif + Service à zéro = dormant et invocable, pas nécessairement erreur/pending ; Pod Ready ne réactive pas un binding interdit. La sémantique des états/événements publics Manifesto actuels reste conservée jusqu’à décision explicite. Un nouveau vocabulaire interne n’est pas un nouvel event déjà accepté.

Scale-to-zero retire les Pods, **pas** le binding, l’artefact admis, les références de secrets ni le KV plateforme. Tout état uniquement en mémoire ou filesystem éphémère doit pouvoir disparaître. Pas d’hibernation mémoire ni de PVC implicite. Compatibilité d’un plugin HTTP avec ce modèle, durée des requêtes/streams, tâches de fond et éventuelle migration de données sont à qualifier (B6).

Retrait minimal sûr : fermer les nouvelles autorisations et fencer la génération, retirer l’exposition/projection, puis traiter les requêtes en cours et l’objet Serving selon la politique de drain à ratifier. L’ordre doit résister aux replays et à la recréation d’un objet de même nom. Conservation/purge des données, délais et destruction irréversible ne sont **pas** décidés ; aucun uninstall global des releases/Secrets/PVC partagés à partir d’un seul binding. Retirer un binding ne révoque pas une release pour les autres projets.

Propriété : enregistrer UID effectivement créé/observé, owner chain, namespace, génération et rôle du writer. Vérifier les UID et utiliser des préconditions de suppression ; conflit/propriété inconnue = stop, pas adoption ni `force`. `ownerReferences` seulement valides pour les scopes Kubernetes, jamais vers un UUID SQL Manifesto ou une ressource d’un autre namespace. Le contrôleur ne supprime pas lui-même les enfants Knative ; ses propres objets doivent avoir une généalogie vérifiable. Nom, digest, label ou field manager seuls ne prouvent pas la propriété.

Secrets : références scopées binding et politique plateforme (OpenBao/Secret approuvé), **jamais valeurs** dans artefact, labels, projection, events ou logs. Un secret projet n’est pas mutualisé par digest. Rotation, invalidation et nettoyage ne doivent ni réveiller un plugin à son insu ni effacer un secret utilisé ailleurs ; modalités exactes à fixer avec B6.

## 8. Cold-start et défaillances

Image pull, scheduling sans capacité, révision invalide, absence d’ingress, erreur de readiness, projection périmée et échec de service d’autorité doivent produire une issue bornée et observable, fail-closed. Saturation et deadline épuisée ne déclenchent ni file durable maison ni attente infinie. Pas de nouveau code HTTP/DTO introduit sans examen de `InvokeHttpError` et du contrat actuel ; fixer le mapping exact en B5. Échec opérationnel ≠ refus d’autorisation dans les preuves.

Lazaret n’ajoute pas de retry automatique d’opération non idempotente après envoi ambigu. Inspecter aussi les retries ingress/Activator/queue-proxy de la version choisie : la chaîne complète doit être compatible avec les garanties métier. Timeout/déconnexion client ne prouve pas que l’opération n’a pas eu lieu. Un retry client peut produire un doublon ; conserver `operation_id` ne suffit pas à promettre le contraire. La politique pour ces ambiguïtés reste explicite et testée ; pas de garantie exactly-once.

## 9. Surfaces, migration et hors scope

Surfaces attendues, **sans autorisation de changer leur contrat public implicitement** :

- `workers/apparatus-operator/src/{controller,desired_state}.rs` : fin de la clé digest pour le runtime, projection binding/génération, contrôle de propriété, observation Serving ; admission/Jobs inchangés. `ReadyBinding` actuel ne porte pas les versions nécessaires : décider projection/transport avant de modifier ce trait/DTO.
- `services/Lazaret/application/src/invoke.rs` : locator bindé et attente HTTP bornée ; `PluginEndpointLocator` n’appelle pas Kubernetes. `identity.rs`, grants et enrollment : préserver leur autorité et claims, démontrer le cycle d’instance.
- Projections métier depuis Manifesto : conserver routes `/components`, routes Lazaret, `crates/manifesto-events`, `crates/apparatus-contracts/src/{protocol,ports}.rs` tant qu’aucun amendement ratifié ne les change ; ne pas fabriquer un event de démarrage/arrêt requis par Knative.
- `ops/deploy/p4/` et pile système : installation/pins Serving/ingress, policies, SA, profils, placement. Aucun changement du monolithe/Compose, du framework ou de CI demandé par ce contrat.

Plan de migration à arrêter avant activation : inventaire CR/Pods/Services historiques par digest et bindings concernés ; nouvel objet par binding avec mapping explicite ; double contrôle/traffic interdit ; couper l’ancien endpoint digest avant ouverture du nouveau chemin ; retrait uniquement des objets prouvés possédés, jamais suppression partagée depuis la réconciliation d’un seul binding. Préserver les données. Rollback fail-closed qui ne restaure pas silencieusement le partage inter-projets. Migrations de contrôle additives explicitement proposées en B3/§13 ; migrations destructives de données hors scope B6, jamais implicites.

L’actuel `apply_valid_record` peut supprimer un CR par digest et `reconcile_object` supprimer un Pod : ces chemins ne doivent jamais agir sur les objets partagés historiques au nom d’un seul binding, ni sur les enfants Serving. Le locator digest de Lazaret et le gold path 0605 sont des preuves historiques/locales, pas le routage cible.

Hors scope : Factory auteur/host P5/P6, runtime non HTTP, coût zéro global, cloud bootstrap/ratification 0600, autoscaler nœuds/predictif, nouveau service de contrôle, partage explicite inter-bindings. Pools système/plugins distincts ; nœuds plugins mutualisés, pas un nœud par binding. Le pool système et la plateforme partagée restent actifs ; choix/provider et minimum de nœuds sont séparés. Partage de noyau ≠ sandbox forte : pas d’exposition de code non fiable sans profil de confiance/isolation qualifié.

## 10. Blocages avant GO implémentation

- **B1 — caller du réveil et cycle d’identité.** Parcours sans session de plugin déjà vivant ; relation instance/Pod/Revision et enrollment au réveil, sans modifier silencieusement les claims ni accepter un bearer IAM dans le plugin.
- **B2 — transport et isolation.** Ingress/pins retenus, preuve mTLS/identité et anti-contournement à froid/chaud ; compatibilité NetworkPolicy/queue-proxy/probes ; sandbox gVisor/Kata ou autre, ou restriction de confiance documentée. Aucun de ces profils n’est présenté livré.
- **B3 — projection/générations.** Source/writer/CAS/fencing et durée de validité, autorité pour désactivation/retrait, évolution éventuelle de `ReadyBinding`/trait/transport et migration des objets par digest. Aucun event/HTTP/trait changé sans inventaire et décision correspondante.
- **B4 — révocation, buffer et drain.** Sémantique d’une requête déjà acceptée, preuve avant effet, invalidation des vieilles instances/Revisions et politique de retrait. Choix métier requis, pas une capacité implicite de Knative.
- **B5 — profil opératoire borné.** Versions Serving/ingress épinglées et compatibilité, valeurs capacité/concurrence/ressources/deadlines/idle, cohérence des retries et mapping HTTP existant ; rien d’illimité/non documenté accepté.
- **B6 — état et cycle métier.** Contrat HTTP réellement éligible au retour à zéro, stockage externe/persistance et migrations éventuelles, rotation/rétention/retrait des références de secrets ; aucun cycle complet de désinstallation inventé.

Les annexes §12 proposent ces décisions ; la lead doit faire ratifier l'ensemble, y compris restrictions/ownership et profil/lock B5, avant de transformer ce document en ordre de codage. Les pins exacts ne sont pas fournis par A : ce verrou reste explicitement NON LEVÉ. Un spike technique peut documenter une compatibilité mais ne ferme ni blocage métier, ni gate pré-prod par lui-même. Le lot présent n’autorise aucun spike/runtime.

## 12. Annexes décisionnelles B1–B6 — propositions du lot A

Les choix suivants complètent la v1 ; **ratifiés par l'Accept humain du 2026-10-20** — les valeurs tiennent comme choix de conception, pas des SLO mesurés, et les mentions « à ratifier » ci-dessous se lisent « ratifié le 2026-10-20, sauf pins exacts » (spike séparé, condition d'entrée de B). Le Statut/Réalité de 0012 reste inchangé par ces choix (Accepted / Unimplemented). Une restriction explicitement indiquée est un choix de périmètre accepté, pas un trou à combler librement pendant le code. Les compatibilités non démontrées restent des gates techniques.

### B1 — Caller vivant distinct de la cible dormante ; enrollment par instance

**Choix proposé.** Le premier caller de cette tranche est un **workload déjà vivant et enrôlé auprès de Lazaret**, distinct de la cible dormante. Il présente son certificat mTLS et sa session workload courante ; `CallOrigin::Background` reste requis. L'activation administrative n'accorde pas ce droit au caller. Pas de session fictive de la cible, pas de certificat permanent par Service, pas d'end-user/browser ni de host P5/P6 inventé. Cette restriction workload→plugin est à ratifier ; si le produit exige un premier appel utilisateur sans workload caller, **retour A**, pas ajout d'un bearer au plugin.

Nouvelle route Lazaret proposée, relative au préfixe de service : `POST /runtime/invoke?project_id=…`. `RuntimeInvokeRequestV1` contient `target_binding_id`, `expected_generation`, `operation_id`, opération et payload bornés ; le projet vient de la query, jamais d'une URL de destination fournie par le caller. La session identifie uniquement la **source**. Lazaret consulte l'autorité pour source, cible, génération, consentements et politique de la capacité proposée `runtime.invoke` ; ACL ∩ consentement ∩ politique reste la règle. Le grant de cible n'est pas déduit du droit de l'admin, d'un droit du seul caller ou du digest commun. `/invoke` existant garde son DTO et sa sémantique ; les bindings migrés ne peuvent plus y joindre un endpoint digest. Pas de nouveau type OpenFGA implicite.

Après autorisation courante, Lazaret signe un `RuntimeInvocationTicketV1` (JWS, clé dédiée au purpose invoke) : version, issuer/audience, identifiant d'autorisation non réutilisable, source, projet/cible, génération, release, grant revision, epoch de révocation, `operation_id`, hash canonique de l'opération/payload, date d'émission/expiration et deadline (jamais au-delà de la validité de la preuve caller). Aucune identité d'instance cible n'y est inventée avant réveil. Le ticket accompagne **la requête elle-même**, pas une nouvelle file ; il n'est ni bearer IAM ni permission autonome d'effectuer une I/O. Sa consommation est définie en B4.

**Enrollment proposé :** l'operator observe dès sa création (sans attendre Ready, pour éviter une boucle enrollment/readiness) un Pod réellement possédé par la chaîne Revision→Deployment→ReplicaSet→Pod, puis enregistre via B3 son UID, namespace, ServiceAccount, Revision UID, binding, génération et release. Le Pod génère sa clé privée en mémoire et adresse CSR + preuve à `POST /runtime/enroll` Lazaret. La preuve est un jeton projeté, lié au Pod UID, audience enrollment dédiée ; `automountServiceAccountToken=false`, aucun jeton audience API cluster ni token par défaut monté. Lazaret vérifie signature/issuer/audience/expiration via clés OIDC de confiance configurées, **sans client Kubernetes**, et recoupe les claims Pod/SA/namespace avec l'enregistrement courant authoritative. Une preuve fournie sans correspondance, un UID supprimé ou une Revision ancienne sont refusés. Validation offline du jeton seule ne prouve pas la présence courante du Pod.

L'operator réserve un nouvel `instance_id` dans l'enregistrement authoritative du Pod ; seul l'enrollment Lazaret active ses credentials. Le certificat est lié à CSR + instance, avec unicité par instance/Pod UID, pas unicité globale du binding empêchant les replicas. La clé reste dans le Pod ; la preuve projetée n'est pas loggée. `/session` peut émettre une session pour cette instance après les mêmes vérifications. `WorkloadIdentity` et `SessionClaims` existants conservent leurs champs ; epoch/UID/Revision sont liés côté registre, pas ajoutés silencieusement à leurs claims. Réveil après zéro = nouveau Pod UID/nouvelle instance, anciennes entrées clôturées ; rotation cert/session ne réactive jamais une ancienne entrée. La modalité CA de 0010 n'est pas décidée par ce choix ; aucune fourniture de clé privée à Lazaret n'est introduite.

**Responsables/surfaces :** D : caller, ticket, enrollment/registre/session ; C : attestation observée Pod/Revision et autorité B3 ; B : preuve projetée et clés publiques de confiance. Fichiers attribués §14. **Oracles :** source vivante→cible à zéro sans session cible ; requête sans droit refusée avant forward ; faux UID/SA/Revision, preuve rejouée après retrait et substitution de CSR refusés ; deux replicas = deux instances ; deux bindings de même release sans identité partagée ; nouveau réveil avec ancienne session refusée. La délivrance enrollment est idempotente sur preuve+empreinte CSR, jamais transfert d'une identité sur un autre Pod.

### B2 — Ingress net-istio privé ; mTLS hop-by-hop et délégation signée

**Choix proposé, à ratifier :** un seul ingress Serving **net-istio**, gateway interne uniquement, avec transport Istio/Envoy standard en mTLS strict ; pas de Kourier en parallèle ni de proxy métier supplémentaire. Le sidecar standard de transport n'est **pas** un sidecar d'autorisation métier ; l'autorisation pré-réveil reste Lazaret. Cette dépendance mesh supplémentaire est un delta structurant explicite de 0012, pas une prétendue réutilisation déjà livrée du mesh actuel. Si son intégration n'est pas retenue ou compatible, retour A ; aucune rétrogradation silencieuse vers HTTP clair/headers de confiance. Version/digests et compatibilité sont soumis au verrou B5.

Pairs à configurer et prouver : Lazaret→gateway interne ; gateway→Activator puis Activator→queue-proxy à froid ; gateway→queue-proxy à chaud. Chaque terminaison Envoy vérifie certificat, trust domain et identité du **pair immédiat**, avec policies distinguant les ServiceAccounts de gateway, Activator et Lazaret. Les connexions proxy→conteneur au sein d'un Pod constituent un segment local de la même frontière sandbox, pas un mTLS bout en bout au plugin. À chaud l'identité du pair peut changer, jamais le besoin de validation du ticket signé. Les clés de transport ne sont pas des certificats d'instance B1 ; aucun certificat/header ne prouve à lui seul le consentement métier.

L'ingress externe refuse ces routes ; l'ingress privé n'accepte que le principal Lazaret autorisé. Nettoyer/refuser les headers entrants réservés d'identité, de routage interne et d'enrollment ; les headers de certificat ne sont admis que depuis une terminaison authentifiée qui les réécrit. Le header `Apparatus-Invocation` transporte un ticket JWS vérifiable dont hash, cible et deadline sont contrôlés avant tout effet via B4. Un `Host`, `Forwarded`, `X-Forwarded-Client-Cert`, `K-*` ou header Apparatus forgé ne doit ni choisir une autre Revision/binding ni conférer de droit. Le ticket ne remplace pas la restriction réseau : un accès direct autorisé par erreur pourrait déjà réveiller du compute.

Default-deny ingress/egress plugins ; autoriser seulement le chemin standard authentifié jusqu'au port queue-proxy, plugin→Lazaret pour enrollment/session/capacités, résolution DNS et contrôle de transport strictement requis. Pas de plugin→plugin/Transit/API cluster/Internet ni de permissions générales par namespace `knative-serving`. Restreindre ports admin/metrics, endpoints Pod/Service directs et URLs taguées ; aucun tag de trafic applicatif publié. Les probes kubelet/queue-proxy et metrics KPA utilisent leurs ports/paths de contrôle, jamais un handler métier et jamais un ticket d'invoke ; leurs exceptions ne doivent pas ouvrir le port applicatif. Une NetworkPolicy seule ne distingue pas les conteneurs du même Pod ni ne prouve l'identité mTLS.

**Sandbox cible proposée : gVisor (`runsc`) via RuntimeClass plateforme**, tout le Pod plugin (user-container, queue-proxy et transport) dans ce profil, sans privilèges/hostNetwork/hostPath, capacités minimales, filesystem en lecture seule hors volumes éphémères bornés. Pool plugins séparé du pool système, nœuds mutualisés. Compatibilité de queue-proxy, injection/probes, démarrage/départ des sidecars et montée depuis zéro **non démontrée ici**. Tant que ces preuves ou le pin RuntimeClass/runtime manquent : aucune exposition de code hostile ; un éventuel spike sur image de référence contrôlée requiert un accord séparé, n'est pas une qualification sécurité. Ne pas présenter le partage de noyau runc comme solution de repli conforme.

**Responsable :** B pour pins, mesh, policies, probes et sandbox ; D pour vérification des tickets/frontière Lazaret ; C pour template Serving ne permettant pas d'override publisher. **Oracles :** matrice cold/hot avec principal permis fonctionnel et canary disponible, autre binding/principal refusé au hop identifié ; falsification de tous les headers réservés ; accès direct Pod/Service/Revision/tag et egress interdits ; probes/metrics fonctionnent sans exécuter d'opération ; nouveau réveil et extinction complète du Pod y compris sidecars. Un DNS cassé, un Pod absent ou une simple capture de configuration ne valent pas preuve de confinement.

### B3 — Autorité transactionnelle Manifesto ; observation non autorisante

**Choix proposé, à ratifier :** source métier = writer PostgreSQL Manifesto ; pas de lecture replica/cache pour une décision allow. C expose un **port métier interne** et son adapter HTTP protégé, sans dépendance cluster dans Manifesto. Operator et Lazaret n'ont pas d'accès SQL direct à sa base. Les événements existants peuvent accélérer une réconciliation, jamais rendre une projection authoritative ni porter une autorisation. Aucun nouveau topic/event `Started/Stopped/Ready` n'est requis.

Schéma additif proposé : `apparatus_runtime_bindings` (clé projet/binding, génération métier existante, grant revision, release admise, état, epoch de révocation, version monotone, profil), `apparatus_runtime_observations` (Service UID, génération observée, Revision UID, endpoint interne contrôlé, fence writer, version et date d'observation), `apparatus_runtime_instances` (mapping B1 et état d'instance), `apparatus_runtime_effects` (réservations B4). Contraintes de clé/monotonie et tombstones durables ; aucune autorisation dans un simple label ou nom DNS. Pas de génération métier concurrente : utiliser la génération Apparatus existante, et mettre à jour epoch/version dans la transaction de changement métier/consentement.

Transport proposé, chemins relatifs au préfixe Manifesto : `GET /internal/apparatus/runtime/bindings` (pagination/cursor), `GET /internal/apparatus/runtime/bindings/{binding_id}?project_id=…` (snapshot writer), `POST …/bindings/{binding_id}/writer-lease`, `PUT …/bindings/{binding_id}/observation`, `PUT …/bindings/{binding_id}/instances/{instance_id}` ; `project_id` est obligatoire et recoupé à chaque chemin. Commande additionnelle explicite : `POST …/bindings/{binding_id}/instances/{instance_id}/revoke`, permise à Lazaret pour fermer/fencer une identité, jamais pour activer un binding. Elle persiste un tombstone d'identité sous le même verrou writer avant l'accusé de révocation local ; pour un caller legacy, ce tombstone d'identité ne crée pas d'instance cible ni de mapping Pod fictif. Rôles machine séparés : operator = read/lease/observe ; Lazaret = read/effets/revoke-identité ; aucun de ces rôles ne modifie activation, consentement ou `VALID`. Authentification mTLS de service + principal machine autorisé, pas d'endpoint public/bearer utilisateur de contrôle. Les méthodes de commande passent par le composition root et l'exécution de commandes du service ; pas de nest operator.

`ReadyBinding` devient un snapshot désiré versionné (`RuntimeBindingSnapshotV1`), non un filtre « seulement ready » : actifs, interdits et tombstones sont nécessaires. `DesiredStateSource::list_ready` est remplacé côté runtime par une lecture paginée de snapshots et un report CAS ; admission par release reste distincte. `PluginEndpointLocator` consomme une projection par projet/binding/génération/version, jamais Kubernetes ; aucun `resolve(digest)` de secours. D ne lit ni les tables ni les détails cluster de C directement.

Writer unique de l'intention = Manifesto ; writer des observations/ressources par binding = operator tenant un bail **distribué**, avec numéro de fence monotone alloué par le writer DB. CAS observation sur `(project, binding, generation, epoch, projection_version, writer_fence)` ; perte de bail/conflit = abandon, jamais dernier-writer-wins. Mutations de l'objet Serving existant via précondition UID/resourceVersion ; création uniquement si état courant actif et absence autorisée par le registre de propriété. Un échec/timeout de création n'autorise pas à adopter un objet de même nom : relire UID/owner chain, puis réconcilier ou STOP. Pas de double writer Flux/operator, pas de suppression des enfants Knative.

Distinguer cinq compteurs : génération **métier** (configuration/release), `metadata.generation` (objet API), **Revision UID** (template Knative), **grant revision** (consentement), **epoch/version de projection** (fencing/invalidation). Aucun n'est inféré d'un autre. 100 % du trafic du Service vise la seule Revision autorisée observée ; pendant une mise à jour sans correspondance exacte, pas de forwarding. Un nombre `observedGeneration` correct sans UID/version métier correspondants ne suffit pas.

Fraîcheur d'autorisation : **aucun cache allow** ; chaque admission d'invoke, enrollment/session et début d'effet consulte le writer courant. La projection opérationnelle/les enregistrements d'instance ont une validité maximale bornée par le profil B5 (valeur proposée là, non acquise). Autorité indisponible, clés inconnues, snapshot expiré, grant incertain ou version discordante = refus/indisponibilité bornée ; aucun stale-while-revalidate pour permettre. Le signal de retrait de Pod borne l'usage ultérieur de son instance, mais l'observation n'est pas une attestation continue d'exécution physique.

Désactivation/retrait : transaction writer ferme l'état, incrémente epoch/version et persiste un tombstone, avant tout nettoyage. Replays/anciennes observations ne peuvent réactiver une autorisation. **Limite distribuée explicite :** un apply déjà en vol peut laisser/créer un objet Serving résiduel à zéro ; le bail DB n'est pas une transaction atomique avec l'API cluster. Cela n'est jamais une réactivation métier ni une route autorisée ; C le détecte et le retire seulement avec UID prouvé. Aucune promesse « zéro objet après commit » ou fencing API fourni par une annotation seule. Si l'interdiction absolue de cette création transitoire est requise, retour A pour admission/fencing additionnel, pas une garantie inventée.

Migration : inventaire global digest→tous bindings/UID/consommateurs, tombstones/init de versions à partir du writer, mode `closed` par défaut pour chaque historique, objets distincts par binding. Le CR d'admission par release peut demeurer partagé ; ses chemins de suppression ne gèrent plus le runtime d'un binding. Aucun événement ancien n'ouvre un binding migré. Transition détaillée §15.

**Responsable :** C pour Manifesto, stockage, port/DTO partagés, bail/CAS et operator ; D consomme le port gelé. **Oracles :** writer redémarré, failover de bail, CAS perdu, apply retardé après fermeture, delete/recreate même nom UID différent, anciens cursors/events, panne writer/observation expirée, deux bindings même release ; aucune autorisation ressuscitée ni suppression croisée. Tests SQL réels pour atomicité/fencing, API réelle pour propriété ; mocks sortants seulement pour adapter HTTP, jamais preuve de confinement.

### B4 — Révocation linéarisée au début de chaque effet, pas au buffer

**Choix proposé, à ratifier :** le commit writer de désactivation/révocation/epoch est le point de linéarisation. Une admission d'invoke antérieure autorise seulement son **acheminement**, pas tous ses futurs effets. Après sortie du buffer, le plugin présente ticket + session mTLS de l'instance cible à `POST /runtime/accept` Lazaret. Vérifications : signature/hash/deadline, source encore autorisée, cible/instance/Revision/génération/release/epoch/grant revision encore courants. Une consommation durable CAS de l'identifiant d'autorisation ouvre un `execution_id` lié à cette instance ; deuxième consommation refusée. Le handler HTTP de référence attend cet accept avant travail, mais un plugin hostile peut l'ignorer : la garantie de sécurité porte sur ses I/O exclusivement via Lazaret.

Chaque effet d'une instance en mode runtime passe par la nouvelle route Lazaret `POST /runtime/effects/invoke`, DTO `RuntimeEffectRequestV1 { execution_id, effect_id, invoke }`. Lazaret applique les validations de capacité existantes et demande au writer Manifesto `POST /internal/apparatus/runtime/bindings/{binding_id}/effects/begin?project_id=…` ; réponse = réservation liée à l'exécution, empreinte de l'effet, epoch, grant revision et deadline. `POST …/effects/{effect_id}/complete` journalise résultat terminé/indéterminé, sans secret. La transaction begin prend le même verrou de binding que les mutations activation/consentement/epoch, recoupe le grant source→cible et l'identité cible, puis commit avant l'I/O. Les verrous source/cible et identités concernées ont un ordre stable ; la révocation d'identité et les changements de consentement passent par le même writer avant leur accusé, pas un simple cache éventuellement cohérent. Aucun autre endpoint capacité, y compris `/invoke` legacy, ne peut contourner ce passage pour une session runtime. Le registre impose ce mode côté serveur, pas un flag choisi par le plugin.

Ordre observable :

- Révocation commit **avant** begin-effect ⇒ effet refusé, même si invoke était dans Activator ou si le plugin tourne déjà. Une session/ticket valide cryptographiquement ne contourne pas epoch/grant courant.
- Begin-effect commit **avant** révocation ⇒ cet effet précis est engagé et peut terminer dans sa deadline ; aucun effet suivant n'est réservé. Le commit begin est la frontière d'engagement métier, pas la fin physique de l'I/O. Ce compromis est à accepter explicitement.
- Timeout/déconnexion/crash après réservation/envoi ⇒ résultat possiblement **indéterminé** ; pas de retry automatique de l'effet, pas de réservation réémise après expiration, pas d'exactly-once revendiqué. Une clé d'effet déjà vue ne permet pas de ré-exécuter une issue ambiguë. Le journal de réservations n'est pas une queue de travail.

Une demande révoquée **pendant Activator** peut encore réveiller un Pod ou atteindre son code : Knative ne fournit pas ici de retrait individuel de buffer. Elle ne peut plus ouvrir d'exécution/effet après le commit de révocation. On ne promet donc ni absence de CPU après révocation d'une demande déjà admise, ni annulation instantanée d'une I/O engagée. Si ces garanties plus fortes sont requises, cette cible est NO-GO et revient à A. « Non autorisé ne réveille pas » concerne la décision initiale d'admission Lazaret, pas une cancellation rétroactive imaginaire.

Drain proposé : fermer/fencer dans le writer, interdire nouveaux tickets/accept/begin, observer les réservations engagées jusqu'à leur deadline, fermer l'exposition et laisser les contrôleurs Serving terminer/retirer le workload selon leur lifecycle. Pas de queue/proxy de drain maison, pas de kill Pod par operator ; les appels HTTP sans effet engagé peuvent échouer. À l'échéance, journaliser les issues inconnues, invalider registre/credentials/ancienne Revision ; ne pas déclarer qu'un timeout a annulé l'effet. Nettoyer uniquement les ressources possédées, par précondition UID, jamais une release/Secret partagé. Les durées sont celles du profil B5 à ratifier.

**Responsables :** C pour sérialisation writer, journal et contrats begin/complete ; D pour accept/exécution/autorisation et tous les chemins I/O ; B pour absence d'egress alternatif et lifecycle Serving. **Oracles :** barrières contrôlées avant/après admission, attente Activator, accept et begin commit ; révocation de part et d'autre du commit ; absence d'effet nouveau prouvée sur KV/collaborateur, pas seulement HTTP refusé ; effet déjà engagé identifié séparément ; replay ticket/effet, ancienne instance et ancienne Revision refusés ; panne writer refuse, crash post-envoi n'entraîne pas de retry. Le durcissement de l'émission CA reste 0010 ouverte.

### B5 — Profil local de référence borné ; pins restent un verrou bloquant

**Choix proposé :** un profil versionné unique, plateforme, sans override publisher et sans valeurs illimitées. Ce profil n'est pas un SLO production ni la clôture `APP-03/06`. Les mécanismes zéro des §§3/5 (KPA, min/initial zéro et permission globale correspondante) sont des exigences de cible déjà écrites ; les autres nombres ci-dessous sont **proposés, à ratifier individuellement**.

**Pins : gate NON LEVÉE.** Le corpus transmis donne un site documentaire `release-1.23`, pas des artefacts vérifiés. Ne pas inventer un numéro de patch/digest ou déclarer Serving/net-istio/Istio/gVisor compatibles. B doit fournir, avant publication de ses manifests et avant C/D, `ops/deploy/p4/knative/versions.lock.yaml` : version exacte + source + SHA256 des manifests, digests de toutes images Serving (dont Activator/autoscaler/controller/webhook/queue-proxy), net-istio, Istio/Envoy, runtime gVisor/runsc et RuntimeClass, ainsi que la matrice Kubernetes/Calico/containerd du lab approuvé. Pin de toute dépendance transitive et SBOM/avis de sécurité à consigner. Le runtime node utilise une version/artéfact vérifié, pas un faux digest OCI si ce n'est pas une image. Résolution statique autorisée seulement au lot compétent ; validation de compatibilité réelle séparée en E. A ne dispose pas ici de cette preuve : **Accept de principe possible, GO publication B/C/D impossible tant que ce verrou n'est pas ratifié**. Aucun nouveau téléchargement/installation effectué par A.

Valeurs du profil local de référence proposées :

Au plus `1` Revision recevant le trafic (**à ratifier**) et `1` ancienne en drain (**à ratifier**), donc plafond cumulé `4` Pods/binding (**à ratifier**), pas « max-scale vaut budget total ». Une autre mise à jour attend la fin du drain. Le plafond global namespace/pool doit aussi être explicite dans le lock de profil, selon capacité réelle.

Volumes temporaires au plus `64 MiB` (**à ratifier**). Quota namespace/pool et charge du système partagé = inventaire obligatoire avant E, pas une capacité production annoncée.

Consult writer/accept au plus `2 s` par étape dans le même budget (**à ratifier**). Chaque effet engagé au plus `5 s` et jamais au-delà de la deadline d'exécution (**à ratifier**). L'échéance absolue n'est jamais remise à zéro à chaque hop.

- Fenêtre stable KPA `60 s` (**à ratifier**), rétention/grâce de retour à zéro `30 s` chacune (**à ratifier**, clés/portée à vérifier sur le pin), observation de zéro à prouver après cette combinaison et le délai de terminaison. Drain métier maximal `35 s` (**à ratifier**) pour les engagements bornés, puis issues inconnues conservées. Aucun cron/warm-up et aucun min-replica caché de sidecar.
- Retention journaux ticket/exécution/effet `24 h` après deadline (**à ratifier**), quota `1000` entrées actives par binding (**à ratifier**) ; saturation = refus borné, pas croissance mémoire/SQL infinie. Tombstones/versions de retrait ne sont **pas** purgés avec ce journal : leur compaction exige une preuve de non-replay et une décision séparée.

**Retries :** aucun retry métier Lazaret/client/framework après envoi ambigu ; aucun retry de méthode invoke/effect non idempotente à l'ingress/mesh. Les retries techniques natifs Activator/queue-proxy avant livraison doivent être inventoriés au pin ; leurs bornes, conservation du ticket et cas d'envoi ambigu sont à prouver, pas supposés désactivables. Double livraison ne donne pas deux accept d'un ticket/effet. L'idempotence CAS/PUT ne couvre pas une opération métier, et une nouvelle demande avec un autre identifiant peut dupliquer un effet métier.

**Mapping proposé, à ratifier**, sans nouveaux status/enveloppes publics : DTO invalide→`InvokeHttpError::BadRequest`/400 ; preuve absente/invalide→`Unauthorized`/401 ; refus d'autorité courant (désactivé, generation/epoch/grant obsolète, mauvais binding, replay)→`Forbidden`/403 ; corps trop grand→`PayloadTooLarge`/413 ; writer/projection/route indisponible, saturation, image/scheduling/readiness ou deadline→`BadGateway`/502 ; défaut interne inattendu→`Failed`/500. Préserver `{ error: String }` et raisons stables snake_case sans secrets/URL interne. Les routes runtime utilisent des raisons explicites distinguant refus/panne/deadline/issue ambiguë ; pas de 200 `QUEUED`, de 503/504/409/429 ajouté sans amendement. **Écart vérifié :** `http/src/error.rs` commente 502/503, mais `BadGateway` répond réellement 502 ; ne pas traiter ce commentaire comme contrat 503. `/invoke` legacy garde son mapping courant. Un 502/timeout ne garantit jamais absence d'effet.

**Responsables :** B : lock, budgets réels et mapping paramètres tiers ; D : deadlines/erreurs/retries de l'application ; C : TTL/CAS/quota des journaux et epochs ; humain : pins/valeurs et compromis d'indisponibilité. **Oracles :** saturer chaque borne avec contrôle positif, reproduire image/capacité/readiness/autorité absentes et deadline, compter effets/doublons ; comparer settings et images réellement exécutées au lock ; retour à zéro complet. Aucune de ces preuves n'est produite par ce document.

### B6 — HTTP fini et état externe ; retrait conserve les données

**Choix proposé, à ratifier :** éligibles uniquement les opérations HTTP finies, bornées par B5, qui tolèrent perte complète de mémoire/filesystem et peuvent reprendre après création d'une nouvelle instance. Pas de websocket/stream durable, daemon, tâche de fond indépendante de l'invoke, cron, affinité mémoire ou transaction ouverte entre deux requêtes. Une image qui l'exige reste non éligible au profil zéro : la rendre `min-scale>0` en cachette n'est pas une implémentation de 0012. La readiness ne lance ni migration ni opération métier et n'est pas un warm-up.

État métier persistant = KV/stockage plateforme externe déjà autorisé et scopé `(project, binding)` via Lazaret ; aucun stockage mutualisé par digest, volume hostPath, hibernation mémoire ou PVC ajouté implicitement. Le filesystem temporaire est borné/jetable ; pas de secret durable ni journal d'effet uniquement local. L'accusé de succès d'une opération exige la persistance prévue par sa capacité, pas une écriture en mémoire. Les effets sont engagés selon B4 ; aucune garantie transactionnelle inter-services ou exactly-once nouvelle. Le profil initial peut se limiter au plugin HTTP de référence KV : compatibilité de chaque autre release à qualifier, sans prétendre Factory/host livrés.

Migration de schéma métier : version de données externe distincte de génération/Revision ; aucune migration exécutée par chaque replica au startup. Fermer/fencer le binding, attendre les engagements admis, établir une sauvegarde/récupération prouvée et une migration exclusive par binding/génération avant ouverture ; privilégier une évolution additive compatible avec la release précédente. Une migration destructive/incompatible nécessite une décision humaine et un contrat de données séparés ; elle est hors GO de cette tranche. Les migrations SQL de **contrôle** B3/registre D sont additives : backfill fermé, aucun downgrade supprimant données/tombstones. Ne pas confondre migration de schéma contrôle et données utilisateur.

Secrets : seule la référence scoped/versionnée apparaît dans configuration, snapshot et événements. Résolution par la capacité Lazaret et la politique existante ; aucun credential externe durable monté/env qui ouvrirait une I/O hors gateway. Un secret plaintext déjà légitimement remis n'est pas « effacé » par un epoch : ne pas promettre cette propriété. #### 13.1-A — Empreintes canoniques opération et effet

**Valeur proposée.** `SHA-256(UTF8(JCS(input)))`, JCS **RFC 8785 intégral**, sans BOM, espace ajouté ni LF final ; résultat `sha256:` suivi de 64 hexadécimaux minuscules. Pas de hash de `Debug`, de `serde_json::to_string` ordinaire, de concaténation de champs ou de JSON simplement trié par ordre UTF-8 : JCS trie les propriétés selon UTF-16 et normalise les nombres selon son modèle IEEE-754. Le domaine ci-dessous est un champ obligatoire du préimage, jamais une option du caller.

Profil lexical commun aux quatre blocs : UUID = `uuid::Uuid`, rendu canonique lower-case hyphenated ; compteurs nouveaux = `RuntimeCounterV1(u64)` dans `0..=i64::MAX`, sérialisés en **chaînes décimales sans signe ni zéro initial** (sauf `"0"`) pour conserver exactement les valeurs au-delà de 2^53 ; dates de contrôle = `RuntimeUnixMsV1(i64)` UTC depuis Unix epoch, non négatives, même encodage décimal string. `schema_version: u16` reste le nombre JSON `1`. Ces règles des DTO runtime et du préimage ne changent **pas** la représentation existante de `WorkloadIdentity`/`SessionClaims` : leur copie normalisée pour le hash est construite explicitement. Les digests de release restent `sha256:<64 hex minuscules>`.

`RuntimeOperationHashInputV1` est **exactement** l'objet JSON suivant (toutes propriétés requises, aucune autre) :

```text
{
  schema_version: 1,
  domain: "urn:aiforall:apparatus:runtime:operation-hash:v1",
  authorization_id: UUID, project_id: UUID,
  source: { instance: UUID, binding: UUID, release: Digest,
            generation: Counter, grant_revision: Counter },
  source_revocation_epoch: Counter,
  target: { binding_id: UUID, generation: Counter, release: Digest,
            grant_revision: Counter, revocation_epoch: Counter },
  operation_id: UUID, operation: String, payload: JSON,
  deadline_unix_ms: UnixMs
}
```

Lazaret remplit le contexte depuis l'identité vérifiée et le writer, après comparaison de `expected_generation` avec la génération cible ; `authorization_id` est le `jti` du ticket, pas `operation_id`. `operation` est la chaîne validée par le protocole existant, sans trim/case-fold ; `payload` est le contenu sémantique des `params` P0 (clé `payload` obligatoire sur le nouveau DTO, `null` autorisé), sans retrait de champs ni conversion de chaînes/base64. Tous UUID sont normalisés avant JCS. Dans le payload, chaînes sans normalisation Unicode/NFC ; rejet UTF-8/surrogates invalides, noms dupliqués **avant** construction d'un `Value`, NaN/Infinity et entiers hors `[-9007199254740991,9007199254740991]`. Les autres nombres suivent strictement JCS/binary64 ; les valeurs décimales exactes ou grands entiers métier doivent être des chaînes. La taille B5 est contrôlée sur le corps reçu avant parsing et sur le JSON canonique, sans augmenter sa borne. Ce profil est propre aux nouvelles routes ; P0 n'est pas réécrit.

Couverture : opération/id/payload, source, cible/release/génération, grants et epochs source/cible, `jti`, deadline. Exclusions : certificat/session bruts, signatures/`kid`, headers/Host/trace, URL/projection/writer fence, Pod UID/Revision/instance **cible** inexistante avant réveil. `iss/aud/purpose/iat/exp` sont néanmoins protégés et validés par le JWS, pas ignorés parce qu'absents du préimage. L'instance cible est recoupée à accept et liée au contexte d'exécution B1/B4. Aucun digest auto-référent dans son propre préimage. D conserve l'empreinte émise associée au `jti` et ne fait jamais confiance au seul hash déclaré par le plugin.

Pour un effet, même algorithme et mêmes règles, objet exact `RuntimeEffectHashInputV1 { schema_version:1, domain:"urn:aiforall:apparatus:runtime:effect-hash:v1", operation_sha256:Digest, execution_id:UUID, effect_id:UUID, instance_id:UUID, invoke:{binding_id:UUID, operation_id:UUID, operation:String, params:JSON} }`. Le contexte d'exécution authoritative relie cette empreinte aux epochs/deadline du ticket ; aucun contexte fourni librement par le plugin. Même identifiant d'effet + autre empreinte = `RUNTIME_ID_REUSED`, jamais une nouvelle réservation ; empreinte identique ne signifie pas autorisation de rejouer l'I/O.

**Justification :** égalité de sens indépendante de l'ordre des clés, séparation opération/effet et absence d'arrondi des compteurs ; ni exactly-once ni autorisation issue du hash. **Surfaces :** C `crates/apparatus-contracts/src/runtime.rs` (types/profil partagé), D construction/vérification et accept/effects ; aucune modification de `protocol.rs`. **Oracles T :** vecteurs RFC 8785 (UTF-16, échappements, nombres/−0), vecteurs dorés communs C/D ; ordre/espaces JSON équivalents ⇒ même hash ; mutation de chaque champ couvert ⇒ hash différent ; doublons, versions/champs inconnus d'enveloppe, nombres interdits rejetés ; effet substitué/replay refusé.

#### 13.1-C — CAS, bail, fence et curseur de liste

**Formes proposées**, types Rust descriptifs à définir par C dans les contrats neutres (sans client cluster). `Counter`/`UnixMs` ci-dessous désignent les newtypes et leur encodage A ; JSON snake_case, `schema_version=1`, champs inconnus rejetés. Sur GET, `schema_version=1` est un paramètre requis ; sur commande, il est requis dans le body. Toutes propriétés de corps listées sont requises ; un `Option` sans valeur s'encode `null`, pas champ omis ni valeur implicite. Le paramètre query cursor est omis seulement pour la première page. Les identifiants projet/binding proviennent des query/path obligatoires, et toute copie dans la réponse/body doit coïncider.

```rust
RuntimeCasV1 { generation: RuntimeCounterV1, revocation_epoch: RuntimeCounterV1,
               projection_version: RuntimeCounterV1, grant_revision: RuntimeCounterV1 }
RuntimeLeaseProofV1 { lease_id: uuid::Uuid, holder_id: uuid::Uuid,
                      writer_fence: RuntimeCounterV1 }
RuntimeWriterLeaseRequestV1 { schema_version: u16, holder_id: uuid::Uuid,
    expected: RuntimeCasV1, renew: Option<RuntimeLeaseProofV1> }
RuntimeWriterLeaseV1 { schema_version: u16, project_id: uuid::Uuid, binding_id: uuid::Uuid,
    proof: RuntimeLeaseProofV1, cas: RuntimeCasV1,
    issued_at_unix_ms: RuntimeUnixMsV1, expires_at_unix_ms: RuntimeUnixMsV1 }
RuntimeWriteGuardV1 { expected: RuntimeCasV1, lease: RuntimeLeaseProofV1 }
RuntimeWriteAckV1 { schema_version: u16, project_id: uuid::Uuid, binding_id: uuid::Uuid,
                    cas: RuntimeCasV1, writer_fence: RuntimeCounterV1 }
RuntimeCursorV1(String) // opaque pour operator/Lazaret ; aucun état d'autorisation
RuntimeBindingPageV1 { schema_version: u16, items: Vec<RuntimeBindingSnapshotV1>,
                       next_cursor: Option<RuntimeCursorV1> }
```

`holder_id` = UUID v4 neuf par processus operator, jamais réutilisé après redémarrage. Fence = compteur **par projet/binding**, alloué sous verrou de ligne par le writer DB : premier grant `1`, strictement augmenté à chaque nouvelle acquisition/takeover, jamais réinitialisé au retrait/réinstallation ; tombstone conservé. Dépassement `i64::MAX` ⇒ fermé/erreur interne, pas de wraparound. Le bail lie principal projector, holder, lease UUID et fence. `renew=None` acquiert seulement en l'absence de bail vivant ; pour le même holder d'un bail encore vivant, renvoyer ce bail **sans l'étendre**. Autre holder vivant ⇒ `RUNTIME_LEASE_HELD`. `renew=Some(proof)` renouvelle seulement le bail courant non expiré dont principal/holder/lease/fence et CAS correspondent ; conserver lease/fence, jamais ressusciter un bail expiré.

Durées proposées **à ratifier** : TTL serveur **10 000 ms**, renouvellement nominal toutes les **3 000 ms** ; aucun TTL libre du client. `expires_at=db_clock_after_lock+10000`, comparaison au `clock_timestamp()` DB après acquisition du verrou, pas au `now()` figé au début d'une transaction en attente ni à l'horloge du caller. À `db_clock>=expires_at`, bail perdu. Toute erreur/panne de renouvellement suspend nouvelles mutations/apply ; C abandonne son travail courant si perte de bail/fence, relit l'autorité avant une nouvelle acquisition. Un apply déjà en vol peut laisser le résiduel fermé documenté B3 ; aucun fencing atomique de l'API externe revendiqué.

Guard obligatoire sur les PUT observation/instance : `(project,binding,generation,epoch,grant_revision,projection_version,holder,lease,fence)` relu atomiquement sur writer. Le fence ne remplace aucun compteur métier ni le contrôle d'UID/resourceVersion hors Manifesto. `projection_version` démarre à `1` à la matérialisation fermée et augmente pour tout changement logique/projection/instance visible ; génération/grant/epoch gardent leurs causes métier B3, sans inférence entre compteurs. Allocation/renouvellement du bail et journalisation begin/complete ne changent pas à eux seuls la version de projection. Revocation d'une seule instance ferme son entrée/tombstone sous le verrou ; elle n'invente pas une nouvelle génération ni ne réactive les autres. Aucune remise à zéro des versions/fences au backfill.

Succès PUT ⇒ `RuntimeWriteAckV1` avec CAS courant. Répétition d'une projection/instance **strictement identique**, même fence vivant et contexte métier toujours courant : ack sans nouveau changement/version ; ce cas ne court-circuite jamais une révocation. Sinon CAS obsolète ⇒ `RUNTIME_STALE_STATE`, mauvais fence ⇒ `RUNTIME_FENCE_CONFLICT`, bail expiré/mauvaise lease ⇒ `RUNTIME_LEASE_LOST`. Observation/instance utilisable seulement si son `writer_fence` est le fence courant d'un bail vivant ; validité au plus `min(observed_at+5000, lease.expires_at)` ; cette borne complète, sans augmenter, la fraîcheur B5 de 5 s. Le rôle lazaret de revoke/begin/complete ne reçoit pas un faux bail projector : B4 sérialise ces commandes sous le verrou métier et vérifie leurs contextes/exécutions/réservations. Complete peut journaliser un engagement antérieur après révocation, mais ne réserve ni ne rejoue l'effet.

**Curseur exact proposé :** chaîne ASCII `rcl1.<kid>.<p>.<mac>`, au plus **2048 octets** ; `p=BASE64URL_NO_PAD(UTF8(JCS(RuntimeListCursorPayloadV1)))`, `mac=BASE64URL_NO_PAD(HMAC-SHA256(K, UTF8("urn:aiforall:apparatus:runtime:cursor:v1") || 0x00 || ASCII(kid) || 0x00 || ASCII(p)))`. `K` = clé dédiée Manifesto **32 octets**, référencée depuis configuration secrète, jamais dans curseur/log/contrat ; `kid="rcl-v1-"+UUID v4 canonique` (43 caractères). Comparaison MAC constante ; encodage non canonique/clé inconnue ⇒ refus. Rotation proposée 24 h ; publier la clé suivante avant activation et garder la précédente en vérification 60 s après dernière émission ; aucune réutilisation de clé invoke/IAM.

Payload exact : `RuntimeListCursorPayloadV1 { schema_version:u16, scan_id:Uuid, project_id:Uuid, principal:String, after_binding_id:Uuid, upper_binding_id:Uuid, page_size:u16, issued_at_unix_ms:UnixMs, expires_at_unix_ms:UnixMs }`. `principal` = SAN authentifié B, recoupé avec le caller courant ; TTL scan **60 000 ms**, sans prolongation de page en page ni grâce. Première page sans cursor : `page_size` défaut **100**, autorisé **1..=200** ; capturer le maximum `binding_id` du projet comme borne haute. Pages suivantes : `(after_binding_id, upper_binding_id]`, ordre UUID octets croissant, même projet/principal/page_size ; paramètre page_size contradictoire ⇒ curseur invalide. Dernière page `next_cursor=null`.

Chaque page lit le writer courant, tombstones inclus ; ce n'est **pas** un snapshot transactionnel multi-page. Une insertion concurrente située avant le dernier UUID peut attendre le prochain scan complet ; jamais déduire un retrait de la seule absence dans une liste. Les commandes et autorisations relisent toujours le writer ; cursor ne rend ni une route ni un grant frais pendant 60 s. Expiration ⇒ nouveau scan, pas fallback sur la liste `ready` historique.

**Justification :** exclusion distribuée vérifiable, compteurs sans ambiguïté et pagination bornée sans transformer un cursor en permission. Champs de bail/fence dans la migration additive C déjà inventoriée ; clé cursor en référence de configuration, pas nouvelle table de secrets. **Surfaces :** C DTO/port/writer/adapter HTTP et operator ; D consomme CAS/erreurs et n'acquiert pas de bail. **Oracles T :** concurrence de holders, expiration exacte/renouvellement après perte, redémarrage et fence monotone après retrait ; CAS retardé et PUT identique ; curseur falsifié/autre principal/projet/version, limite/TTL/ordre/pages et insertions concurrentes ; panne writer = pas d'allow ni suppression par absence.

#### 13.1-D — Erreurs v1, mapping et absence de retries métier

**Valeur proposée.** Ensemble fermé `RuntimeErrorCodeV1` ci-dessous, noms wire exacts en SCREAMING_SNAKE_CASE ; réponse d'erreur des **nouvelles routes internes Manifesto** : `RuntimeControlErrorV1 { schema_version:u16=1, code:RuntimeErrorCodeV1, retry_class:RuntimeRetryClassV1, effect_outcome:RuntimeEffectOutcomeV1 }`. `RuntimeRetryClassV1` wire = `never | read_only | reconcile_after_read` ; `RuntimeEffectOutcomeV1` = `not_started | may_have_started`. Aucun détail libre, secret, URL ou message SQL renvoyé ; diagnostic corrélé côté serveur seulement. Les nouveaux DTO runtime refusent versions/enum/champs inconnus. Une réponse d'autorité de version/code/formats inconnus devient chez D `RUNTIME_AUTHORITY_PROTOCOL_ERROR`, pas une erreur 400 imputée au caller ni un allow.

Le public Lazaret conserve **exactement** `{"error": String}` et `InvokeHttpError` : les variantes avec chaîne (`BadRequest`, `Forbidden`, `BadGateway`) portent le nom du code converti **ASCII lower-case** (ex. `runtime_stale_state`), uniquement sur les nouvelles routes/gardes runtime. Les variantes sans chaîne gardent leurs littéraux existants : `Unauthorized` ⇒ `"unauthorized"`, `PayloadTooLarge` ⇒ `"payload too large"`, `Failed` ⇒ `"operation failed"` ; le code détaillé reste interne. Aucun nouveau champ public ni changement des raisons legacy non migrées. Codes finis et correspondances **HTTP interne → variante InvokeHttpError / HTTP public** :

- `RUNTIME_INVALID_REQUEST`, `RUNTIME_UNSUPPORTED_VERSION`, `RUNTIME_CURSOR_INVALID` : **400 → BadRequest / 400**, `never`.
- `RUNTIME_CURSOR_EXPIRED` : **400 → BadRequest / 400**, `reconcile_after_read` uniquement pour recommencer une liste sans ancien cursor.
- `RUNTIME_UNAUTHENTICATED`, `RUNTIME_INVALID_PROOF` : **401 → Unauthorized / 401**, `never` (signature/issuer/audience/purpose/kid, session ou preuve expirée à l'entrée).
- `RUNTIME_SERVICE_FORBIDDEN`, `RUNTIME_CALLER_FORBIDDEN`, `RUNTIME_BINDING_CLOSED`, `RUNTIME_RELEASE_NOT_ADMITTED`, `RUNTIME_IDENTITY_REVOKED`, `RUNTIME_HASH_MISMATCH`, `RUNTIME_LEGACY_DISABLED` : **403 → Forbidden / 403**, `never`. Hash syntaxiquement invalide relève de `RUNTIME_INVALID_REQUEST`, pas de ce mismatch.
- `RUNTIME_BINDING_NOT_FOUND` : **404 → Forbidden / 403**, `never` ; authentifier/autoriser le rôle avant lookup, sans révéler l'existence d'un binding d'un autre projet au public.
- `RUNTIME_STALE_STATE`, `RUNTIME_FENCE_CONFLICT`, `RUNTIME_LEASE_LOST` : **409 → Forbidden / 403**, `reconcile_after_read` **uniquement** pour le contrôle projector ; jamais retry d'invoke/accept/effet. Stale = génération/epoch/grant/version attendus discordants ; fence = fence non courant ; lease lost = bail expiré/lease-holder non concordant.
- `RUNTIME_LEASE_HELD` : **409 → BadGateway / 502**, `reconcile_after_read` pour operator après fermeture de son ancienne tentative et relecture du bail ; pas de takeover d'un bail vivant.
- `RUNTIME_REPLAY`, `RUNTIME_ID_REUSED` : **409 → Forbidden / 403**, `never`. Replay = ticket/effet déjà consommé non réutilisable ; id reused = identifiant réutilisé avec autre empreinte/contenu. Une répétition purement idempotente de report/complete retourne son ack conforme C/B4, pas une nouvelle exécution.
- `RUNTIME_PAYLOAD_TOO_LARGE` : **413 → PayloadTooLarge / 413**, `never`.
- `RUNTIME_AUTHORITY_UNAVAILABLE`, `RUNTIME_PROJECTION_UNAVAILABLE`, `RUNTIME_ROUTE_UNAVAILABLE`, `RUNTIME_CAPACITY_EXHAUSTED`, `RUNTIME_KEY_UNAVAILABLE` : **503 → BadGateway / 502**, `read_only`. Projection = absente/périmée/non observée ou route non établie, **pas** autorisation positive issue d'une ancienne vue ; clé indisponible = provider/configuration injoignable, distinct d'un kid présenté non approuvé (`INVALID_PROOF`).
- `RUNTIME_DEADLINE_EXCEEDED` : **504 → BadGateway / 502**, `never` (deadline de l'opération admise atteinte ; aucune nouvelle échéance).
- `RUNTIME_AUTHORITY_PROTOCOL_ERROR`, `RUNTIME_EFFECT_OUTCOME_UNKNOWN` : **502 → BadGateway / 502**, `never` ; le second impose `effect_outcome=may_have_started`.
- `RUNTIME_COUNTER_EXHAUSTED`, `RUNTIME_INTERNAL` : **500 → Failed / 500**, `never` ; overflow arrête le binding/contrôle, jamais reset de compteur.

Les huit routes internes retournent **200** sur succès (snapshot/page, bail, ack ou réservation selon la méthode), jamais un succès `QUEUED`/202 ; PUT/complete idempotents ne rejouent aucun effet. Les 404/409/503/504 ci-dessus ne sont introduits que pour les **huit nouvelles routes internes**, et font partie de cette proposition à ratifier ; ils ne deviennent pas de nouveaux statuts publics d'invoke et ne changent pas le contrat historique de `InvokeHttpError`. Le rôle est évalué avant ressource/curseur ; erreur de preuve ⇒ 401, identité authentifiée sans rôle/droit ⇒ 403.

**Règle de retry normative :** `retry_class` décrit une possibilité de récupération, pas une commande de rejouer. `read_only` permet au plus **une** relecture supplémentaire de metadata GET dans le budget total de consultation B5 de **2 s** et la deadline existante ; pas de prolongation ou boucle. `reconcile_after_read` signifie fin/suspension du travail fenced, nouvelle lecture writer puis **nouvelle** tentative de metadata avec CAS/bail courants ; jamais réutiliser l'ancien guard ni obtenir un grant par retry. Nouveau scan après expiration n'autorise aucune absence→suppression.

Aucun de ces codes n'autorise un retry automatique framework/ingress/client de `/runtime/invoke`, `/runtime/accept`, `/runtime/effects/invoke`, begin-effect ou d'une I/O. Les POST métier ne sont jamais rejoués automatiquement, même si une erreur porte `read_only`. Un timeout/débranchement après admission/envoi/réservation dont l'absence d'effet n'est pas prouvée impose `RUNTIME_EFFECT_OUTCOME_UNKNOWN`/`may_have_started` et `never`, même si la cause technique initiale était 503/504. Le client applique cette garde indépendamment du champ retry reçu. `not_started` ne peut être affirmé sur la seule absence de réponse ; un 502 public n'atteste jamais absence d'effet. Aucun code inconnu, saturation ou panne ne provoque fallback digest/local.

**Justification :** distinguer refus courant, conflit de contrôle et indisponibilité sans agrandir l'API publique ou promettre une cancellation. **Surfaces :** C enum/erreur HTTP interne et guards/ports ; D adapter/mapping runtime `http/src/error.rs`, contrôle de retries et garde legacy ; T suites contracts/control/errors/effects prévues §14. **Oracles :** cas paramétré pour chaque code, raison wire exacte, status interne/public, version/code inconnu ; spies/effets réels prouvant zéro replay d'opération après timeout ambigu ; conflit metadata récupérable seulement après relecture, jamais ancien guard ; legacy migré refusé et legacy non migré inchangé.

**Gel utilisable après ratification de 13.1 seulement :** C publie les types, codec et mappings ci-dessus comme unique source ; D ne crée aucune variante locale, T dérive ses vecteurs/cas de cette annexe. Les durées/identités supplémentaires ici sont proposées à l'humain, pas déjà acquises par l'Accept précédent ; les gates B5/§15 restent indépendantes. Aucun nouveau fichier partagé, route, événement, client cluster, migration destructive ou changement de claims n'est autorisé par cette complétion.

4. À tout redémarrage/rattachement d’une instance D, reprendre la barrière de maintenance et le rapprochement des étapes 1–3 avant sa readiness identité/dispatch. Vérifier aussi le sceau et l’identité de la base ; **un sceau persistant seul ne prouve pas qu’une base n’a pas été restaurée à un état antérieur**. Répertoire absent/restauré, nouveau périmètre ou restauration C/D non coordonnée ⇒ aucun legacy en attendant la réconciliation complète avec le writer C actuel, jamais « index vide donc legacy ». Les instances déjà en service n’utilisent pas une base en cours de restauration. Les tombstones et l’historique des actes sont conservés ; pas de disponibilité promise pendant cette barrière.

Il ne suffit donc **pas** de lancer un poller sur les projets connus ni d’attendre 5 s : sans cette barrière, une nouvelle migration et une session legacy pourraient se croiser. Cette condition est nouvelle et explicite ; elle n’est pas présentée comme déjà implémentée.

**Dispatch exact de `/session` après validation TLS du certificat :**

- D recherche son enrollment runtime **par fingerprint certifié**, avec résultats distincts `absent`/`erreur`. Une entrée runtime connue, même close/expirée, ne retombe jamais sur le store legacy. Elle fournit `project_id`, binding et instance ; recouper le répertoire, puis faire le GET binding `ByInstanceId` et les validations §13.2-B/D avant émission. Répertoire manquant/incohérent ⇒ fermé. Les claims émis gardent strictement leur forme existante.
- Seulement si le store runtime répond **absent**, D consulte l’enrollment legacy pour retrouver le binding, puis son répertoire local writer. Entrée de refus présente ⇒ `RUNTIME_LEGACY_DISABLED` sans signer de session. Entrée absente **et bootstrap/périmètre valide** ⇒ exécuter la sémantique legacy existante, **sans appel RuntimeControlPort** et sans ajouter de project_id.
- Certificat inconnu des deux stores ⇒ refus historique ; même fingerprint présent dans les deux stores ⇒ incohérence fermée. Store/répertoire indisponible n’est jamais `absent` : pas de session ni fallback ; mappings runtime d’indisponibilité §13.1-D, sans changer la forme publique. Aucun paramètre/body/header ne sélectionne le mode.

La même classification/consultation négative couvre `/enroll` legacy, `/invoke`, consommation des anciennes `SessionClaims`, autorisation de capacités et tout locator/dispatch local historique : une ancienne session **déjà émise** ne contourne pas le refus en évitant `/session`. L’émission antérieure d’un token peut finir avant la barrière, mais ne lui donne aucune utilisation autorisante après celle-ci. Une identité runtime échouant à la revalidation ne passe jamais par `IdentityService` legacy en secours. Hors binding migré/en cutover, les raisons/DTO legacy restent inchangés ; le coût ajouté est une lecture **locale D**, pas un appel runtime pour les sessions non migrées.

**Justification :** un certificat legacy sans projet ne peut pas découvrir seul le marqueur writer ; une projection négative, installée avant lui et monotone, ferme la fenêtre sans prétendre à une transaction inter-services. **Surfaces :** D `application/src/identity.rs`, `application/src/runtime.rs`, module proposé `application/src/runtime_cutover.rs`, `infra/src/runtime_store.rs`, migration additive runtime, `http/src/lib.rs`, `setup/src/app.rs` ; C commandes de maintenance et inventaire writer. Nouveaux chemins proposés explicitement attribués D/C, pas de modification de la migration historique ni de copie des grants C.

**Oracles T :** les trois cas session (legacy non migré ⇒ zéro appel runtime ; legacy fenced/migré ⇒ refus sans signature ; runtime ⇒ projet du store puis GET exact), fingerprint ambigu/store en erreur, bootstrap incomplet/base remplacée, tous replicas et session déjà émise. Barrières de concurrence D-install/C-prepare, panne après chacun des commits, crash avant/après ack, anciens events/pages/404 et redémarrage ⇒ jamais de retour legacy ; mauvaise association projet/binding refusée, pas d’inférence par digest. Vérifier le refus sur chaque bypass legacy et sa conservation après rollback. SQL réel pour durabilité/synchronisation locale ; tests d’adapter sortant distincts d’une preuve de cutover distribué.

#### 13.3-C — Gap n°8 : trois actes writer par binding, puis ouverture explicite

**Valeur proposée :** une matérialisation est un acte de maintenance plateforme **nominatif**, pas une conséquence de `save_component`, d’un event, d’un tick legacy, d’un backfill ou d’un GET. C porte les commandes ci-dessous dans l’application Manifesto et son unité de travail writer ; l’opérateur humain de cutover en est l’acteur habilité, via le runner setup de maintenance. Ni projector ni lazaret, au titre des huit routes, ne reçoit le droit d’activer un binding. HTTP/queue génériques ne publient pas ces commandes de maintenance par simple enregistrement ; entrée non protégée/non implémentée ⇒ commandes désactivées et binding fermé.

Formes internes proposées, sans nouvelle route ni champ dans les snapshots §13.2 :

```rust
RuntimeBindingCutoverPlanV1 {
    schema_version: u16, migration_id: Uuid, project_id: Uuid, binding_id: Uuid,
    expected_generation: RuntimeCounterV1, expected_grant_revision: RuntimeCounterV1,
    release: RuntimeDigestV1, profile: String, profile_lock_sha256: RuntimeDigestV1,
    inventory_sha256: RuntimeDigestV1
}
FenceRuntimeBindingV1 { plan: RuntimeBindingCutoverPlanV1 }
PrepareRuntimeBindingV1 {
    schema_version: u16, migration_id: Uuid, project_id: Uuid, binding_id: Uuid,
    expected: RuntimeCasV1, drain_evidence_sha256: RuntimeDigestV1
}
OpenRuntimeBindingV1 {
    schema_version: u16, migration_id: Uuid, project_id: Uuid, binding_id: Uuid,
    expected: RuntimeCasV1, service_uid: String, revision_uid: String,
    profile_lock_sha256: RuntimeDigestV1
}
```

Le contexte d’exécution contient **séparément** l’identité opérateur authentifiée et l’accusé D de confiance §13.3-B ; ils ne sont pas reconstruits depuis ces objets. Le runner les transmet comme capacité de maintenance typée **non désérialisable depuis HTTP/body/queue**. Il ne fabrique pas une attestation en important un JSON d’accusé non vérifié. Les handlers passent par l’exécution de commandes du composition root et l’unité de travail du service, jamais par du SQL de script inter-service ni une route machine supplémentaire. Un résultat incertain impose relecture/journal et reprise explicite ; pas de retry métier automatique ou de booléen « force ».

**Inventaire immuable lié au plan :** projet/binding et compteurs writer, release et référence/UID du CR d’admission, liste explicite de tous les anciens Services/Pods/owners avec namespace, nom, UID/resourceVersion et **tous** leurs consommateurs, état des engagements/données à préserver, périmètre de coupure, référence du lock/profil B et identité opérateur. L’inventaire est recueilli par l’opérateur/contrôleur déjà habilité à lire le cluster ; Manifesto/Lazaret n’acquièrent pas de client cluster. L’empreinte référence le contenu versionné et vérifié, ne transforme pas une déclaration caller en preuve de propriété/`VALID`/drain. Inventaire incomplet, objets partagés sans coupure ciblée démontrée, profil non verrouillé ou absence de preuve ⇒ STOP. Un changement d’inventaire/portée exige une reprise approuvée, pas un overwrite silencieux.

**Ordre normatif, explicitant §15 étapes 1→4 :**

1. **Inventorier, refuser chez D et fermer chez C.** Recenser les UID/consommateurs ; installer le refus D et vérifier le commit/accusé §13.3-B **avant** toute matérialisation C. Désactiver explicitement le binding métier legacy avec sa commande existante ; la transaction conserve les compteurs et les engagements nécessaires. `FenceRuntimeBindingV1` refuse une legacy encore active, un projet/binding/release/compteur discordant ou un accusé D absent/non vérifié. Il verrouille projet → bindings métier en ordre UUID → runtime, comme begin-effect et les hooks de fermeture. Dans **une transaction**, il vérifie l’état métier fermé, crée seulement pour ce binding la ligne runtime `closed`, le marqueur irréversible et le journal du plan ; retire l’éligibilité aux ticks/dispatchs hérités. Première matérialisation : `projection_version=1`, epoch initial `1` si aucun historique n’existe ; génération/grant revision proviennent des lignes métier writer. Toute reprise conserve/incrémente les compteurs/fences existants, jamais de reset. La phase de maintenance interne est `fenced`, **sans permis de créer Serving**. Retrait d’une ligne runtime existante/tombstone ou réactivation d’un historique sont interdits. L’arrêt du writer legacy est vérifié avant de lui retirer des objets ; un appel externe legacy déjà en vol reste à drainer, pas prétendument annulé par SQL.
2. **Drainer et prouver la coupure héritée.** Ne plus admettre de nouvelle autorisation ancienne ; fermer les identités/sessions et endpoints digest/locaux pour ce binding, attendre les engagements antérieurs ou conserver explicitement leur issue indéterminée selon B4. Contrôler les applications legacy en vol et tous les consommateurs d’objets partagés. La preuve de coupure/drain est reliée au plan par `drain_evidence_sha256` et contrôlée par le runner de maintenance, pas acceptée comme un simple `drained=true`. Aucun retrait de release/CR d’admission, Secret partagé ou données. Sans coupure effective démontrée ⇒ rester fenced/closed.
3. **Préparer fermé, puis observer à zéro.** `PrepareRuntimeBindingV1` reprend le même acte, exige son full CAS courant et l’accusé D encore durable, la preuve de l’étape 2, le binding métier non actif et la ligne runtime `closed/non-tombstone`. Dans sa transaction writer, il relit les grants/consentements et **l’autorité d’admission existante** : release exactement `VALID`, jamais un status/body/label fourni par la commande ni une modification de `VALID` par C. Il vérifie le profil identifié par `profile` et son lock immutable (`profile_lock_sha256`) approuvé par B : sandbox, transport, origine/CA Lazaret et limites configurés ; valeur inconnue/non disponible ⇒ refus. Il journalise phase interne `prepared`, incrémente la version de projection pour ce changement et remet un permis de préparation borné au plan et au CAS résultant. Cette phase ne vaut ni état runtime active ni autorisation d’invoke.
4. **Ouvrir par acte writer distinct.** Après création/observation ci-dessous, seul `OpenRuntimeBindingV1` peut passer `closed → active` pour cette préparation. Il reprend les mêmes verrous et relit **après verrou** full CAS, génération/grant/epoch/release, projet/binding métier et consentement/politique courants, admission `VALID`, lock/profil, journal de coupure/accusé D et exclusivité legacy/runtime. Il exige le **Service UID déjà enregistré** pour ce plan, la Revision UID exacte et l’observation route Ready fraîche : bonne release, générations API égales, identité de Service et endpoint privé attendus, fence du bail projector courant/vivant, `db_now < valid_until <= min(observed_at+5000, lease.expires_at)`. Horloge DB après verrou, aucune confiance dans les dates d’open. Aucun Pod/instance/certificat cible n’est requis pour cette ouverture à zéro. Sous ce même commit, effectuer l’activation métier explicite pour le **mode runtime exclusif**, activer son intention pour la génération/epoch courantes, inscrire phase interne `opened`, auteur/plan/CAS/UID/lock/date dans le journal et incrémenter la projection ; **ne pas réactiver l’éligibilité legacy**. Les compteurs métier restent ceux des règles existantes, jamais une seconde génération runtime ; si l’activation les change, les projections/instances antérieures sont invalidées et un nouveau report du contexte résultant est indispensable avant tout allow. Si le changement de CAS rend l’ancienne projection incompatible, elle reste inutilisable jusqu’au prochain report fenced frais : aucune réécriture de date ou allow stale pour « finir » l’ouverture.

**Permis de préparation et propriété des objets.** Résultat local C, non bearer réseau : `RuntimeBindingPreparationPermitV1 { migration_id, project_id, binding_id, cas, release, profile, profile_lock_sha256, inventory_sha256 }`, avec les types V1 ci-dessus. Le runner transmet ce résultat de confiance à une tâche explicite de préparation du contrôleur existant ; il ne lance pas un deuxième writer concurrent. Le contrôleur, sous son identité projector, relit GET binding et acquiert son bail via les routes existantes, recoupe le plan/permis, le CAS courant et le profil, puis pré-déclare le Service binding fermé à zéro. Nom/namespace sont ceux dérivés par la plateforme, aucun override publisher. **Exception bornée** à la règle générale B3 « création seulement actif » : cette seule préparation administrativement autorisée peut créer à `closed`; un closed de désactivation/révocation ou un tombstone sans ce permis n’autorise aucune création. Les compteurs changés rendent un permis retardé inutilisable ; le résiduel d’un apply en vol garde la limite distribuée B3, pas un nouveau droit.

La préparation n’effectue ni warm-up HTTP ni création/patch d’un Pod enfant. Elle utilise les seules images/références admises et le template §13.2-B. L’UID réellement rendu par la création du Service est enregistré via le PUT observation existant et les registres de propriété ; un objet préexistant de même nom n’est pas adopté. Après timeout, relire la preuve UID/owner chain de **sa propre création** ou STOP ; l’absence d’une réponse n’autorise pas un nouvel UID arbitraire. Les updates/reprises sur UID connu utilisent UID/resourceVersion ; le writer refuse un report qui substitue le Service UID lié au plan. Le premier report valide le lie durablement, les suivants ne le remplacent pas silencieusement. Une nouvelle création légitime après retrait requiert un nouvel acte de préparation approuvé, jamais l’effacement de l’ancien UID. Le permis peut être réémis pour le **même** plan après reprise administrative et relecture complète ; pas de renouvellement automatique d’un permis invalidé par révocation.

Les preuves admission/ownership sont lues par l’operator et la chaîne d’admission existante ; le writer contrôle ses autorités/observations enregistrées et la cohérence transactionnelle, **sans appeler Kubernetes**. Elles ne sont pas remplacées par une copie caller de `VALID`, une URL ou un UID. En absence d’autorité admissible consommable sans client cluster, prepare/open échouent fermés : ce complément n’invente pas un second circuit d’admission.

**Journal/reprise.** Métadonnées de cutover/phase, hashes, auteur, UID attaché et actes d’ouverture sont ajoutés à la migration de contrôle C et au journal writer du binding, sans modifier les enums/DTO gelés ni exporter de secrets. Identifiant réutilisé avec autre contenu ⇒ conflit fermé ; reprise identique relit l’état courant et le journal, ne réapplique pas une ancienne ouverture. Désactivation, retrait, changement de release/génération/grant ou perte de conditions invalide la préparation et ferme/fence selon B3 ; **les hooks de fermeture n’insèrent ni ne préparent ni n’ouvrent** une ligne manquante. Réouverture exige un nouvel acte explicitement approuvé et des preuves courantes, jamais une observation/event retardé. Le marqueur et le refus D survivent toujours. Retrait du résiduel possédé reste §15 étape 5 ; aucun delete/force/backfill/migration de masse n’est autorisé par ces commandes.

**Justification :** séparer refus durable, préparation technique fermée et autorisation métier empêche une legacy active, un apply ou un backfill d’ouvrir le runtime ; l’ouverture est un commit writer explicite après preuves, pas un effet de bord d’un report. **Surfaces :** C module proposé `services/Manifesto/application/src/command/apparatus_runtime.rs` et son enregistrement/runner de maintenance dans setup, `infra/src/apparatus_runtime/runtime_control.rs`, migration de contrôle additive, `infra/src/transaction.rs` (fermeture seulement), `workers/apparatus-operator/src/{controller,desired_state,runtime_ownership}.rs` ; D répertoire/accusé et consommation du marqueur §13.3-B ; B fournit le profil/lock et les preuves techniques, sans prise de propriété de ses fichiers par C. Les noms de modules nouveaux sont des ajouts à l’ownership C/D §14, pas un droit d’écrire les fichiers de T/B.

**Oracles T :** transaction réelle par étape ; legacy active/projet ou compteur erroné/absence ack D/inventaire incomplet/non-VALID/profil inconnu ⇒ aucune ouverture ni création implicite. Bindings multiples d’une release, UID tiers/même nom/Service UID substitué, CAS/fence expiré **pendant l’attente du verrou**, ancienne Revision, observation >5 s ou route non Ready ⇒ refus. Préparation autorisée à zéro sans enrollment cible ; report/lease/ancien event seuls ne passent jamais active. Ouverture concurrente à révocation/grant/release, reprise après chacun des commits et crash après apply avant report ⇒ pas de double dispatch ni remise en legacy, historique/engagements conservés. Hooks de mutation sur binding non matérialisé ⇒ pas d’insertion. Premier invoke seulement après autorité/observations courantes, aucun warm-up ; preuve réelle de propriété/coupure distincte d’un test SQL ou d’un HTTP mock.

**Limite de ce complément et ordre de publication :** ratification humaine de §13.3, puis implémentation C/D coordonnée et oracles T, avant ouverture effective ; les gates §15/B5/E restent indépendantes. Le ledger signale aussi le **gap n°9 (bootstrap du caller source)** : il n’est pas arbitré par les trois présents blocs. Aucun caller legacy sans registre/epoch authoritative ne devient autorisé par l’accusé D, le permis de préparation ou un tombstone `legacy_fence`. En attendant sa décision distincte, conserver le refus source ; ne pas prétendre qu’ouvrir une cible résout ce bootstrap. Cette annexe ne ferme ni 0009/0010 ni les APP-xx et ne vaut aucun GO runtime.

#### 13.4-A — Gap n°9 : caller runtime déjà migré et vivant, jamais une assertion legacy

**Valeur proposée : retenir l’option (ii).** Un workload legacy non migré ne peut **pas** appeler un binding migré via `/runtime/invoke`, même s’il possède un certificat/session legacy valides. Le caller doit avoir achevé son propre cutover §13.3 et disposer d’une **nouvelle identité runtime** adossée au registre `current`. La migration d’une cible ne matérialise pas sa source ; ni Prepare, ni un backfill, ni la première requête ne créent des permissions ou une ligne source en secours. `/invoke` legacy garde la sémantique non migrée et ne devient pas un pont vers la cible runtime.

Preuve exacte de source, à vérifier **avant** émission du ticket ou forwarding :

1. Certificat client vérifié et session workload courante concordante, `CallOrigin::Background`, source distincte de la cible selon B1. D retrouve **par son store runtime** le fingerprint, l’instance, le binding et le projet source ; aucune origine/projet source tiré d’une déclaration cible/caller. Entrée legacy seule ⇒ `RUNTIME_LEGACY_DISABLED` pour cette voie cross-legacy→runtime, sans changer les raisons des parcours legacy non migrés. Entrée runtime close/expirée, ambiguïté des stores ou panne ⇒ refus selon §13.1-D, jamais fallback.
2. D recoupe son répertoire de cutover, puis fait `get_binding(lazaret, source_project_id, source_binding_id, ByInstanceId{source_instance_id})`. Il exige binding runtime actif et autorité/grants/epoch courants ; une instance unique `kind=pod,state=current`, la correspondance certificat/store/Pod UID/namespace/ServiceAccount UID/Revision/release/génération/grant, le fence d’un bail vivant et la fraîcheur ≤5 s selon §13.2. Un snapshot absent/incomplet/fermé/périmé n’est pas une invitation à matérialiser une source.
3. D construit source/epoch et le ticket à partir de cette autorité, après les contrôles ACL ∩ consentement ∩ politique source/cible, dans le budget/délai déjà gelé. C revalide le registre et les compteurs source/cible au début de l’effet B4 sous les verrous communs ; le fait que D soit authentifié ne dispense pas du registre source. Aucun contexte plugin, ancien certificat ou seul droit d’admin n’y supplée.

`legacy_fence` garde **uniquement** son sens §13.2 : tombstone de révocation d’une identité historique, sans Pod/Revision attestés. Il ne peut être `current`, n’est pas converti en `pod` et ne fournit pas un epoch source autorisant. L’option (iii), assertion D + legacy_fence sans registre current, est donc exclue. L’option (i), import d’un Pod historique au Prepare, n’est pas retenue : un Pod legacy sans chaîne Serving et preuve projetée conformes ne reçoit ni Revision fictive ni identité runtime par équivalence ; aucun patch de Pod enfant, échange silencieux de certificat ou backfill de grants. Une telle prise en charge serait un autre amendement, pas une latitude de C/D.

**Bootstrap et reprise exacts — limite de disponibilité à ratifier :**

- L’entrée d’un scénario invoke exige au moins **un caller runtime déjà vivant et qualifié indépendamment de la cible en cours de migration**. L’inventaire de campagne identifie projet/binding/instance/Pod UID/Revision de ce caller et vérifie sa preuve courante, sans prétendre l’avoir créé par cet inventaire. Sa migration antérieure ne suffit pas à prouver sa présence actuelle.
- Pour convertir un caller legacy : exécuter pour **son binding** Fence → Prepare → Open, avec refus D préalable et invalidation des anciennes identités. Seul un **vrai nouveau Pod Serving**, observé/enregistré par C et enrôlé par D selon §13.2, peut ensuite fournir sa session runtime. Ce Pod n’est pas enregistré comme héritier autorisé de l’ancien UUID/certificat. La préparation et l’ouverture de ce binding à zéro ne le démarrent pas et ne garantissent donc pas à elles seules un caller utilisable.
- **Aucun bootstrap autonome depuis un ensemble tout legacy/tout à zéro n’est livré par ce choix.** Si aucun caller runtime n’est déjà vivant, le premier invoke reste **NO-GO**, même après migration de tous les bindings. Ne pas résoudre cette absence par self-invoke, URL de warm-up, min/initial-scale augmenté, Pod seed/host fabriqué, session fictive ou dérogation aux grants. Une voie d’amorçage indépendante exige une décision humaine distincte ; elle n’est pas présentée comme existante. Ce choix ferme l’ambiguïté de confiance, pas un problème général de liveness.
- À la perte/expiration/retrait du caller, à son retour à zéro ou après restauration des registres, refaire les contrôles courants ; aucune réutilisation d’un ancien snapshot/session/epoch ou du tombstone pour reprendre. Un autre caller déjà qualifié peut prendre le relais selon B1 ; sinon rester fermé. Préserver une activité réelle ne permet ni keepalive artificiel ni min-replica caché.

**Justification :** c’est la seule option proposée qui conserve sans nouvelle forme d’identité les autorités et chaînes de preuve ratifiées. La présence d’une ligne `apparatus_runtime_bindings` marque déjà le cutover §13.3-B ; une matérialisation source-only cachée ne peut pas simultanément laisser le binding « legacy non migré ». Le coût assumé est l’absence de cold-start global autonome, non un allow inventé sur absence. **Surfaces :** C `services/Manifesto/infra/src/apparatus_runtime/runtime_control/begin.rs` et lecture du registre, `workers/apparatus-operator/src/runtime_observation.rs` ; D `services/Lazaret/application/src/runtime.rs`, classification de l’identité et futur handler invoke/runtime, store/adapter existants ; E choisit un caller **réel** dans son inventaire, sans écrire de code seed. Aucun nouveau schéma/migration requis par ce bloc.

**Oracles T :** caller legacy valable + cible migrée ⇒ refus avant ticket/forward/begin, zéro matérialisation et zéro requête de création ; assertion D authentifiée et tombstone legacy_fence seuls ⇒ refus. Contrôle positif avec caller runtime distinct, réellement current et cible à zéro. Migrations source puis cible, certificat legacy après cutover, nouvel enrollment, absence de Pod après Open, ensemble tout à zéro, reboot/restauration et révocation entre ticket/begin ⇒ reprise fermée sans fallback. La fixture positive installe explicitement l’autorité source conforme ; elle ne fait pas passer son arrange pour un mécanisme de bootstrap produit. Les suites legacy non migrées conservent leurs oracles.

#### 13.4-B — Gap n°10 : attente metadata bornée, pas de receipt ni d’adoption après crash

**Valeur proposée : retenir l’option (i).** Conserver `RuntimeObservationV1` complet et strict. Aucune observation ServiceUID-seul, Revision UID/name vide, URL factice, booléen de propriété, valeur bidon ou neuvième route. Pas de receipt signé/persisté additionnel : un tel protocole serait une nouvelle décision. La réponse réussie de création donne seulement au **même processus/tentative** une provenance transitoire permettant d’attendre les métadonnées puis de faire le premier report complet. Elle ne vaut pas propriété durable après perte de ce contexte.

**Ordre avec §13.3-C :** Fence et coupure/drain terminés, Prepare commité à closed avec permis valide ; le contrôleur déjà habilité acquiert son bail/fence, relit l’autorité et les preuves d’admission/profil, puis peut faire **une seule création** du parent absent. Pendant cette fenêtre, aucune ouverture/invoke/enrollment cible n’est accordée. La branche générale du contrôleur ne traite pas un binding prepared comme un closed ordinaire à supprimer : seule la tâche de préparation explicite possède cette exception bornée. Le draft `ServingRuntimeBridge::reconcile_parent`, encore limité à active versus remove_closed, doit respecter cette distinction déjà ratifiée ; ce constat n’autorise pas A à le corriger.

**Bornes proposées de cette seule attente de préparation :**

- `t0` = instant monotone **avant** le POST create ; deadline totale `t0+30_000 ms`, création, lectures, contrôle du bail et premier report/confirmation inclus. Aucun reset à la réception du Service ou entre tentatives, pas de délai libre du publisher. Ce budget administratif ne prolonge ni un ticket, ni la deadline B5 d’un invoke, ni le seuil startup/enrollment métier.
- Après réponse create **2xx complète avec UID/resourceVersion non vides**, conserver en mémoire namespace/nom/UID/resourceVersion retournés, projet/binding, migration/permis, contexte métier et fence. Aucun fichier/log/label/body ne peut recréer ce contexte comme preuve de création après redémarrage. Le resourceVersion n’est pas un entier local à incrémenter : chaque nouvelle lecture le reprend sur le même UID.
- Lire le parent, sa Configuration et la Revision désirée par rounds espacés d’au moins **1_000 ms**, au plus **28 rounds**. Chaque round complet de lectures cluster est borné à **2_000 ms**, tronqué au budget restant de découverte ; arrêter cette découverte au plus tard à `t0+28_000 ms` pour réserver jusqu’à **2_000 ms** au report/confirmation writer final. Les appels inachevés sont abandonnés localement à échéance ; aucune annulation physique rétroactive de l’API n’est revendiquée. Pas de watch/reconnexion ou poll infini caché.
- Conserver TTL/renouvellement du bail **10_000/3_000 ms**, mêmes preuves et contrôles §13.1-C ; le renouvellement est coordonné avec la tentative, pas un second writer. Toute consultation writer garde son budget §13.1/B5 de 2 s, sans dépasser la deadline globale. Erreur/perte de bail/fence, CAS/contexte métier différent, révocation, admission/profil incohérent ou horloge incertaine ⇒ abandon immédiat ; aucun renew après expiration pour continuer la même tentative.

**Ce qui peut être reporté :** chaque lecture vérifie que le parent garde **l’UID issu de cette réponse create**, dans le namespace/nom plateforme attendus. Suivre la vraie chaîne de contrôle Service → Configuration → Revision par UID ; sélectionner la Revision du template/rélease/génération désirés, pas une ancienne `latestReadyRevision` ou la première Revision listée. Recouper générations API observées, image admise, release et profil ; prendre l’endpoint réellement observé et approuvé par le profil privé. Pas d’inférence de propriété à partir des seuls labels/fence. Une suppression/recréation du parent ou de sa chaîne pendant l’attente invalide la tentative. Ne pas muter les enfants Serving pour obtenir plus vite les champs.

Dès que **tous** les champs requis existent et concordent, le contrôleur capture une observation complète, datée de cette lecture réelle, puis envoie le PUT observation fenced existant. `route_ready=false` reste une valeur honnête acceptable pour enregistrer ce premier ensemble complet : il n’est pas nécessaire d’attendre Ready pour fixer l’UID, mais on ne remplace aucun champ requis par une valeur supposée. **Ce report ne permet pas Open** tant que la route n’est pas réellement Ready et fraîche. Le writer lie l’UID au plan de préparation et ne retourne succès qu’après persistance cohérente de l’observation/propriété selon §13.3-C. Un report complet enregistré est le premier point de propriété durable ; la réponse create seule ne l’est pas.

En cas de réponse PUT ambiguë, aucune seconde création, nouveau nom, réécriture de date ou report fictif : au plus **une relecture GET binding** de confirmation, dans le budget total de 2 s de cette étape et les 30 s globales, si du temps reste. Elle ne confirme la propriété que si l’autorité contient l’observation complète du **même UID**, du même plan/contexte/fence, sans révocation intervenue ; sinon suspendre. Une requête PUT ayant déjà épuisé ces budgets n’ouvre pas une fenêtre supplémentaire de confirmation. Les règles de retry metadata du gel ne sont pas étendues à l’invoke/effet.

**Ré-observation après le premier report :** le parent UID est désormais connu par l’autorité, jamais par le seul contexte transitoire. La boucle existante peut relire ce même parent et ses enfants, nominalement toutes les **2_000 ms**, et publier des observations complètes réellement nouvelles avec CAS/bail courants. Chaque itération est bornée (lectures ≤2 s puis consultation/report writer ≤2 s dans le budget de contrôle), sans heartbeat qui rafraîchit une vieille capture. Toute absence, erreur ou retard laisse expirer la validité ≤5 s et ferme les autorisations ; aucune garantie de disponibilité n’est déduite de cette cadence. Un UID durable ne remplace ni une route Ready ni une observation fraîche. Open reste une **commande séparée**, après GET/relecture writer courants et toutes ses préconditions §13.3-C ; il n’est jamais déclenché par le seul succès create/report.

Son existence possible ne devient pas une propriété par simple relecture au prochain tick. Les 30 s bornent l’attente, pas la durée de vie du résiduel ; aucun effacement automatique à échéance. Après redémarrage, un report effectivement commité avant le crash permet seulement la reprise UID connu ; sans cette preuve durable, rester inconnu.

Propriété indémontrable ⇒ STOP, pas adoption, force ou suppression aveugle.

Après résolution approuvée et absence/état des objets vérifiés, nouvel acte de préparation avec contexte/CAS courants, historique conservé et éventuelle nouvelle création autorisée ; jamais injection du parent inconnu dans le registre, réemploi du permis invalide, reset des compteurs ou relance de Open ancien. #### 13.5-A — Gap n°11 : attestation Adm-A par acte, transportée mais non créée par l’operator

**Valeur proposée : retenir l’option (ii), avec challenge writer et preuve signée courte.** Adm-A exporte une attestation de sa décision `VALID` courante pour **un** acte Prepare **ou** Open ; l’operator/runner transporte ces octets, Manifesto les vérifie hors ligne avec une clé publique configurée et les consomme dans sa transaction. Une signature de transport de l’operator, un rôle projector, son booléen `signature_verified`, un JSON de runner ou l’inscription du digest dans `apparatus_bindings` ne remplacent jamais cette attestation. Manifesto ne produit, ne renouvelle et ne décrète pas `VALID`.

**Écart réel à ne pas masquer :** `workers/apparatus-operator/src/admission.rs::AdmissionRecord` porte digest/politique/rapport et références CRI/enveloppe ; `runtime_projection.rs::AdmittedServingImage::verify` consulte ce store et vérifie la signature de l’enveloppe. `admit.rs::EnvelopeDocument` ne contient que descripteur et image CRI : sa signature Cosign actuelle n’est **pas déjà** une attestation portable fraîche de décision Adm-A, de rapport, de profil et d’acte de maintenance. L’export signé décrit ici est un **nouveau format à implémenter sous l’autorité Adm-A**, pas une propriété inventée de l’enveloppe historique. L’option (i) n’est pas ajoutée en parallèle : ni RPC de lecture d’un store operator, ni mount de son JSON mutable dans Manifesto, ni projection autorisante rafraîchie par le contrôleur.

**Formes exactes proposées**, réservées à la maintenance, sans ajout aux huit DTO/routes : mêmes Uuid/Counter/UnixMs/Digest, Options explicites et règles de parsing strict §13.1. Le challenge est émis/persisté par le writer Manifesto, jamais choisi dans une requête caller.

```rust
RuntimeAdmissionActionV1 = Prepare | Open; // wire: prepare | open
RuntimeAdmissionChallengeV1 {
    schema_version: u16, challenge_id: Uuid, authority_id: Uuid, installation_id: Uuid,
    action: RuntimeAdmissionActionV1, migration_id: Uuid, project_id: Uuid, binding_id: Uuid,
    expected: RuntimeCasV1, release: RuntimeDigestV1,
    profile: String, profile_lock_sha256: RuntimeDigestV1, inventory_sha256: RuntimeDigestV1,
    service_uid: Option<String>, revision_uid: Option<String>,
    issued_at_unix_ms: RuntimeUnixMsV1, expires_at_unix_ms: RuntimeUnixMsV1
}
RuntimeAdmissionAttestationV1 {
    schema_version: u16, iss: String, aud: String, purpose: String,
    jti: Uuid, iat: i64, exp: i64, challenge: RuntimeAdmissionChallengeV1,
    record_id: Uuid, admission_revision: RuntimeCounterV1, policy_id: String,
    report_sha256: RuntimeDigestV1, envelope_reference: String, cri_image: String,
    observed_at_unix_ms: RuntimeUnixMsV1, valid_until_unix_ms: RuntimeUnixMsV1
}
```

`authority_id` identifie le store/émetteur Adm-A de confiance ; `installation_id` le writer/déploiement Manifesto consommateur. Ils sont provisionnés par B/setup, jamais découverts depuis la preuve. `service_uid/revision_uid=null` pour Prepare ; ils sont non nuls et égaux à la commande/observation authoritative pour Open. Tous les champs du challenge doivent être **identiques** à l’intention writer enregistrée, y compris action, migration, full CAS, projet/binding, release et hashes ; aucun wildcard « valable pour ce digest partout ». Une seule intention non consommée par migration/action ; nouveau challenge invalide le précédent, sans remise à zéro des compteurs. Son expiration est fixée à **60_000 ms** après l’horloge DB d’émission. Émettre un challenge n’active rien et ne vaut ni Prepare ni Open.

La preuve n’a pas de champ booléen `valid`/`signature_verified` : son purpose signifie « Adm-A a constaté la décision VALID courante pour ces preuves et ce challenge ». Seul le chemin Adm-A ayant réellement vérifié cette décision peut la signer. `record_id` est l’identifiant **du record Adm-A**, pas un UID de ressource de déploiement ni un UUID inventé par Manifesto. `admission_revision>=1`, monotone et durable par autorité/descripteur, change sur toute modification de décision/politique/rapport/enveloppe/CRI ; tombstone et identité conservés, jamais compteur local de processus, mtime ou reset après restauration. Les métadonnées de record/révision sont un ajout au store Adm-A à réaliser avant émission ; un ancien JSON sans ces garanties n’est pas promu implicitement en preuve v1.

`policy_id` doit être dans la politique explicitement approuvée par le consommateur ; profil initial : **`apparatus-p4-conformance/v1`**, valeur actuelle de `conformance.rs::POLICY_ID`. Le digest descripteur signé est `challenge.release`, distinct de `report_sha256` et du digest de `envelope_reference`. Référence enveloppe OCI et image CRI doivent être pinées `…@sha256:…`, canoniques, ≤2048 octets chacune et conformes aux dépôts autorisés du profil ; pas de tag, substitution ou téléchargement arbitraire par Manifesto. `profile`/UID gardent les bornes §13.2 ; policy_id ASCII ≤128. La preuve compacte entière est bornée à **16 KiB**.

#### 13.5-B — Émetteur, clés, fraîcheur et limites de confiance

**Writer de la décision et de la preuve = Adm-A**, sous l’identité admission/signature P4 autorisée ; le contrôleur ne reçoit aucun droit de mint. L’export relit le store Adm-A **authoritative protégé**, pas un cache operator chargé au démarrage. Il recoupe digest, politique, rapport attesté et décision VALID ; vérifie réellement la chaîne signée/enveloppe et son lien au CRI selon les gardes Adm-A/Cosign existantes. Présence d’un tag `.sig`, conformance de harness, catalogue Manifesto, réputation officielle/VERIFIED ou argument du runner ne suffisent pas. La clé de signature n’est accessible ni au build/publisher, ni au contrôleur, ni à Lazaret/Manifesto/plugin. Le split interne admission/signer non tranché par 0008 n’est pas décidé ici : le signer approuvé signe exclusivement l’assertion émise par Adm-A, pas un payload brut proposé par le contrôleur.

L’export exige une source sérialisée : **un seul writer Adm-A pour l’authority_id**, verrou exclusif inter-processus sur la décision persistée et relecture de sa révision après toute vérification lente. Toutes les mutations Adm-A et l’émission participent à ce même verrou ; stores clonés, replicas cache, writers concurrents non fenced ou restauration remettant les révisions à zéro ⇒ pas d’émission. Après validation coûteuse, le dernier contrôle de décision/révision et l’émission sont cohérents sous ce verrou ; signature bornée à **2 s**, sans prolongation si le provider tarde. Le store et ce verrou restent hors Manifesto. L’implementation doit prouver ce single-writer/stockage, et ne pas supposer qu’un mutex privé de chaque processus protège un fichier partagé.

**Profil JWS fermé proposé :** `iss="urn:aiforall:apparatus:adm-a:v1"`, `aud="urn:aiforall:manifesto:apparatus-runtime:materialization:v1"`, `purpose="apparatus.runtime.admission-materialization.v1"`, `schema_version=1` ; `jti=challenge.challenge_id`. Header protégé à seules clés `alg="RS256"`, `typ="apparatus-admission-materialization+jwt"`, `kid` requis. Signature RSA **3072 bits**, exposant **65537**, clé/purpose dédiés à cet export Adm-A ; pas de réemploi IAM/session/invoke/enrollment, ni assimilation de la clé Cosign existante à ce nouveau purpose. `kid="ara-v1-" + BASE64URL_NO_PAD(SHA256(RFC7638_JWK_THUMBPRINT_INPUT))`, même calcul RFC7638 que §13.1-B sur la clé publique, sans modifier ses vecteurs/profils existants. Payload UTF-8/JCS strict ; version/champs/doublons/algorithme/typ inconnus rejetés ; pas de `none`, HS256, `jku/jwk/x5u` ou clé indiquée par l’émetteur non approuvé.

Setup Manifesto charge une **liste publique épinglée** `(authority_id, installation_id, iss, aud, purpose, kid, clé)` depuis la configuration B. Aucune découverte HTTP/JWKS dynamique, appel IAM, token Transit ni clé privée dans Manifesto. Rotation explicite : clé suivante approuvée/configurée chez les consommateurs **avant** première émission ; ancienne retirée au plus tard **5 s après** sa dernière émission, hors révocation d’urgence immédiate. Aucun besoin de garder une ancienne clé 60 s : un challenge n’est pas une preuve signée valable 60 s. Clé inconnue/révoquée, configuration incomplète ou indisponibilité provider ⇒ fermé, jamais nouvelle tentative avec un autre algorithme. L’accès Transit et le TCB restent sous les responsabilités/gates 0008, pas une qualification de Transit dev.

**Fraîcheur :** `observed_at_unix_ms` date le dernier contrôle authoritative Adm-A, après les vérifications lentes ; `valid_until=min(observed_at+5000, challenge.expires_at)`. `iat=floor(observed_at/1000)`, `exp=floor(valid_until/1000)`, `exp>iat`, sans grâce. Au writer après verrou : `observed_at<=db_clock<valid_until`, `db_clock_seconds<exp` et challenge non expiré, avec horloges de confiance ; toute date future/discordance ferme. Signer, transporter, attendre un verrou ou retenter ne rafraîchit aucune date. Une attestation expirée n’est jamais « re-signée » par le relais ; Adm-A doit refaire le contrôle. Cette fenêtre ≤5 s est un coût de disponibilité administratif, pas un SLO ni une preuve instantanée globale.

**Profil séparé :** la signature lie le hash du profil au challenge pour empêcher sa substitution, mais **Adm-A ne devient pas l’autorité de qualification du sandbox/mesh/limites**. Manifesto vérifie séparément que `profile`/`profile_lock_sha256` correspondent au lock B approuvé réellement configuré et aux préconditions §13.3. Attestation VALID sans ce lock ⇒ refus ; lock valide sans attestation Adm-A ⇒ refus. Aucun rôle de service ne fusionne ces deux preuves.

#### 13.5-C — Injection, consommation transactionnelle et ordre Fence → Prepare → Open

Seam proposée côté Manifesto, construite **une fois dans setup**, sans importer le store/le domaine operator ou IAM :

```rust
pub trait RuntimeAdmissionProofVerifier: Send + Sync {
    fn verify(
        &self,
        expected: &RuntimeAdmissionChallengeV1,
        compact_jws: &str,
        db_now: RuntimeUnixMsV1,
    ) -> Result<VerifiedRuntimeAdmissionV1, RuntimeErrorCodeV1>;
}
```

`VerifiedRuntimeAdmissionV1` est une capacité locale immuable à champs privés, **non Deserialize**, produite seulement après vérification par l’adapter réel. Elle porte les claims vérifiés, kid et empreinte du JWS ; elle ne signifie pas à elle seule « ouvrir ». Le writer recoupe toujours nonce/intention, phase/CAS, confiance actuelle de la clé, dates et état négatif local. Implémentation par défaut `RejectRuntimeAdmissionProofVerifier` : Prepare/Open **désactivés**, pas un `is_valid(digest)` retournant true. Le vérificateur de clé publique est pur/local ; il ne lance ni Cosign/ORAS, ni lecture de store distant, ni appel Transit/IAM. Aucun I/O d’autorité/signature externe sous les verrous SQL Manifesto.

1. **Fence reste possible sans preuve positive** : fermer et matérialiser closed selon §13.3 ne doit pas dépendre de l’admissibilité de la release. Le refus D et le canal/acteur de maintenance restent obligatoires. La preuve d’admission ne remplace ni l’accusé D typé ni la preuve de coupure/drain.
2. **Avant Prepare**, setup/runner demande localement un challenge writer pour le plan fermé/fenced exact. Il en transmet le contenu à l’export privilégié Adm-A par le parcours de Job/commande de maintenance existant, sans nouveau serveur HTTP. Ce contenu est un challenge, pas un ordre de rendre VALID. Adm-A produit éventuellement le JWS ; l’operator/runner le relaie dans le contexte de maintenance de l’acte. Un fichier/JSON n’est ici que le **conteneur d’octets non fiables** ; signature, identité opérateur et ack D sont vérifiés séparément. Tant que cet export/canal réel ou la clé épinglée manque, aucun fallback : maintien des ports désactivés.
3. **Prepare transactionnel** : relire intention/challenge et full CAS après les verrous, vérifier la preuve exacte/fraîche et le lock B courant, puis exécuter uniquement les préconditions/écritures §13.3-C. Consommer le challenge et journaliser `(challenge_id, empreinte JWS, record_id, admission_revision, politique, rapport, enveloppe, CRI, kid, validité)` dans le **même commit** que prepared/permis. Pas de double commit « preuve acceptée » puis préparation non protégée. Ne pas logguer de secret ou créer une clé privée ; la preuve est publique mais le journal courant privilégie ses identifiants/hashes.
4. **Création/observation** : seulement après Prepare, selon §13.4-B et son budget create→Revision indépendant. L’operator garde ses vérifications Adm-A/Cosign avant toute mutation externe ; l’attestation acceptée par Manifesto ne lui donne aucun skip. L’expiration de cette preuve Prepare pendant les 30 s de préparation n’est ni une permission prolongée ni un renouvellement tacite : Open exigera une **nouvelle** preuve. L’image/enveloppe doivent rester celles attachées à la préparation.
5. **Avant Open**, après Service UID enregistré et observation complète, émettre un **nouveau challenge `action=open`** sur le CAS courant et ces UID, puis obtenir une nouvelle attestation Adm-A. Une preuve Prepare, même encore valide, est inutilisable. Record/politique/rapport/enveloppe/CRI doivent correspondre à ceux de Prepare ; une décision révisée ou un mapping changé impose une reprise de préparation approuvée, pas une substitution d’image sous la même génération. Le profil B et toutes les conditions §13.3/§13.4 sont relus. Modifier le CAS pendant l’export rend la tentative stale ; ne jamais ignorer projection_version ni allonger la fraîcheur pour faire passer Open.
6. **Open transactionnel** : même vérification/consommation atomique avec son commit d’ouverture. Un challenge consommé ne peut servir à un autre acte ; reprise après ack perdu = lecture du journal/état courant, pas seconde ouverture ni création. Un rollback SQL n’autorise pas à réutiliser aveuglément une preuve : l’opérateur reprend explicitement dans les budgets restants ou obtient un nouveau challenge. Aucun retry métier automatique. Les autorisations ultérieures gardent les lectures writer et règles B1–B4 ; la preuve n’est pas un bearer d’invoke et ne crée aucune identité source/cible.

Stockage **additif local C** des intentions/challenges consommés et d’un guard négatif par `(authority_id, release)` : révision Adm-A maximale déjà vue, record_id stable et blocage explicite. Révision inférieure, changement d’identité de record inexpliqué, nonce/jti/empreinte contradictoires ⇒ refus ; jamais de retour à un compteur initial après purge/restore. Les preuves expirées ne permettent pas de purger les fences/revocations. Après restauration C ou Adm-A, suspendre émission et Prepare/Open, invalider tous les challenges/permis encore pendants et rapprocher identités, révisions/guards et journal avant réactivation ; un sceau/JSON restauré seul ne prouve pas les high-watermarks actuels. Incapacité à établir la monotonie/provenance ⇒ maintien désactivé, jamais reset de record_id/révision pour repartir. Challenge/anti-replay/guard sont des données internes de maintenance : aucun champ ajouté à RuntimeBindingSnapshotV1 ou aux huit requêtes.

**Révocation et limite distribuée, sans dégrader 0005 :** une signature récente n’est pas un oracle de validité éternelle ou une transaction entre Adm-A et C. Pour rendre une admission antérieure inadmissible, la procédure de retrait suspend d’abord l’émission de preuves pour ce record, puis **bloque/fence dans le writer C tous ses bindings et intentions, avant le commit de retrait Adm-A**. Le guard négatif par release ferme également les nouvelles préparations/Open concurrents ; accusé de fermeture durable requis via le canal de maintenance de confiance, pas bool_ack. C ne devient pas source VALID en imposant ce refus local. L’effet de révocation pour les bindings est le commit writer : pas d’attente FGA/cleanup, engagements antérieurs seulement selon B4. Aucun nouveau protocole HTTP de révocation n’est ajouté : les actes locaux de fermeture/maintenance portent ce parcours. ### Rollback et restrictions résiduelles

Au premier échec d'autorité, mismatch génération/UID, perte de bail, compatibilité mTLS/sandbox, borne non prouvée ou bypass : **fermer/fencer le binding dans le writer, refuser les nouveaux tickets/accept/effets, conserver les preuves et données, drainer les seuls engagements déjà admis**. Un objet/Pod résiduel n'est pas réautorisé ; les contrôleurs standards gèrent sa terminaison. Ne pas remplacer cette fermeture par Flux suspend.

Rollback de code/config : revenir seulement à une version qui comprend le marqueur de fermeture/tombstones et refuse le runtime migré. Si le binaire précédent réactive le locator digest ou ignore les epochs, **ne pas le redéployer pour ce binding** : conserver le mode fermé/maintenance. Aucune réouverture automatique du partage digest, de HTTP clair, d'un dispatch local ou d'un profil sans sandbox. Rollback d'une release uniquement si schéma externe compatible et nouvelle génération/epoch explicitement approuvée ; jamais rollback SQL destructif ou réemploi d'identités anciennes. Perte de disponibilité assumée plutôt que fallback permissif.

Restrictions à accepter : caller workload vivant (pas premier appel browser autonome) ; requête anciennement autorisée pouvant encore réveiller du compute après révocation mais aucun nouvel effet admis ; effet réservé avant révocation pouvant finir/être indéterminé ; objets résiduels transitoires possibles lors d'apply en vol, sans résurrection d'autorisation ; pas d'exactly-once, purge, workload non HTTP ou coût système zéro ; pins et preuve gVisor/mesh non fournis par A, donc **aucune exposition hostile ni GO de publication sans ces verrous**. Une exigence plus forte nécessite un amendement humain, pas une promesse de l'implémentation.
