# IAM → OAuthConnect v2 — contrat de raccordement

Date : 2026-11-08. Base inspectée : `b028c2fdc213eee26f3e009392301955e920ce5f`. Canon secondaire de [ADR-0413](../adr/0413-oauthconnect-multi-instances-profils.md), **Accepted / Partial**, en application du [contrat principal §§3–7](oauthconnect-multi-instances.md#5-adaptation-iam-et-contexte-oidc) et de 0412. Ce document borne le lot utilisateur « raccordons IAM » ; il ne ratifie aucun nouveau choix métier et ne constate aucune implémentation IAM.

## 1. Autorité et périmètre

- Déjà acceptés : nonce IAM indépendant et durable, API v2 authorize+complete, consommation writer avant complétion, migration additive nullable, LOGIN/LINK/RELINK uniformes et aucun fallback v1. Le présent texte précise les coutures et l'ordre d'exécution de ces invariants, pas une nouvelle frontière : **aucune nouvelle ADR** et aucun changement de Statut/Réalité de 0413.
- Connect est un acquis du lot précédent : le parent rapporte **295 PASS**. Ne pas rouvrir ses profils, OIDC/JWKS, AppState HMAC-only ou son listener ; l'[annexe de frontière service, dont §10](oauthconnect-oidc-service-boundary.md#10-amendement--appstate-hmac-only-sans-autorité-jwt), reste applicable. Ces preuves ne sont pas réexécutées ici et ne sont pas des preuves IAM.
- SDK `93b890ff7b821e9cb2e7d0aeb81957d098778a2f` immuable. IAM dépend du contrat vendor-neutral, jamais de `oauth-connect-infra`, JSONPath ou `openidconnect`. Pas de nouveau profil, claim riche, API métier, autorité JWT, cache de nonce ou harness.
- Slugs, UUID, clé `(provider/instance, external_id)`, règles d'email, routes navigateur et intentions restent inchangés. Ni migration `provider_tokens`, ni bulk relinking, ni bascule/configuration de déploiement, ni retrait des services legacy, ni reset DB. L'équivalence GitLab `sub == ancien id.to_string()` reste une condition **externe** de cutover, pas une preuve à fabriquer dans IAM. Ce contrat/plan QA n'autorise implicitement aucune extension de manifeste, configuration déployée ou SDK ; un besoin nouveau de cette nature retourne au parent pour autorisation distincte.

## 2. Types et coutures de domaine

Dans `services/IAMRusty/domain/src/entity/oauth_transaction.rs` :

- `OAuthTransaction` reçoit `authentication_nonce: Option<String>` : valeur originale nécessaire à la complétion, pas seulement son hash. `None` représente les lignes pré-migration, jamais un BEGIN v2 réussi.
- `BegunOAuthTransaction` reçoit `authentication_nonce: String`, en conservant `code_challenge: Option<String>` et `code_challenge_method: Option<String>`. Il porte le contexte autorisé pour START, **jamais** le verifier. Supprimer le Debug dérivé qui révélerait le nouveau champ ; employer un Debug expurgé, y compris lorsque ce type est imbriqué dans une commande.
- `BeginOAuthTransaction` ne reçoit pas de nonce fourni par l'appelant. `ConsumeOAuthTransaction` ne reçoit ni nonce d'authentification attendu, ni verifier : le callback ne peut choisir ou réparer ces secrets.
- `OAuthTransaction::begin` et `ConsumedOAuthTransaction::consume` conservent leurs signatures repository/input et leurs erreurs existantes. Le port `OAuthTransactionWriteRepository::{create,consume,purge_expired}` conserve ses signatures ; sa documentation et ses implémentations précisent désormais la purge des **deux** secrets.
- La couture de complétion du domaine remplace l'ancien helper `ConsumedOAuthTransaction::exchange_code` :

```rust
pub async fn complete_authorization(
    &self,
    client: &dyn FederatedOAuthClient,
    code: &str,
) -> Result<idp_connect_contract::ProviderAuthentication, DomainError>
```

Ce helper construit `CompleteAuthorizationRequest` depuis le code reçu et **le redirect, le verifier et le nonce de sa transaction consommée**, puis appelle exactement une fois le port v2. Pas de paramètre public `expected_nonce`, d'extracteur public de secrets, de construction libre de `ConsumedOAuthTransaction`, de Clone ajouté ou de méthode retournant un couple de secrets. Le helper ne fait ni SQL, ni identification de compte, ni persistance des tokens. Conserver les conversions d'erreurs génériques existantes ; pas de JSON, code ou nonce dans le message d'erreur.

Le domaine réutilise `ProviderAuthentication` du contrat, dont `tokens` et `profile` sont déjà les types vendor-neutral réexportés par IAM. Pas de nouveau DTO concurrent, ni d'exposition d'ID token. La signature empruntée ne constitue pas une garantie linéaire du langage : les orchestrations ne l'appellent qu'une fois ; aucun retry, fallback ou seconde complétion sur la même capacité n'est autorisé.

## 3. BEGIN et START : données exactes et précédences

1. Conserver l'admission provider/registry, l'intention et la cible authentifiées, le state signé, le cookie navigateur et la politique de redirect existants. `OAuthRouteContext::begin` reste la couture HTTP vers le BEGIN de domaine.
2. Après validation des entrées de BEGIN, générer **32 octets OsRng indépendants**, encodés base64url sans padding. Génération distincte de celle du verifier PKCE ; aucune dérivation depuis state, nonce du state, cookie ou challenge. Le format canonique est exactement 43 caractères décodables en 32 octets et réencodables à l'identique.
3. Persister la transaction avec `Some(authentication_nonce)` et le verifier éventuel sur le writer **avant** de retourner `BegunOAuthTransaction` et avant tout appel authorize ou réponse START réussie. Échec de création : pas d'appel Connect, pas de succès/cookie présenté comme START réussi. Le nonce s'applique même à un provider OAuth sans PKCE ; aucun branchement GitHub/GitLab/OIDC dans IAM.
4. Les coutures `OAuthService::generate_authorize_url` et `LinkProviderUseCaseImpl::authorize_url` passent à `authorize_authentication(&AuthorizeAuthenticationRequest)`. Corps : `redirect_uri` et `state` inchangés, `nonce = begun.authentication_nonce`, `code_challenge` et `code_challenge_method` copiés ensemble depuis `begun` (les deux absents, ou challenge exact + `S256`). Ne jamais reconstruire le challenge ailleurs ni envoyer le verifier au START.
5. La base de l'instance reçoit le suffixe `/v2/authorize`. IAM ne modifie pas l'URL vendor retournée pour y ajouter un nonce : Connect l'ajoute pour OIDC et l'omet pour OAuth. **Ne pas exiger un paramètre query nonce pour tous les providers** dans le garde navigateur : IAM ne connaît pas leur profil. Conserver la vérification de provenance/allowlist de l'URL et `validate_authorization_pkce`, notamment les paires absentes, incomplètes, dupliquées, non demandées ou différentes.

Le nouveau nonce n'est pas ajouté au state, au cookie ou aux paramètres publics de callback. Sa présence dans l'URL d'autorisation OIDC est attendue ; ce n'est ni une autorisation de le journaliser, ni une source pour le nonce attendu au retour. Un échec authorize laisse une transaction abandonnée jusqu'au cleanup existant ; pas de suppression compensatoire ni de réemploi automatique.

## 4. Callback : writer, refus legacy et non-rejeu

Ordre obligatoire, identique pour LOGIN/LINK/RELINK :

1. Inspecter/vérifier le state signé, le provider de route, l'intention/cible, le cookie navigateur et le contexte de redirect selon 0412 **avant** tout effet writer. Un état/cookie malformed n'autorise aucune consommation. Aucun nouveau paramètre query ne fournit une autorité manquante.
2. Sur le writer, garder **tous** les prédicats actuels : hashes state/nonce de state/browser, provider, opération, cible, redirect, expiration exacte, `consumed_at IS NULL`, horloge primaire et `SELECT … FOR UPDATE`. Aucune lecture replica comme capacité. Ajouter seulement `authentication_nonce` à la projection des secrets de la ligne verrouillée ; ne pas filtrer les lignes legacy en ajoutant un prédicat `authentication_nonce IS NOT NULL`.
3. Pour une ligne correspondante non expirée, charger ses valeurs originales, puis faire dans la même transaction l'UPDATE `consumed_at = clock_timestamp(), pkce_verifier = NULL, authentication_nonce = NULL`. Commit **avant** retour du record de consommation. Si SQL/commit échoue, erreur de stockage expurgée, jamais de capacité ni d'appel externe, même si l'issue du commit est incertaine.
4. `ConsumedOAuthTransaction::consume` garde ses contrôles post-writer (`consumed_at`, correspondance et validité) et exige un nonce durable au format canonique. Alors seulement il construit la capacité privée. Le helper de complétion ne fabrique aucune valeur de secours ; ses éventuels gardes défensifs refusent avant I/O.

**Cas legacy/corrompu tranché pour l'implémentation** : nonce SQL NULL, vide, mal formé ou non canonique sur une ligne dont les bindings sont valides ⇒ **consommation et purge commitée, puis refus générique `InvalidTransaction` sans capacité**, nouveau START requis. Ce n'est pas un refus « avant SQL » : seul le writer connaît ce champ. Ne pas créer une prélecture, le recevoir du navigateur, le générer au callback, revenir en v1 ou laisser le verifier stocké pour une seconde tentative. Le second callback ne trouve plus de ligne consommable. Une ligne dont les bindings ne correspondent pas reste intacte ; une ligne expirée reste du ressort du cleanup.

Cette précédence prolonge le consume existant avant validation de capacité ; elle n'accorde aucun privilège à un ancien state. Elle ne réinitialise ni l'état sur échec Connect, ni l'expiration, ni le cookie pour rendre un callback rejouable. Aucun succès partiel n'est récupérable après timeout/erreur : il faut repartir d'un START.

**Réconciliation QA Q-2** : l'oracle SQL legacy est donc fixé **avant** les tests : après callback authentique correspondant, `consumed_at IS NOT NULL`, les deux secrets SQL NULL, zéro complete et zéro fabrication de nonce ; bindings incorrects/ligne expirée suivent les exceptions ci-dessus. Ne pas ajouter une restauration ou une garantie nouvelle d'annulation réseau après commit. Le refus sans nonce et le non-rejeu ne dépendent jamais d'un succès fournisseur.

## 6. Adapter HTTP IAM : v2, bornes et expurgation

Dans `infra/src/auth/http_connector.rs`, implémenter explicitement les deux méthodes **déjà présentes** du trait :

```rust
async fn authorize_authentication(
    &self, request: &AuthorizeAuthenticationRequest,
) -> Result<AuthorizeResponse, FederatedOAuthError>;
async fn complete_authorization(
    &self, request: &CompleteAuthorizationRequest,
) -> Result<ProviderAuthentication, FederatedOAuthError>;
```

- Utiliser `AUTHORIZE_AUTHENTICATION_PATH` et `COMPLETE_AUTHORIZATION_PATH`. La base configurée identifie l'instance (cible de déploiement : `/oauth-connect/{slug}`), le JSON ne choisit ni instance ni profil. Vérifier avant requête le format nonce et la cohérence PKCE déjà fixés par le contrat. Aucun appel v1 sur erreur HTTP, désérialisation, timeout ou refus de méthode v2 par un client legacy.
- Réutiliser le HMAC existant sur **POST / PATH complet / timestamp / octets JSON réellement envoyés**, fenêtre30s côté récepteur, clé propre à l'entrée. Signer le corps qui contient nonce/PKCE, pas une version reconstruite après signature ; ne pas réduire le PATH au suffixe. Conserver la normalisation héritée de clé HMAC et le Debug expurgé du connector.
- Conserver HTTPS vérifié et les racines additionnelles locales au client, les exceptions `SecurityMode` explicites et `redirect::Policy::none()`. Fixer connexion3s, conserver timeout total **10s par requête IAM→Connect, lecture comprise**. Ce timeout n'est pas la somme des délais des appels vendor exécutés par Connect ; il n'autorise ni retry ni garantie de succès pour tout scénario vendor lent. Aucun assouplissement TLS/global ni nouveau paramétrage ops.
- Remplacer la lecture `response.json()` non bornée par un reader privé avant `serde_json::from_slice`. Maximum lu/accepté **1 MiB**, avec comptage réel des octets reçus et arrêt avant accumulation au-delà ; `Content-Length` ne constitue pas la seule garde (absent, faux ou chunked). Si une compression est prise en charge, la limite porte aussi sur les octets décompressés ; ne pas annoncer gzip qualifié si le client actuel ne le décode pas. Une compression non prise en charge ne devient pas du JSON valide. Pas de `.text()`, `.bytes()` ou `.json()` préalable non borné, ni de dépendance sur l'implémentation Connect pour partager ce reader.
- Accepter seulement succès2xx + JSON décodable dans le DTO complet ; redirect3xx,401,autres erreurs, HTML, JSON tronqué et dépassement ⇒ catégorie `FederatedOAuthError` générique de l'opération, jamais résultat partiel. Ne pas lire/dumper le corps d'erreur pour l'expliquer ; ne pas propager les messages reqwest/serde contenant URL ou valeurs. Pas de nouveau code/enveloppe d'erreur publique.
- Tests sentinelles : code, verifier, nonce, tokens et corps Connect malveillant ne paraissent ni dans Debug des nouveaux types/commandes, ni dans les erreurs/logs ajoutés. Les logs de phase peuvent rester sans valeur sensible. Ne pas étendre ici cette correction en refonte générale des logs métier historiques.

**Compatibilité v1 hors parcours IAM** : conserver méthodes/DTO/constants v1 et defaults v2 refusants de `idp-connect-contract`. `GitHubConnect`, `GitLabConnect` et les preuves historiques de leur protocole restent consommateurs : ne pas supprimer ou réinterpréter leurs méthodes pour faire compiler IAM. L'adapter IAM peut garder ses méthodes v1 explicites pour compatibilité/tests ; aucune orchestration LOGIN/LINK/RELINK IAM ne les appelle ni n'utilise un default v1 comme validation OIDC. Le reader commun peut sécuriser les deux versions sans transformer v1 en fallback.
