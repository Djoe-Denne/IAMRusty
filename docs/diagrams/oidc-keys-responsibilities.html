OIDC · CLÉS, ROTATION ET RESPONSABILITÉS · 7 NOVEMBRE 2026

La clé privée reste chez le fournisseur

OAuthConnect est le client / RP : il vérifie les signatures avec un cache de clés publiques en RAM. Il ne génère, ne stocke ni ne renouvelle la clé privée RS256 du fournisseur.

Nouveau kid : seul NoMatchingKey peut demander un refresh borné, puis une nouvelle vérification du même ID token ; jamais de second POST du code. Une clé ancienne encore fraîche peut rester utilisable après un échec de refresh pour un autre kid. Révocation non instantanée ; aucune garantie de zéro interruption, même après restart.

Qui fait quoi dans le dépôt ?

configuration

Valide issuer, origines, scopes, PKCE et références de secrets.

setup · secrets / transport

Résout client_secret + HMAC via SDK/OpenBao ou direct au boot ; HTTP de confiance, TLS/CA.

setup · mixed / app

Catalogue mixte et démarrage avant écoute : tranche C encore refusante, non livrée.

oidc · callback

Discovery et HTTP borné ; garde chaque URL avant I/O, y compris le JWKS interne.

oidc · protocol

Client standard ; métadonnées épinglées + snapshot JWKS retenu ; auth du token endpoint.

oidc · cache

Snapshot public en RAM, TTL/cooldown et single-flight local ; aucune rotation de clé privée.

oidc · verify

Signature RS256, issuer/audience/temps, azp, nbf, nonce et at_hash s’il est présent.

oidc · profile

Sub exact, profil normalisé ; fusion UserInfo avec contrôle du subject et des conflits.

http

Registry et routes v2 ; HMAC par instance sur PATH complet. Pas un serveur JWKS fournisseur.

IAM

Comptes UUID, liens et transactions. Adaptation v2 + nonce durable futurs, hors de ce lot.

Ne pas confondre : RS256 fournisseur = signature d’identité ; client_secret = auth au token endpoint ; HMAC IAM→Connect = secret S2S ; JWT IAM = clés de la plateforme ; TLS/CA = confiance transport. OpenBao résout les secrets OAuthConnect, pas son cache JWKS. GitHub en profil OAuth n’utilise pas de JWKS d’identité.

Réalité / déploiement : code OIDC/cache et router présents au canon ; composition C encore refusante. Compose conserve GitHubConnect/GitLabConnect et leurs URLs legacy ; l’overlay oauth-proof utilise un simulateur, pas une preuve GitLab live. Pas de nest OAuthConnect dans le monolithe inspecté. ADR0413 : Accepted / Partial ; aucun cutover ni runtime qualifié.

Responsabilité opérateur : GitLab.com → opérateur SaaS ; GitLab self-managed → Ops GitLab selon sa version et son mécanisme officiel. Emplacement privé, calendrier et chevauchement réels non établis ici. Changer les clés sous le même issuer n’est pas changer l’autorité : ne pas remplacer l’issuer sous le même slug.
