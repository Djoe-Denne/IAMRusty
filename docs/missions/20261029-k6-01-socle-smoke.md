# Ordre de mission1 — Installer le socle fonctionnel k6 et un smoke simple

**Préparation seulement.** Résultat demandé : une structure petite, documentée,
reproductible sous Linux, avec un scénario volontairement simple qui atteint de
vrais endpoints existants. Pas encore de campagne auth complète ni de performance.

## Entrées et décisions

Lire AGENTS, [recherche](20261029-k6-recherche-et-enchainement.md),
[ADR0504 Proposed](../adr/0504-validation-fonctionnelle-linux-k6.md) et
[contrat Proposed](../contracts/k6-functional-linux.md). Ratifier les frontières
avant code ; architecte pour toute modification structurelle. Les ADR0200–0202
restent Accepted,0412 Implemented localement ; pas preuve k6 acquise.
Revalider HEAD/diff et WIP étrangers, puis préparation/config/start utilisateur
pour cette mission. QA proportionate proposée, commandes exactes dans sa policy.

## Livrables autorisés

- `ops/tests/k6/README.md`, configuration d'exemple sans secret, version k6 et
  Chromium épinglées/provenance/checksums, quelques helpers nécessaires seulement.
- Un smoke `k6/http` avec allowlist fermée de GET publics/readiness réellement
  existants. Exemple cible : IAM `/iam/health` après vérification de son contrat,
  pas route inventée ni serveur factice de remplacement. Aucun seed ou POST caché.
- Entrée Linux explicite pour lancer un scénario et produire un résumé non secret,
  reliée aux gardes/baux existants. Pas nouveau déployeur ou API d'administration.
- Démonstration locale Linux de disponibilité du module navigateur avec Chromium
  si ce prérequis peut être vérifié sans créer une UI ni une campagneOAuth.
  Un succès HTTP seul ne qualifie pas Chromium ; marquer le prérequis séparément.

## Architecture et exclusions

Structure V1 du contrat ; utiliser JavaScript local simple avant d'ajouter bundler,
TypeScript ou dépendances. Aucun Grafana/Prometheus/Cloud, pluginxk6, k6Operator,
dashboard, framework ou OHA. Pas compilation/tests Rust dans Docker. Pas changement
service/API/config d'identité pour rendre le smoke vert. Aucune migration de suite
existante, aucun lancement de la mission2 ou3 par effet de bord.

Runner Linux hors cluster ; vérifier les endpoints depuis son espace réseau.
Conserver TLS et sandbox, pas de `insecureSkipTLSVerify`/ignore-certificate-errors.
Des exemples Docker ne constituent pas une autorisation de runtime privilégié.

## Acceptation et QA bornée

1. Sur la cible autorisée, un run1VU/1itération vérifie le statut et un contenu
   stable pertinent, pas seulement « socket ouverte ». Nombre de cas exact/non nul.
2. Check volontairement faux → exit non nul ; cible incorrecte ou entrée manquante
   → refus/échec explicite, jamais succès par zéro requête. Réutiliser les endpoints,
   sans développer une nouvelle infrastructure de mocks.
3. Cas absent/phase interrompue détectés ; journaux et erreurs sans URL sensible
   ni credentials, sentinelles de confidentialité vérifiées.
4. Versions et provenance enregistrées. Commandes typiques à figer après choix
   du script : `k6 version`, `k6 inspect <smoke>`, `k6 run <smoke>`. Aucune sortie
   de ces commandes n'est prétendue exécutée dans cet ordre de mission.
5. Cleanup possédé vérifié sur succès et échec précoce, inventaires avant/après,
   registre contemporain si des ressources sont créées. Pas de runtime réveillé
   pour rédiger les documents ou faire les contrôles statiques.

## Organisation et sortie

Un auteur outillage suffit ; contrôle documentaire/sécurité ciblé seulement là où
sélection de cible, credentials ou baux changent. Pas pipeline systématique.
Scope : dossier k6, raccordementLinux minimal explicitement nommé et docs ; toute
extension infra exige préflight/revue appropriés. Livraison intégrée et vérifiée
avant consommateurs. Ledger `.cursor/handoffs/20261029-k6-01-socle.md` au lancement,
preuves PASS/FAIL/INCONCLUSIVE, limites et procédure de reprise. Aucun essai antérieur
k6 dans le dépôt n'a été localisé par recherche de noms ; pas audit exhaustif déclaré.
