# Parent Ubuntu des trois scénarios k6

## Mandat et statut

GO utilisateur : exécuter health, OAuth Chromium et SAN sur GitHub Ubuntu jetable,
indépendamment du poste Windows, en consommant les images déjà sauvegardées.
Contrat `docs/contracts/k6-three-scenario-ubuntu-ci.md` toujours **Proposed**.
Cette implémentation n'est pas encore une qualification E2E réussie.

## Localisation / impact

- Workflow manuel `.github/workflows/k6-e2e.yml`, inputs explicites run/attempt
  de packaging et SHA applicatif ; permissions contents/actions lecture seulement.
- `ops/tests/k6/ci/image_input.py` : admission du run master réussi, digests API
  et interne, inventaire fermé, provenance et ABI des images. Aucun fallback
  cache/rebuild ; applications T et SDK S restent distincts des harnesses.
- `runtime.py` : kubeconfig privé, cluster mono-nœud unique au run/attempt,
  reçus Docker create contemporains, processus liés à PID/UID/start et cleanup
  indépendant. Les labels détectent un doute mais n'autorisent pas une adoption.
- `campaign.py` : PKI/credentials neufs, chart des backings existant puis chart
  natif opt-in ; aucun service reconstruit. JWKS direct/Service en TLS vérifié,
  configuration Envoy chargée, cinq phases inchangées et deltas exacts.
- `browser.py` : distribution complète vérifiée, base NSS privée et CA recoupée ;
  sandbox et TLS obligatoires. Aucun sysctl, exception AppArmor ni no-sandbox.
- `provision.py` : acquisition explicite des CLI épinglés, sans démarrer de runtime.

Le retrait du cluster est limité au cluster jetable possédé et aux IDs reçus,
après arrêt gracieux. Aucun prune ni retrait de ressource Windows ou d'autre
mission. Les images du runner restent à la destruction de la VM ; les preuves
publiées sont une liste fermée, jamais les clés, configurations privées ou logs.

## Validation et limites

Tests offline d'admission/refus, restauration et fermeture, plus régressions CI
existantes : **71 tests CI PASS, 10 régressions natives PASS, aucun skip**.

annulation dure du runner peut empêcher le reçu final ; le verdict doit rester
incomplet plutôt que prétendre zéro fuite.

faire l'objet d'un accord utilisateur distinct : profil unique, attachment exact,

distincts, NoNewPrivs, UID et seccomp renforcé) ; ne pas affaiblir ce témoin.

Références : [restrictions Ubuntu24](https://documentation.ubuntu.com/release-notes/24.04/#unprivileged-user-namespace-restrictions),
[politique AppArmor upstream](https://gitlab.com/apparmor/apparmor/-/wikis/unprivileged_userns_restriction.md),
