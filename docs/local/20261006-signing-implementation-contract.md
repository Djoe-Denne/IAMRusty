## 2. b — version provider et lifecycle avant retrait privé

### Binding et contrat Transit

- Ajouter à `SigningKey` une **version explicite** `provider_key_version: Option<u32>` : Transit exige `Some(v)` avec `v>0` (stockage SQL avec conversion entière vérifiée) ; jamais `0`, `latest` implicite ou default inventé à 1. PEM test/remote existant peuvent rester `None` lorsque leur référence existante suffit au contrat actuel. Pas de version/credential/keyref publiée dans JWKS.
- Conserver les ports `domain/src/port/signing.rs` : Sign/GetPublicKey et `OrganizationSignerProbe`/`OrganizationSignerRotator`. Préférer des opérations Sign/GetPublicKey **paramétrées par le binding enregistré/version** plutôt qu'un nouveau framework de résolution. `JwtTokenService` sélectionne la ligne Active primaire avant de construire le JWS ; `kid`, public et version viennent de cette ligne, pas d'un kid/provider plateforme figé au boot. Adaptateur refusant une combinaison owner/keyref/credential/version incompatible ; cache possible du public canonique, jamais de l'autorité Active.
- `TransitSigningProvider::{new,sign_digest,public_key,fetch_public_key_pem}` : envoyer `key_version=v`, SHA256 préhashé de 32 octets, `prehashed=true`, `hash_algorithm=sha2-256`, `signature_algorithm=pkcs1v15`. Lire **`data.keys[v.to_string()].public_key`**, jamais `values().find_map` ni `latest_public_key` en secours. Public fourni/caché toujours lié à cette version et confronté au public fournisseur/probe d'enrôlement.
- Parser strictement la signature `vault:v{v}:<base64>` ; rejeter version différente, préfixe/format/base64 invalides et réponse sans version. Garder validation locale de la signature contre le public attendu avant émission ; une signature mathématiquement valide n'autorise pas à ignorer la version réponse.
- Transit concret : création `POST /v1/transit/keys/{name}` RSA2048 non exportable, lecture contrôlée des propriétés/public/version ; rotation **du même nom** `POST /v1/transit/keys/{name}/rotate`, découverte de la version successorale puis lecture/probe/sign **épinglés**. La découverte de `latest_version` n'est autorisée qu'à l'enrôlement après l'opération, jamais pour signer ou lire un public déjà admis. Un nom existant incompatible/non-versionnable est refusé.
- Pas de réseau sous verrou SQL. Le fournisseur peut conserver une version non admise après échec IAM : aucune compensation/destruction de clé prétendue. Pas de retry automatique de Rotate après timeout ambigu. Si rotations concurrentes rendent impossible d'identifier un successeur prouvable sur le binding autorisé, **STOP** ; ne pas prétendre que la lecture du latest prouve une création exclusive. Une version successorale effectivement identifiée/probée peut être épinglée indépendamment des rotations ultérieures.
- RemoteHttp reste Sign/GetPublicKey, rotation non supportée actuellement : conserver ce refus explicite, ne pas inventer Rotate/KMIP/cloud. Une impossibilité de rotation/enrôlement sûr d'un fournisseur est une escalade, pas une rotation PEM.

### Séquence et courses

1. Lire binding/Active et une révision writer monotone de scope avant I/O. Étendre la persistance locale avec une révision de scope conservée même après disable/absence d'Active ; `expected_active_kid` seul ne clôt pas un configure/probe retardé après révocation. Aucun timestamp utilisé comme epoch.
2. Obtenir/créer/rotater la version autorisée hors lock ; public canonique + preuve de possession sur **cette version**, owner/issuer/kid/RS256 fixés. Configure identique compare binding complète **version comprise** et n/e normalisés : retourne la ligne effective inchangée, sans nouveau kid/churn/timestamps.
3. Courte transaction writer : revalider scope/révision/binding/capacité après probe, insérer Pending admise, publier une révision canonique durable incluant Pending ; Active précédente intacte. Reprise d'une Pending identique = pas de nouveau Rotate ni double charge.
4. Promotion dans **une autre transaction** : vérifier révision attendue, Pending/binding/version/probe, prépublication durable, taille et droits de transition ; retirer l'ancien Active et activer la nouvelle version atomiquement. Retourner la ligne committée. Disable/revoke concurrent incrémente la révision et invalide toute continuation antérieure, y compris s'il ne reste aucun Active.
5. Garder N public Retiring jusqu'à retraite + TTL access configuré + skew60 ; ne pas coder TTL900. Revoked et Retiring expirée ne sont pas publiées ; rotation fournisseur seule ne révoque aucun JWT offline. Prépublication durable ≠ preuve que tous les caches ont rafraîchi : pas de promesse zéro-401 ni d'attente réseau sous lock.
6. Après Sign et vérification du candidat : `confirm_active_for_emission` fait un SELECT **neuf, autocommit, primaire**, compare toute binding et version, sans transaction antérieure à l'I/O ni verrou global d'émission. Les codecs access ET registration gardent ce même point de linéarisation.

## 4. d — slots, représentation préparée, snapshot matérialisé

### Candidat chiffré, prouvé arithmétiquement seulement

- `SLOT_BYTES_MAX=4096` = maximum **d'une entrée JSON compacte**, pas PEM et pas séparateur ; `SLOT_CAP_ORG=8` ; `SLOT_COUNT_GLOBAL=191` (epochs publiables, pas entreprises).
- Ajouter les partitions nommées `SLOT_CAP_PLATFORM=16` et `SLOT_COUNT_GLOBAL_ORG=175` (=191−16). Les orgs ne peuvent pas emprunter ces 16 places, même si la plateforme est vide. Churn org inchangé 4/3600s.
- Avec enveloppe vide E=11 (`{"keys":[]}`), coût majorant d'un slot =4096+1 séparateur : **11 + 191×4097 = 782538 ≤ 786432 < 1048576**. Coût org ≤175×4097=716975≤720896. Après org et enveloppe il reste **69446 ≥65536** pour plateforme ; 16×4097=65552 y tient. Attention : 16 entrées maximales + séparateurs ne tiennent PAS dans exactement65536 ; les places org volontairement plus conservatrices financent ce dépassement. La réserve minimale64KiB est préservée, pas une égalité artificielle.
- Ces valeurs sont un candidat sous Proposed : calcul statique vérifié ici, **aucun test de serializer exécuté**. Accept humain des nombres/compromis en fin ; jamais « capacité runtime prouvée ».
- À l'admission du nouveau binding : parser le RSA une fois, canoniser n/e, construire la représentation publique préparée et vérifier ponctuellement sa plus longue variante (`retiring`, 8 octets contre pending7/active6) ≤4096. Les autres bindings/champs sont immuables. Cette validation d'entrée n'est pas une tarification exacte par clé ni un rescan du jeu complet.
- Maintenir RSA2048..8192, exposant impair≥3/u64/backend, kid32hex UUIDv4, issuer URL≤1024 octets UTF8, alg/use/constants et org UUID. **1024 octets issuer ne prouvent pas 1024 octets JSON** : échappements adversariaux testés, taille réelle de l'entrée contrôlée. Aucun champ extensible non borné, provider ref, PEM, version ou secret dans l'entrée publique. Tout changement DTO/serializer/variant invalide la preuve avant activation.
- Test dédié à écrire : arithmétique enveloppe/partitions/séparateurs, vrais DTO compacts maximalistes autorisés (Unicode/contrôles/quotes/backslash, n8192/e64, scope/org/status), refus >4096 y compris 4097, snapshot≤782538≤writer<SDK1MiB. Référence attendue indépendante, pas calcul auto-confirmant à partir de la fonction d'admission.

### Persistance et opérations

- Choix local recommandé : canonical public n/e préparés par binding en DB ; table singleton de publication matérialisée (révision globale, payload/DTO compact, horloge de matérialisation, prochaine expiration, TTL/skew de politique). Révision de scope introduite en b distincte de la révision globale de publication. Pas de compteur process ni nouveau framework/cache d'autorité.
- Admission sous le verrou global actuel puis scope/issuers/rows ordonnés ; horloge `statement_timestamp()` **après attentes**. Agrégats COUNT SQL/index sur predicate publiable et scope + churn indexé ; aucun chargement/parsing des historiques PEM ni recalcul des trois prix par entrée. L'ordre et l'autorité des verrous ne changent pas.
- Tous writers (insert Pending, configure, promote, update, bootstrap, retire, revoke) mettent à jour lignes préparées et snapshot dans **la même transaction**. Construire le snapshot proposé depuis les entrées publiques préparées bornées, vérifier sa vraie taille avant commit/activation/retraite ; rejet = aucun effet partiel. O(N) assemblage du snapshot lors mutation est permis ; les rescans/reparses d'admission et `reserved_entry_bytes`/prix exact global disparaissent.
- Expiration : GET lit sur primaire payload + horloge DB + deadline. Si deadline atteinte (ou TTL/politique diverge), transaction courte avec même verrou writer, relecture et rematérialisation avant de répondre. Pas de scheduler obligatoire ; pas de libération au compteur alors que GET ressert l'ancienne Retiring. Filtre Retiring exact et même horloge pour comptage/publication ; timestamp de retraite jamais renouvelé.
- `SigningKeyPublicationSnapshot`, `TokenUseCaseImpl::get_jwks`, `JwkSet` et le handler JWKS consomment le snapshot validé, sans reconversion PEM du jeu complet. Garder API DTO pour le seed a2 ; servir les bytes préparés si nécessaire sans changer l'enveloppe publique. Payload vide autoritatif ≠ DB erreur ≠ registry non initialisée. Pas de bootstrap depuis GET, d'éviction ou de LIMIT sur publication admissible.

Révocation/drain restent possibles hors capacité ; état historique invalide est signalé, jamais silencieusement tronqué.
