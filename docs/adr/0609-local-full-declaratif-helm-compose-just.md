## Contexte

**Baseline historique :** les constats des deux paragraphes suivants décrivent `51996139ec31317aaef85e49ab3c9266591f3902`, où cette cible était **Unimplemented**. Ils ne décrivent pas le code livré au freeze de la mission ; son état **Partial** est détaillé ci-dessous.

Le rendu effectif est Kustomize **puis** Python : `render-local-full.py::render`, `local_full_openbao.py` et `local_full_oauthconnect.py` créent/modifient workloads, agents, configuration, politiques et références. `proof_profile` construit aussi la variante de preuve. Le profil brut ne suffit donc pas à décrire le système. `deploy-local-full.py:910-991` répartit les objets par noms, quiesce les applications, démarre une première réplique puis force quatre services à deux. Cette séquence protège les migrations de démarrage : un apply global n'est pas équivalent.

`local_registry.py` définit Zot, son réseau, ses volumes et ses auxiliaires par commandes Docker. Le bootstrap transforme le manifest Calico puis exécute `set env`. Les règles API sont patchées en fonction de la cible ; l'exception ingress du 9 novembre est manuelle et peut disparaître au prochain apply. Les définitions des Pods de stockage auxiliaires sont aussi en Python (`local-full-storage.py:103-125`).

**Contradictions à conserver visibles :** 0600 propose Flux/Kustomize first-party et Helm tiers, mais reste **Proposed / Unimplemented** ; le shim Envoy Gateway n'est pas une installation Helm opérationnelle. OpenTofu n'a pas d'adaptateur cloud livré dans cette tranche. 0607 propose la distribution Zot ; 0608 autorise un parcours local explicite kind-load. Ni Flux ni GKE ne doivent être inventés pour satisfaire cette migration. Les mentions historiques de compilation en conteneur dans 0606 ne remplacent pas la règle actuelle Windows pour le développement.

Analogue hors plage : 0500 photographie déjà une configuration typée et une description Compose, sans second loader spécifique au déploiement. Le nouveau chart alimente ces mêmes contrats de configuration, sans modifier cette ADR Accepted ni présenter sa liste Compose historique comme l'inventaire actuel du lab.

## Décision

**Le profil local-full complet a une définition standard unique ; Python n'est plus son moteur de construction ou de séquencement.** La migration concerne les Ops déjà livrés, pas une nouvelle plateforme cloud.

1. **Helm, rendu local seulement, pour local-full.** Un chart versionné décrit tous les workloads et auxiliaires du profil, y compris leurs ServiceAccounts/RBAC, Services, ConfigMaps, PVC, NetworkPolicies, probes, agents OpenBao, init containers, volumes, configuration TOML/HCL/Envoy et répliques. Des valeurs typées sélectionnent les profils existants et les phases. Le besoin de rendre ensemble les objets et leurs configurations embarquées justifie Helm plutôt qu'une nouvelle succession de substitutions Python après Kustomize. Le chart n'utilise ni `lookup`, plugin, post-renderer spécifique, hook de mutation, ni génération aléatoire. **Pas de `helm install/upgrade`**, donc pas de transfert implicite d'ownership ni de secrets dans l'historique d'une release.
2. **just, déjà présent, pour le graphe d'opérations.** Un fichier dédié déclare les phases et leurs dépendances, les appels au renderer et les attentes standard Kubernetes. Aucun contrôleur GitOps supplémentaire n'est requis pour ce lab. Le graphe reste à granularité de phases, sans noms d'applications ; aucun port ligne à ligne du script vers du shell. Les ressources déclarent leur catégorie et leurs besoins ; les gardes interprètent seulement ces métadonnées bornées. La réconciliation et les rollouts restent ceux de Kubernetes.
3. **Migrations : conserver les phases transitoires, les sortir du code.** Quiescence autorisée des seules applications possédées, fondations/dépendances/bootstrap, applications à une réplique pendant les migrations au démarrage, attente de disponibilité, puis répliques finales déclarées. Verrou exclusif et refus des Jobs concurrents restent des gardes. Aucun nouveau mode migration Rust ou Job de migration fictif n'est supposé. Les Jobs existants de bootstrap/seed restent déclarés, avec leur idempotence propre.
4. **Compose pour le Zot applicatif hors Kind.** Le service, les auxiliaires de préparation/transport OCI, le réseau, les volumes, les droits, TLS/mTLS et ACL sont déclarés dans Compose et des fichiers de configuration. Le registre P4 reste distinct. Un registre déjà enregistré est conservé sous ses IDs actuels : Compose n'est pas une procédure d'importation de son conteneur. Pas de recréation/adoption implicite ; le contrat prévoit un mode de réemploi vérifié et une transition additive explicite. **Publier vers ce registre existant conserve le helper Skopeo nécessaire**, désormais déclaré Compose : projet/conteneur de tentative neufs, réseau externe vérifié, reçus propres au transport, aucun nouveau registre/réseau/volume persistant ni transfert d'ownership. Archive, destination, certificats et configuration sont montés en lecture seule ; seuls sorties/tmp de tentative sont inscriptibles, sans socket Docker ni accès aux volumes de données Zot. Le helper possédé est arrêté même sur échec, sans suppression implicite. Le registre conserve identité/configuration/stockage et ses permissions OCI historiques ; les écritures OCI normales restent la finalité de `publish`.
5. **Kustomize pour le CNI épinglé ; Kind pour sa topologie.** Calico 3.29.7, son CIDR et `FELIX_IGNORELOOSERPF` deviennent un paquet vérifié et un overlay, sans modification textuelle ni `set env`. Les adresses API et exceptions ingress autorisées sont des inputs de cible attestés, rendus par les déclarations réseau ; les tests UID/RV/préimage/postimage restent obligatoires. Une IP observée n'est ni une autorisation ni une valeur portable.
6. **Déclarations aussi pour les opérations auxiliaires.** Les Pods de backup/restore ont des templates déclaratifs. Les recettes d'images restent dans les Dockerfiles et sont assemblées par Buildx Bake ; la sélection/description statique des cibles sort des tables Python. Python conserve l'instantané des sources, les preuves d'artefacts et la validation finale, pas une deuxième recette de build. Pour la PKI, autorités, identités, SAN, usages et bundles publics résident dans `ops/scripts/local-full-certificates.cnf` : OpenSSL consomme directement les sections d'extensions, et le wrapper lit les métadonnées publiques sans fabriquer de `.ext` ou de noms/SAN par service. Le contrat borne ces opérations aux capacités déjà livrées.
7. **Exceptions Python fermées et justifiées.** Validation d'inputs/ACL, wrappers CLI, ancrage/baux/UID et non-adoption, transfert confidentiel et CAS de secrets, appels/gardes PKI et protection du matériau privé, provenance/fraîcheur, reçus et diagnostics. L'exception PKI ne couvre pas un second catalogue statique : `AUTHORITIES`, `leaf_profiles()` et `registry_profiles()` restent des vues compatibles de la déclaration OpenSSL. Les seeds métier OpenFGA/OpenBao et protocoles de sauvegarde peuvent rester là où aucune déclaration standard ne garantit leur sémantique. Leurs enveloppes Kubernetes sont déclaratives. Pas de nouveaux générateurs YAML/JSON/Dockerfile, de listes de services cachées ou de remplacement impératif dans un autre langage.

**Précision snapshots privés (arbitrage parent du 2026-11-09, pas Accept) :** **pas de bascule snapshot Agent cette session au pin OpenBao 2.6.2**. Conserver le seul client HTTP strict déjà livré comme exception fermée, justifiée par le défaut upstream précis ci-dessous, et non par l'habitude Python. Toutes les définitions publiques de ressources/configurations/policies/plans/gabarits passent néanmoins dans le chart/déclarations : plus de dictionnaires ou générateurs publics par service en Python. Le helper reste limité à l'accès HTTP strict indispensable, l'hydratation privée, les validations et la promotion atomique ; aucune nouvelle chaîne Agent→fallback Python n'est introduite puisque la bascule n'a pas commencé. Les seeds CAS métier restent distincts. Rôles/SA/audiences/CA/permissions/champs, refus de données partielles, TTL/non-root et contrôles de préimage/provenance sont conservés ; aucun token de validation dans IAM/simulateur. Le token OpenBao dans le TOML Lazaret est l'exception applicative legacy maintenue.

**Défaut upstream vérifié en source le 2026-11-09 :** dans **2.6.2**, `BAO_DISABLE_REDIRECTS` existe et protège le client templating, mais l'auto-auth clone le client avant le login Kubernetes ; `api.Client.clone` ne recopie pas `DisableRedirects` et `NewClient` ne restaure pas ce champ du défaut d'environnement dans le clone fourni. Un environnement fermé peut supprimer les proxies ambiants, pas corriger ce clone. **Ce défaut bloque la cible native future, pas la réception de la migration Ops actuelle sous l'exception explicite.** Pas de bump/patch OpenBao, proxy ou outil détourné dans cette mission. La cible future reste Agent auth/read/render + garde offline validation/promotion sur staging mémoire ; sa levée exige un **pin exact autorisé** et une preuve des options/flags et du refus des redirections **auth et lectures**, ainsi que du proxy ambiant, avant remplacement. Le [contrat §4.1](../contracts/ops-local-full-declarative-iac.md) distingue les critères actuels et futurs ; aucune qualification Agent native ou modification des autres scopes n'en découle.

Cette décision introduit une **exception locale explicite** à la proposition first-party Kustomize de 0600, pas une ratification ni une réécriture de sa cible cloud. Le legacy, les profils distincts et les frontières P4 restent préservés. Le contrat fixe la compatibilité des commandes et le retrait effectif de l'ancien générateur.

## Conséquences

- Impact **architectural / API-contrat Ops** : renderer, déployeur, reprise d'epoch, bootstrap, registre, stockage auxiliaire, recettes d'images, commandes et tests de parité. Aucune crate, route métier, migration de données ou dépendance SDK nouvelle.
- Helm devient un outil effectif, avec version exacte et compatibilité à verrouiller et qualifier ; le simple lint d'un chart ou le succès d'un template n'est pas une preuve live. just ne fournit pas de réconciliation continue, Compose ne garantit pas la non-adoption et un Job n'offre pas l'exactly-once.
- Les doubles sources local-full devenues inutiles et leurs branches Python doivent être supprimées après parité ; exporter un YAML tout en conservant les constructeurs ne satisfait pas cette ADR. Les bases partagées encore consommées par le legacy ne sont pas supprimées.
- Les secrets restent hors valeurs Helm, sorties publiques et state OpenTofu. Le rendu public doit être possible sans secret. Les opérations sur les secrets et les ressources existantes gardent leurs restrictions, même lorsqu'un outil standard permet davantage.
- Migration du déployeur **sans destruction du lab** : noms/selectors stables, UID vérifiés, pas de prune, rotation CA, recréation PVC/registre ou changement automatique de profil. L'autorisation destructrice historique de 0608 n'est pas reconduite.

## Alternatives écartées pour ce périmètre

- **Kustomize puis post-traitement spécifique** : conserve précisément le générateur et les mutations de configuration à retirer. Kustomize pur reste valable pour les ensembles statiques ; il n'est pas remplacé globalement.
- **Helm seul / apply global** : ne couvre pas le verrou d'opération, la quiescence autorisée ni la barrière entre bootstrap, démarrage migrateur et scale-out.
- **Flux/Argo/kapp ou Helmfile maintenant** : ajoutent un moteur, une surface de privilèges ou une migration d'ownership sans nécessité pour ce graphe local. Flux demeure une proposition cloud, pas une livraison implicite.
- **Task/Ansible/nouveau moteur maison** : just existe ; déplacer les mêmes boucles et constructeurs dans un autre langage ne réduit pas le problème.
- **OpenTofu pour les Pods/commandes locales** : ne livre aucun hébergeur manquant, introduirait state/providers et risques de secrets sans supprimer les gardes locales. Son contrat cloud actuel reste honnêtement non provisionnant.

## Non décidé ici

Accept formel ; cloud/GKE/Flux, production/HA, retrait métier des connecteurs historiques, refonte de l'operator Apparatus, nouveaux mécanismes de migration Rust, conversion des protocoles de seeds en contrôleurs. Une qualification navigateur ou une garantie de performance ne découle pas de ce choix d'outils.

### Clarification de compatibilité — 2026-11-09

Historique de l'arbitrage sur un **candidat antérieur** au freeze : le constat ci-dessous n'est pas une réouverture de la livraison finale ; ses dispositions et la portée des vérifications actuelles sont distinguées dans l'état Partial ci-dessus.

La formule initiale du contrat « ce chemin ne crée plus rien » visait les ressources persistantes du registre, mais interdisait aussi, à tort, son transport historique : à la base `5199613`, `local_registry.py::copy` (`375-401`) crée un Skopeo via `helper` (`189-198`). Dans le candidat du worktree `ops-iac-registry` consulté, `copy` (`489-490`) refuse les états sans `compose` ; `test_legacy_publication_is_explicitly_blocked_before_export_or_creation` entérine donc une régression de capacité, pas une parité. `registry/publish.compose.yaml` et `publish.sh` fournissent déjà une déclaration de transport, mais le montage global `/work` inscriptible reste à séparer pour protéger les inputs. Le §5 du contrat précise l'exception bornée et les oracles attendus ; il n'autorise ni importation du registre ni transport HTTP Python de remplacement. Les résultats 25 tests + 4 refresh rapportés par le parent ne constituent pas une preuve live de ce delta ; **live NOT RUN**, Statut/Réalité inchangés, aucun Accept implicite.
