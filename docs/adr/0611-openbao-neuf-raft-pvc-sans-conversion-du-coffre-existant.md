## Contexte

Le coffre déclaré dans `ops/deploy/charts/local-full/values.yaml:2174–2271` est un Deployment OpenBao **2.6.2**, lancé par `files/public/337352d157c7/run-openbao.sh` en mode **DEV/mémoire**, avec un `emptyDir.medium: Memory` sur `/run/openbao`. Le script seed puis révoque son root éphémère. Le listener HTTPS ne rend pas ses données persistantes. Reconfigurer ce Pod pour ajouter du stockage perdrait son coffre mémoire : ce serait une migration destructive cachée derrière keep-data.

La cible 0610 retire l'hydratation Ops Python/Agent, pas les accès métier Transit/KV. `services/Lazaret/configuration/src/lib.rs::VaultConfig` contient un `token: String`, une URL et une CA, pas une API token-file. [0506](0506-mutualisation-openbao-conditionnee-aux-usages.md) ne décide aucune extension SDK ; le [pointeur wiki antérieur](../../obsidian/AI%20FOR%20ALL/projects/aiforall/decisions/0506-mutualisation-openbao-conditionnelle.md) porte cette distinction, pas une décision de stockage local. Les fichiers privés complets valides de l'opérateur restent des inputs, sans nouveau modèle de menace d'administrateur malveillant.

## Décision proposée

**Coffre existant compatible HTTPS : le conserver tel quel, sans apply/upgrade/rollout/reseed automatique. Nouveau coffre : serveur non-DEV, Raft mono-nœud sur PVC dédié.**

- Pin image 2.6.2 inchangé ; PVC `openbao-data`, stockage `/openbao/data`, identité Raft stable `openbao-local`, une seule réplique et remplacement sans chevauchement des writers. HTTPS vérifié pour toute commande et tout client ; aucun nouveau listener HTTP de bootstrap. Ce n'est ni une offre HA ni une promesse de conservation après destruction des nœuds Kind.
- L'absence d'un Deployment ne prouve pas l'absence d'un coffre : un PVC conservé peut déjà être initialisé. Après démarrage du serveur, utiliser son état natif `initialized`/`sealed`, jamais un ancien fichier ou l'échec d'une commande comme preuve de « coffre neuf ». Ne pas attendre readiness unsealed avant init/unseal, ni utiliser sealed/non initialisé comme motif de redémarrage liveness.
- Première initialisation native : `operator init -format=json -key-shares=1 -key-threshold=1`, sortie privée hôte créée exclusivement **avant** l'appel, sans écrasement ; unseal d'une seule part par JSON stdin au CLI natif, mounts explicites dont KV v2 `secret` (non créé implicitement hors DEV), auth/policies/rôles et seeds nécessaires. Racine éphémère de bootstrap, jamais credential du produit, puis révocation après bootstrap réussi. Pas de gestionnaire maison de rotation/backup/lease/ACK, journal de reprise ou epoch manager.
- Credentials métier : inputs complets fournis ou tokens natifs limités aux politiques du consommateur, sorties privées ; aucun secret argv/log/Helm public. Les tokens issus du root doivent être orphelins s'ils doivent survivre à sa révocation. Expiration/remplacement opérateur explicites, pas de token permanent ou de renouvellement maison ajouté silencieusement. Une configuration produit complète doit être fournie avant de lancer le consommateur ; aucun nouveau composeur de TOML.
- `reset-data` efface le coffre du lab mais préserve CA et fichiers hôtes. **Préserver un ancien fichier ne le rend pas valable pour le nouveau coffre.** Nouvelle initialisation = chemin de sortie neuf explicite et nouveaux credentials liés au coffre neuf ; aucune recherche de « dernière clé », réutilisation automatique de root/token ancien, écriture aveugle ou protocole de génération.

## Garde des clés — choix humain acquis, limité au coffre neuf du lab

L'utilisateur a explicitement choisi **« 1/1 local (Recommended) » : Shamir 1 part / seuil 1**, dans un fichier hôte privé protégé, pour le **coffre neuf du lab mono-opérateur uniquement**. Ce choix remplace la recommandation 5/3 précédente et lève la réserve préalable à l'automatisation init/unseal du poste. Il n'offre pas de séparation entre détenteurs : la possession de cette unique part suffit à déverrouiller ce coffre. Pas de généralisation à la production ou au multi-opérateur ; coffre existant et anciennes clés hôtes intacts, sans rekey ni migration de seal.

`seal "static"` existe au pin documenté 2.6.x, mais **n'est pas le choix humain** ; aucun auto-unseal statique/KMS ni fichier de clé suffisante monté implicitement au serveur. La part Shamir reste dans le fichier privé du poste explicitement désigné. Les chemins d'init exclusive/unseal/tokens et la remise humaine des configs complètes restent requis ; ni recherche latest ni protocole d'epoch ne remplacent ces inputs. Ce choix ciblé n'implique pas l'Accept de toute l'ADR.

## Alternatives et conséquences

- Backend `file`/PVC : réellement disponible en 2.6.x, mais non transactionnel et sans verrou système selon sa documentation ; Raft reste natif sans dépendance supplémentaire et évite ce compromis. Un nœud ne fournit toutefois ni réplication utile ni sauvegarde.
- Convertir DEV à la relance : perte mémoire certaine ; refusé. Migration/export/recréation du coffre ancien = opération distincte autorisée, pas livrée ici.
- Piper une clé dans `operator unseal` : **pas une interface non interactive au pin 2.6.2** ; le code utilise une saisie terminal cachée. Pour la voie fichier retenue, `bao write sys/unseal -` reçoit l'unique part dans un JSON sur stdin, primitive CLI/API standard, sans clé en argv. La saisie cachée interactive sans argument reste une primitive native, pas une obligation de garde séparée.
- Laisser le root ou créer des tokens enfants révoqués avec lui : ne remplace pas des credentials produit utilisables. Fichiers complets et durée de validité restent une responsabilité explicite de l'opérateur, pas un service de rotation déguisé.
