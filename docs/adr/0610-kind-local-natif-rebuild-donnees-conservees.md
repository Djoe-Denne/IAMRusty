## Contexte

L'utilisateur demande maintenant **une entrée qui reconstruit toutes les images applicatives et lance les services dans Kind**, conserve DB/cache/stockage par défaut et propose un reset destructif explicite du lab. Il retire du lancement les protocoles maison de bon cluster/daemon, ancrage, baux/ACK/nonces, reprise, provenance, refresh, backup et preuves. Les reporter en shell, PowerShell ou dans un nouveau moteur IaC ne répondrait pas à sa demande. Exécution directe par la racine, pas d'équipe ou de pipeline de rôles imposé.

Cette cible diffère de 0609/contrat v1.7, **Proposed / Partial**, qui conservait ces protocoles et leurs interfaces. Ce n'est pas une nouvelle obligation de parité avec ce candidat. Les analyses `minimalByFeature` du canvas fourni distinguent 31 buts conservés et 32 hors lancement ; parmi les 49 candidats provider sans outillage spécifique, 26 buts restent nécessaires et 23 sont retirés. Ces nombres ne mesurent pas des lignes supprimables et ne fixent aucune priorité.

Deux contraintes matérielles bornent le choix : `cluster-local-full.yaml` ne déclare aucun `extraMount`, et les PVC du chart utilisent `standard` ; détruire les nœuds ne préserve donc pas leurs données par magie. Au diagnostic initial du 9 novembre, `Dockerfile.build` montait un target Cargo persistant et appelait un collecteur Python ; `--no-cache` seul ne forçait pas une compilation Cargo neuve. Le chart historique était déjà déclaratif mais `local-full.just` déléguait ses phases à Python. Les livraisons partielles ultérieures sont distinguées ci-dessous, pas décrites par cette baseline historique.

## Décision

**Le lancement local devient un workflow court d'outils natifs, non transactionnel, sans framework de contrôle ou de preuve spécifique.**

1. **Une entrée `just kind-local`, reset explicite.** Elle enchaîne préparation privée, Bake, création/réemploi Kind, import natif, initialisations nécessaires, déploiement et readiness. `just kind-local reset-data` ajoute la destruction/recréation du seul cluster de lab dédié. Cible fixe `aiforall-local-full`, contexte natif explicite `kind-aiforall-local-full` ; aucun audit automatique d'identités du daemon/cluster ni protocole d'adoption. Les règles d'intervention des agents sur des ressources réelles restent applicables, hors code produit du lanceur.
2. **Build depuis le checkout courant.** Bake/Dockerfiles consomment les sources effectives et le SDK local, sans snapshot, surveillance de dérive ou reçu maison. `.dockerignore` exclut les secrets, sorties privées, `.tmp`, worktrees, targets Windows et artefacts parasites. Un producer Cargo natif construit les binaires déclarés avec un target vide **non monté en cache** ; les caches de téléchargement peuvent rester. `--no-cache` et une référence de build unique empêchent de réutiliser les anciennes images ; aucun prune ni nettoyage global.
3. **Distribution par `kind load`.** Toutes les images applicatives déclarées sont construites ; seules les workloads activées sont déployées. Un tag commun à l'invocation relie simplement Bake, import et valeurs Helm, sans attestation de provenance. Pas de registre applicatif Zot/Skopeo dans ce parcours. Le Zot P4/enveloppes reste une dépendance distincte si Apparatus est activé ; ses garanties métier ne sont pas retirées.
4. **Conservation par défaut, reset réellement destructif.** Les nœuds, PVC et dépendances de données sont conservés ; seuls les workloads de calcul sont remplacés après arrêt des writers. PostgreSQL/Redis/Zot P4 gardent leurs volumes. OpenBao DEV et LocalStack éventuellement volatils restent en fonctionnement plutôt que d'être redémarrés par un hash global de configuration. Le mode `reset-data` détruit le cluster dédié puis le recrée : perte assumée de tous ses états Kubernetes et node-local, pas des fichiers privés hôtes, images/caches Docker ou ressources externes. Aucune promesse de sauvegarde, de récupération après panne ou d'effacement forensique.
5. **Initialisations réelles, une réplique locale.** Garder les migrations SQL réellement livrées (`/app/migration up` dans les entrypoints des cinq services), la migration datastore OpenFGA, les DB/queues effectivement consommées et les seeds nécessaires. Un workload de calcul à une réplique suffit : pas de phase HA 1→2 par défaut. OpenFGA utilise son CLI officiel et un ConfigMap d'IDs conservé ; le [contrat §5.4](../contracts/kind-local-native-launcher.md) précise la commande native combinée store+modèle, le DSL/parsing officiel et la publication des IDs depuis l'hôte, sans adoption de stores ou replay au rebuild. OpenBao utilise ses documents et CLI natifs, sans client Python pour ces tâches. Pas de suppression de tuples, de store ou de KV au rebuild normal.
6. **Privé par fichiers complets, pas par composition Ops.** Les services consomment des TOML/JSON/credentials complets hors Git via Secrets Kubernetes standards. Ni composeur IAM, renderer privé ni manager d'epoch à conserver pour justifier Python. L'accès **métier** au coffre reste celui du produit et des ADR Accepted ; la préparation Ops des fichiers n'est pas une nouvelle API SDK. La limitation [OPS-OPENBAO-262-REDIRECTS](../guides/ops-declarative-boundaries.md) reste une dette bornée : pas de bascule Agent, bump, proxy, client détourné ou perte de protection implicite. Une capacité privée encore impossible à retirer doit être nommée, pas déclarée qualifiée.
7. **TLS et clés stables.** HTTPS sur les flux HTTP conservés, TLS natif PostgreSQL/Redis et autres protocoles concernés, CA/SAN/trust vérifiés sans mode insecure. **Exception Rust explicitement choisie par l'utilisateur :** étendre seulement la configuration Redis de Lazaret (`tls_enabled`, CA PEM explicite), son adaptateur et le raccord setup pour `rediss`/TLS serveur vérifié au pin redis 0.27.6 ; défaut plaintext conservé pour les profils/tests hérités, TLS activé dans le nouveau profil. Redis/données/backend restent inchangés, sans proxy ni extension SDK/domaine. Le [contrat §5.1](../contracts/kind-local-native-launcher.md) fixe l'API native `Client::build_with_tls`, les features synchrones Rustls, la sélection sûre de provider et les tests positifs/négatifs. OpenSSL et le `.cnf` existant portent la PKI ; clés et CA locales réutilisées indépendamment du rebuild et de `reset-data`. L'entrée de navigateur proposée est `https://127.0.0.1:18443` par `kubectl port-forward` standard vers Envoy, au premier plan : pas de tunnel propriétaire ou d'attestation IPIP. Ce port distinct évite de réutiliser le mapping historique 18080 réservé par les nœuds existants ; toute activation OAuth doit déclarer ses origines/callbacks correspondants.
8. **Première installation OpenBao distincte de keep-data.** [0611](0611-openbao-neuf-raft-pvc-sans-conversion-du-coffre-existant.md) **Proposed / Partial** propose Raft mono-nœud/PVC pour un coffre neuf, jamais la conversion du DEV mémoire existant. Le [contrat OpenBao v1.2](../contracts/kind-local-openbao-bootstrap.md) fixe chemins privés init/unseal/CA/tokens, init exclusive et absence de réemploi automatique d'anciens credentials après reset. **Choix utilisateur acquis : Shamir 1 part / seuil 1, fichier privé protégé pour le coffre neuf du lab mono-opérateur uniquement**, sans rekey de l'existant ni auto-unseal statique/KMS. Bootstrap/remise et unseal après restart ont désormais été observés dans le cycle opérateur borné ci-dessous ; Statut Proposed maintenu, aucune qualification générale inférée.

**GO utilisateur du 2026-11-11 (« cool go ») :** `kind-local` reste build/déploiement ; `local-stop` arrête les trois nœuds vérifiés via Engine local, `local-start` les reprend sans build/déploiement avec unseal/queues manquantes, `local-status` observe même le lab arrêté et l'ancien arrêt applicatif devient `local-apps-stop` ([contrat §1.1](../contracts/kind-local-native-launcher.md#11-cycle-natif-des-nœuds-existants--go-utilisateur-du-11-novembre-2026)). Ces contrôles bornés précisent le point 1 sans framework d'autorité ; **Proposed / Partial**, reprise automatisée end-to-end non qualifiée.

## Conflits explicites et invariants conservés

- La demande remplace, pour cette entrée, les exigences **Proposed** de 0606/0607/0609 concernant autorité/reprise, OCI applicatif, snapshot/provenance et compatibilité des anciennes commandes. Le code utile est réutilisable ; leurs PASS historiques ne qualifient pas cette nouvelle cible. Aucune ADR Accepted n'est réécrite ou supersédée.
- AuthN/AuthZ, frontières Apparatus, CAS métier encore consommé, crypto privée et contraintes de provider des ADR Accepted restent. Retirer un déployeur ne retire pas les contrôles du produit. Aucun changement métier Rust/SDK ; seule l'extension de transport Redis TLS dans Lazaret est autorisée, sans modifier domaine, backend ou schéma de données. Pas de fallback signing PEM ou credentials root applicatifs pour simplifier le lancement.
- Ne pas confondre retrait du framework d'autorité du lanceur et permission de purger un daemon partagé. Suppressions fixes au cluster dédié ; pas de `docker prune`, suppression par image globale, contexte protégé ou ressource étrangère. Le parent conserve inventaire/autorisation/registre d'intervention, sans installer ces procédures dans le lanceur.
- Un lancement à la fois, arrêt sur erreur native et relance explicite. Pas de verrou global, journal transactionnel, rollback de DB/KV ou reprise automatique. Une erreur de TLS, bootstrap ou migration reste un échec, pas un démarrage « dégradé » annoncé vert.
- **Écart de portée de la readiness Redis livrée :** `templates/redis.yaml` / README `kind-minimal` déclarent une probe TLS/CA/PING-PONG locale avec SNI, **pas une vérification hostname/SAN par `redis-cli 7.2.7 --sni`**. Elle ne prouve donc pas à elle seule la cible CA/SAN du §7 et ne peut pas être renommée en oracle d'identité serveur. Le client métier Lazaret Rustls conserve sa vraie IT CA/SAN antérieure ; son raccord de configuration au profil est maintenant présent, **sans handshake cross-Pod qualifié**. Limite/écart signalé au [contrat §5.3](../contracts/kind-local-native-launcher.md), **sans abaisser la cible ni ratifier une exception**, sans nouveau choix structurel dans cette photographie.

## Alternatives écartées

- **Conserver les wrappers/ACK de 0609 ou les traduire en PowerShell** : contraire au nouveau périmètre fonctionnel ; seuls les appels natifs et branches élémentaires d'installation sont nécessaires.
- **Détruire le cluster à chaque lancement et promettre la conservation** : faux avec les PVC/node-local et l'absence de montages hôtes actuels. Externaliser le stockage serait un autre chantier.
- **Réutiliser le cache target avec `--no-cache`** : ne garantit pas un rebuild Cargo complet ; le target neuf rend l'heuristique de timestamps inutile.
- **OpenTofu/Ansible/GitOps pour verrouiller le script** : nouveau moteur sans besoin local retenu. Le CLI OpenFGA suffit à l'initialisation, pas de provider/cloud imaginaire.
- **Contourner le défaut Agent OpenBao 2.6.2** : hors mandat. Les fichiers privés complets suppriment le besoin d'hydratation Ops multi-sources quand le produit les accepte ; ils ne corrigent ni son backend volatile ni ses besoins métier au coffre.
